第一阶段：建立真实基线和项目边界
1. 核对本地、GitHub 和旧网站的版本关系。 确认哪些功能只在本地，哪些已提交，旧网址实际展示哪个版本，建立可恢复的基线。
2. 建立全站资产清单。 列出地图节点、理解页、学习路径、软件、教程、资料、图片与中英文版本，记录对应来源和发布状态。
3. 重新核验现状。 将文档中的历史检查结果与本次实际检查分开，记录已确认问题、待核验事项和缺失功能。
4. 固定产品范围。 本轮包含免费阅读、地图、分层学习、中英双语、账号同步、搜索可见性；投稿与社区治理进入后续阶段。
5. 建立统一任务清单。 每项任务记录目的、依赖、交付物、验收方法和状态，避免开发过程中不断扩张范围。
交付物是一个可信的现状清单和实施清单。现有页面是否保留、修订或暂缓推广，应依据内容检查结果决定，不能由队列状态直接推断。
第二阶段：把“学习全貌”和“理解原理”设计成两条清晰入口
6. 设计“快速认识 AI 世界”入口。 从用户熟悉的场景出发，解释 AI 能做什么、主要组成、共同基础和局限，最后引入地图。
7. 设计“从基础开始理解”入口。 复核现有九层学习路径对非技术读者的适用性，标明必要前置知识和可选深入内容。
8. 为内容设阅读层次。 例如“先理解核心意思”“继续理解机制”“进一步看数学与实现”，让读者能够自主深入。
9. 让地图解释关系。 除了展示连线，还要说明“为什么有关”“方向意味着什么”“这对理解当前概念有什么帮助”。
10. 明确学习结果。 每个阶段写出用户学完后能够解释或判断什么，而不仅是要读哪些页面。
这里需要重点检查一个假设：现有官方路径适合系统学习，但是否适合一个只想建立 AI 常识的非技术用户，目前还没有真实用户证据。
可先将“20 分钟建立初步全貌”“若干短学习单元掌握基础逻辑”作为待验证目标，不能提前宣传成确定效果。
第三阶段：建立内容质量标准，并逐批完善现有内容
11. 制定概念页教学标准。 每页检查核心解释、具体例子、机制、适用边界、相关概念、来源和下一步学习是否充分。
12. 建立三份独立评价。 事实是否准确；讲解是否有效；审核记录是否完整。三者分别记录证据和问题。
13. 检查概念之间的一致性。 同一术语不能在不同页面含义漂移；前置知识、关系方向、跨页解释不能互相矛盾。
14. 检查图表和例子。 图形、箭头、公式、单位、图注与正文应一致；类比需要说明失效边界。
15. 优先完善基础旅程所需页面。 根据实际学习路径选出第一批，而不是机械地按搜索热度选题。
16. 逐批覆盖其余公开内容。 130 个理解页都进入清单，但只针对发现的问题修订，不预设全部重写。
17. 检查软件、教程和资料库。 确认信息是否过期、链接是否有效、推荐理由是否成立，以及它们是否真正帮助初学者。
18. 建立纠错与更新规则。 读者可以指出“事实错误”“看不懂”“内容过时”；不同问题进入不同处理流程。
理解页的修改与发布继续遵守现有 Stage 2 控制器和人工确认机制。教学标准可以在项目层制定，具体内容修改必须走受控流程。
验收不能只靠“我读起来觉得不错”：至少需要新读者复述和应用测试。
第四阶段：让中英文成为两条完整、同步的学习旅程
19. 整理现有英文覆盖。 区分界面、图谱节点、理解页和资料等内容类型。已经完成的翻译继续复用。
20. 维护统一术语。 保持概念 ID、关系与学习进度跨语言共享，中英文名称、别名和解释一致。
21. 按完整学习单元成对发布。 一个入口、它依赖的概念页、练习、导航和提示都准备好，再宣称该单元支持双语。
22. 检查英文教学表达。 不只检查字面准确，还要检查例子、句式、术语密度是否适合英文初学者。
23. 建立源文变更追踪。 中文修改后识别受影响的英文，明确是否需要更新，避免过期译文长期不被发现。
24. 提供明确的语言切换。 切换后保留当前概念与学习位置；缺失译文时明确告知，不将中文正文伪装成英文页面。
“中英文同时发展”适合采用同一批学习内容双语完成，不必等全站所有长尾资料都翻译完成才能开始用户测试。
第五阶段：补齐独立网页和公开发布架构
25. 确定长期域名和中英文路径。 例如 /zh/concepts/.../ 与 /en/concepts/.../，稳定 ID 尽量沿用现有设计。
26. 为正式内容生成完整 HTML。 直接打开概念页即可读到正文；地图、内容页共用受控发布的数据，避免维护两套正文。
27. 连接内容页、地图与学习路径。 提供可抓取的普通链接，并让“在地图中查看”准确定位当前概念。
28. 兼容旧 Hash 地址。 保留旧书签的恢复逻辑。由于服务器收不到 # 后的内容，旧 Hash 页不能简单依赖逐页服务器 301，应设计客户端兼容导航。
29. 建立正式发布清单。 自动决定哪些内容可公开、哪些进入预览；生成产物保留应有审核标记，不意外发布内部材料。
30. 选择托管与部署流程。 接入 GitHub、预览环境、正式环境、HTTPS、自定义域名、缓存和回滚。
31. 处理边界页面。 真正不存在的内容返回正确的 404；旧普通路径迁移、资源路径和子目录部署均有明确规则。
对当前项目，我倾向于先采用“静态内容网站＋现有交互地图＋托管账号服务”。可以先验证 Cloudflare Pages 一类静态托管方案；它支持静态 HTML 和预览部署，但选型仍需实测目标地区的访问情况。Cloudflare 官方文档
独立网页的意义是稳定抓取和分享。Google 明确建议避免用 Hash 片段加载不同页面内容。Google JavaScript SEO 文档
第六阶段：完善初学者体验、移动端和无障碍
32. 调整首页。 清楚说明服务对象、能学到什么，并提供“了解全貌”“开始基础学习”“探索地图”等明确入口。
33. 统一阅读体验。 规范字体、行宽、标题层级、图注、目录、提示和中英文排版。
34. 设计手机地图体验。 检查点选、缩放、返回、面板切换和误触，避免桌面界面直接缩小。
35. 提供列表与文字关系视图。 不依赖拖动画布，也能浏览概念和关系。
36. 完善站内搜索。 支持中英文术语、缩写和别名，结果区分概念、工具与资料；无结果时有可用建议。
37. 完成无障碍检查。 检查键盘、焦点、对比度、缩放、屏幕阅读器、图片替代文字和登录流程。
38. 优化性能与失败体验。 核心正文优先显示，地图和重资源按需加载；网络失败时能重试和恢复。
以 WCAG 2.2 AA 为设计与验收目标，自动检查结合人工操作，不能把一次自动扫描通过当作完整符合声明。W3C WCAG 说明
性能目标可采用真实用户第 75 百分位的 LCP ≤ 2.5 秒、INP ≤ 200 毫秒、CLS ≤ 0.1；初期数据不足时先做实验室测试，后续补真实访问数据。Web Vitals
第七阶段：增加账号与可靠的跨设备进度
39. 明确进度模型。 区分“读过”“自认为理解”“完成练习”等状态，避免把一次点击当成已掌握。
40. 选择托管认证与数据库。 先验证登录方式、邮件送达、地区访问和成本。Supabase 可作为候选，不必自己从零实现认证。
41. 保留访客学习。 阅读与本地记录无需注册；需要跨设备同步时再提供登录。
42. 处理首次登录迁移。 将现有本地进度与账户进度安全合并，避免覆盖任何一方已有记录。
43. 设计同步与冲突规则。 覆盖两设备同时修改、取消完成、离线后重连、重复请求、退出和换账号。
44. 实现账户控制。 包括退出、恢复访问、导出数据、删除账号，以及同步状态与失败提示。
45. 验证数据隔离。 用不同测试账号证明用户无法读取或修改他人的进度；后台密钥不进入前端。
46. 验证恢复能力。 测试备份恢复、数据结构升级、节点调整和内容更新后进度是否仍能正确解释。
账户数据需要数据库层的权限控制，不能只在界面中隐藏他人记录。Supabase 权限文档
离线阅读可沿用现有能力；完整离线应用暂不作为新增工程。在线账号不可用时，公共知识仍应可读。
第八阶段：补齐 SEO 与 GEO 的全站基础
47. 生成页面元数据。 每页有准确标题、摘要、canonical、分享预览和正确语言信息。
48. 配置双语搜索关系。 中英文各自拥有规范地址，并通过互相对应的 hreflang 表达语言版本关系。Google 多语言说明
49. 生成 Sitemap 和抓取规则。 只纳入适合索引的页面；检查 robots.txt、页面索引指令、CDN 和访问控制是否一致。
50. 区分搜索与训练爬虫。 为搜索发现配置 OAI-SearchBot 等相关访问；是否允许训练抓取单独决定。OpenAI 爬虫说明
51. 添加匹配可见内容的结构化数据。 描述网站、文章、导航等真实信息，不添加虚构作者、评分或资质。
52. 验证搜索抓取。 接入 Google Search Console、Bing Webmaster Tools，检查具体 URL 的抓取与索引问题。
53. 在发布时通知变更。 更新 Sitemap；有价值时接入 IndexNow，仅提交真正变更的 URL。
54. 完善可引用表达。 章节能独立说明问题，关键断言有来源、时间和边界，图片有可读文字解释。
55. 建立品牌事实页。 统一中英文名称、项目目的、作者、维护方式、联系方式和纠错入口。
56. 建立 GEO 观察样本。 固定真实问题，区分品牌提及、来源引用、描述准确性和实际访问。
Google 表示其 AI 搜索功能不需要特殊 AI 标记；IndexNow 也不保证收录。验收应检查可发现性和真实表现，不承诺 AI 一定推荐。Google AI 搜索说明、IndexNow FAQ
基础 GEO 从首次公开发布就开始；复杂监测等到有数据后再扩展。
第九阶段：建立单人也能维护的安全与运维机制
57. 整理发布流水线。 运行与变更相关的数据、页面、语言、链接和浏览器检查；内容发布继续受现有控制器约束。
58. 固定依赖与构建。 保证换一台机器仍能构建，记录依赖更新策略和必要配置。
59. 检查公开产物。 防止将密钥、内部记录、测试数据或本机材料打包上线。
60. 保护管理入口。 维护域名、GitHub、托管与数据库账户的恢复方式和权限。
61. 建立监控。 覆盖网站可用性、错误页面、登录失败、同步失败和必要的服务额度。
62. 建立备份与回滚。 分别覆盖代码、内容、数据库和配置，并实际演练恢复。
63. 写明隐私与使用说明。 清楚解释保存哪些数据、用途、保留与删除方式；账号数据和统计数据分别处理。
64. 明确内容与代码授权。 梳理第三方来源、图表和依赖；决定原创内容与代码如何允许转载或贡献。
65. 设成本上限与处理方案。 分别记录域名、托管、数据库、邮件、统计、翻译与开发工具开支，并设置可用的额度告警。
预算目前没有具体数额，因此先不承诺月费。购买开发工具订阅后，托管、邮件和数据库仍应作为独立成本管理。
第十阶段：从早期就验证真实学习效果
这一阶段不能等所有功能完成才开始。第二、三阶段有原型和样板内容时，就应开展第一轮。
66. 招募第一批中英文用户。 建议每种语言先找 5—8 位目标用户做形成性测试；小样本用于发现问题，不用于证明普遍有效。
67. 观察完成任务。 让用户找到起点、读懂概念、查看关系和继续学习，观察时尽量不替他们解释界面。
68. 检查学习前后变化。 使用难度相近但不同的问题，观察是否能解释和迁移应用；条件允许时增加延迟回访。
69. 区分问题原因。 是概念讲错、解释跳步、前置知识缺失、译文不清，还是操作找不到入口。
70. 修订后再测试。 记录哪项改动解决了什么问题，避免只收集满意度。
71. 扩大后续样本。 在公开测试中覆盖不同基础、语言、设备和地区，逐步判断结果是否稳定。
可以先设一个内部目标：多数测试者无需指导即可完成核心任务，并在解释或应用题上出现明确进步。具体比例应在试测后确定，避免现在制定一个看似精确却没有依据的分数。
第十一阶段：公开测试、传播与数据反馈
72. 发布边界清楚的 Public Beta。 双语核心旅程可用，公开说明内容范围，并提供明显的反馈入口。
73. 建立最小统计。 观察访问来源、开始学习、继续学习、路径完成、返回使用和同步失败，不收集无关个人信息。
74. 制作双语演示资产。 包括网站介绍、实际学习演示、原创关系图和可分享的专题入口。
75. 逐个验证传播渠道。 中文可先试图文与视频各一个；英文先选一个适合初学者的社区或内容渠道，根据有效使用再增加。
76. 推动真实教学使用。 邀请教师、作者或学习组织试用，记录他们实际引用什么、使用时遇到什么困难。
77. 检查流量是否转为学习。 将曝光、引用、点击与学习行为分开，识别具体流失位置。
78. 按证据扩充内容。 优先解决真实搜索、用户反馈和学习路径暴露出的缺口。
不需要先达到某个访问量才算成熟；但要评价为“优秀”，必须有真实用户从中获益的证据。
第十二阶段：达到成熟版本并持续维护
79. 完成所有公开核心内容的三维复核。 准确性、教学效果和记录完整性分别有结论；其他公开内容也有明确维护状态。
80. 完成双语核心旅程验收。 从首次访问到理解、复习、同步，均能独立完成。
81. 完成技术与运维验收。 关键任务、抓取、权限、恢复、移动端和无障碍检查有真实结果。
82. 通过多轮用户验证。 重要问题得到修复，并验证没有在另一语言或设备上重复出现。
83. 建立固定维护节奏。 每周处理反馈与异常，每月检查失效链接和动态内容，每季度复核学习效果、恢复能力、成本与路线。
84. 再决定是否走向开源社区。 届时补贡献指南、内容提案流程、维护权限和社区规则；公开投稿不自动成为正式内容。
