# 半自动入库规范（M1）

> 把一份资料变成一份**可审核的 diff 提案**，审核通过后再合并进 `data/graph.js`。
> 展示与入库分离（SPEC §2.3）：网页永远只读数据，入库是离线步骤。
>
> ⚠️ 不要和 `PROMPT_TEMPLATE.md` 混淆——那份是「换个主题重做一遍这个项目」的引导模板，
> 且内容停留在 D6 改版前的树结构，已过时。

## 0. 一次入库的完整流程

```
资料（网址 / PDF / 视频链接 / 本地文档）
  ↓ ① 取全文
  ↓ ② 抽概念 → ③ 去重匹配 → ④ 判层级 → ⑤ 找连接
  ↓
tools/proposals/NNN-<slug>.md   ← 人读的提案，不是机器格式
  ↓ ⑥ 人工审核（改 / 删 / 确认）
  ↓ ⑦ 合并 → 校验 → 重算布局 → 提交
data/graph.js
```

## 1. 取全文

| 资料类型 | 做法 |
|---|---|
| 网页 | WebFetch；403 时改用 PowerShell `Invoke-WebRequest` 或找镜像/原始版本 |
| PDF | 下载后 `py -3.11` + `pypdf` 抽文本（**注意**：默认 python 环境没有 pip，必须用 `py -3.11`） |
| 视频 | 优先找字幕/文字稿；没有就请用户提供要点 |
| 本地文档 | 直接 Read |

抽出的原文放 `tools/_raw/`（已 gitignore，**不入库、不发布**）。

## 2. 抽概念

**只抽够格当节点的**，判据是 SPEC §3.1：有独立身份、值得单独一张卡片、能与其他概念连线。

沿用 `tools/concept-checklist.md` 的筛选规则：

- ❌ 产品名、厂商名（Pinecone、LangChain…）→ 进详情页的「代表实现」，或作 emerging 节点
- ❌ 参数细项 → 合并进已有的聚合节点（如「采样与解码参数」）
- ❌ 评价指标 → 进相关概念的详情页，不建节点
- ❌ 职业介绍、学习资源、通用软件工程常识
- ✅ 有自己的**成因**和**对策**的机制 → 这是最该建节点的一类

## 3. 去重匹配（这一步最容易垮）

对每个候选概念，与现有 53 个节点比对，**必须在提案里显式给出结论**：

| 判定 | 含义 | 提案里怎么写 |
|---|---|---|
| **新增** | 现有节点都不覆盖 | 列出最接近的 2 个及为什么不是同一个 |
| **合并** | 和某节点是同一个概念的不同叫法 | 写明合进哪个、加进 `aliases` |
| **补充** | 现有节点覆盖了，但资料提供了新的案例/来源/侧面 | 写明追加到哪个节点的哪个字段 |
| **丢弃** | 不够格当节点 | 写明理由 |

匹配方式：标题 + `aliases` 精确/模糊匹配，再加语义判断。**宁可判成「疑似重复」交给人审，也不要自作主张新建。**

## 4. 判层级（D2）

- 默认 **emerging**（活跃层 L1），符合 SPEC「新捕获内容默认进活跃层」
- **但提案里要给出建议层级和理由**（用户 2026-07-19 决定），常见判断：
  - 教科书级、几年不变、已被广泛接受 → 建议 `base`
  - 已站稳但仍在演进的技术/概念 → `emerging`
  - 具体新闻/项目/版本发布 → 不建节点，作 `activity` 条目挂到相关概念上
- 升降级始终是**人工确认**的动作，系统只建议

## 5. 找连接

**跨边是这个项目的核心价值，抽取时要主动找，不能等它自己冒出来。**

对每个新概念问一遍：

- 它**组成**了什么 / 是什么的**一种**？（`part-of` / `is-a`）
- 它**使**什么成为可能？（`enables`）
- 它**约束**了什么？（`constrains`）
- 它**缓解**了什么问题？（`mitigates`）
- 它**威胁**着什么？（`threatens`）
- 它常和什么**被对比**？（`contrast`）

优先找**跨大区**的边——同一大区内的联系读者容易自己想到，跨区的才是增量。

## 6. 允许的改动范围（用户 2026-07-19 决定）

| 允许 | 不允许 |
|---|---|
| 新增节点、新增边 | **改写现有节点的 `body`** |
| 给现有节点**追加** `cases` / `sources` / `activity` / `aliases` | 删除现有内容 |
| 修正明确的事实错误（须在提案里单独标出并说明依据） | 静默调整措辞 |

理由：已审校过的内容不该被默默改掉，但新资料应该能给老节点带来增量。

## 7. 写作规约

新节点的 `body` 必须遵守 plan.md §4.5 的四段骨架：
**是什么 → 为什么会这样（机制）→ 约束/影响了什么 → 怎么应对**。

正文提到其他概念用 `[[node-id]]` 内联链接。

⚠️ **中文正文里不要用英文双引号**，用「」——会破坏 JS 字符串语法（已踩两次）。

## 8. 版权

外部资料**只作选题依据和事实核对，正文一律自己写**。
来源记进节点的 `sources` 字段，许可证信息记进 `CREDITS.md`。
遇到明确禁止转载的来源（如 roadmap.sh），原文一个字都不能进仓库。

## 9. 合并后的固定动作

```powershell
node tools\validate.js                    # 必跑：语法/悬空边/坏[[引用]]/缺字段
# 起 http server → 浏览器跑 tools\find-seed.js 选种子
# 勾上全部层 → 按种子重跑布局 → tools\dump-positions.js 导出坐标
node tools\validate.js                    # 再跑一次确认坐标齐了
# 无头 Edge 截图目视确认 → git commit
```
