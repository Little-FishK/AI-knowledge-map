## 1. 目标回顾（一句话）

一个**纯静态网页**，把 AI 知识组织成 **主干树 + 跨边** 的地图，纵向分 **基础层 / 活跃层L1 / 活跃层L2** 三层叠加；
每个概念点开有**卡片→详情页**（定义、案例、相关知识、来源）；
新资料（网址/视频/文档）通过 **Claude Code 会话内的半自动入库流程** 变成可审核的 diff，合并进 `graph.json`。

## 3. 文件结构（目标形态）

```
ai_knowledge_map/
├─ index.html            # 单页应用：图渲染 + 卡片 + 详情面板
├─ assets/
│  ├─ app.js             # 加载 graph.json、Cytoscape 初始化、交互逻辑
│  ├─ style.css          # 视觉：分区配色、边类型配色、卡片/详情面板
│  └─ cytoscape.min.js   # 本地内嵌（保证双击即开、离线可用）
├─ data/
│  └─ graph.json         # 唯一数据源 { nodes: [], edges: [] }
├─ docs/
│  ├─ SPEC.md            # 设计规格
│  ├─ KNOWLEDGE_STRUCTURE.md
│  ├─ PROMPT_TEMPLATE.md # 入库抽取用的提示词模板
│  └─ plan.md            # 本文件
└─ tools/
   └─ (M1) 入库中间产物：proposal-*.json（审核用，合并后可删）
```

**关键约束**：`index.html` 双击能直接打开。若浏览器 `file://` 协议禁止 `fetch('data/graph.json')`，则退化为把 JSON 内嵌进一个 `data/graph.js`（`window.GRAPH = {...}`）用 `<script>` 引入——**M0 直接采用内嵌方案**，避免起本地服务器。

## 4. 里程碑与任务

### M0 — 原型：验证结构好不好用 ★ 当前目标

目的：**先验证"树骨架+跨边+叠层"这套结构在真实内容上好不好用**，不追求内容全。

| # | 任务 | 产出 |
|---|---|---|
| M0-1 | `git init`，建目录骨架，写 `.gitignore` | 仓库可提交 |
| M0-2 | 取 aiknowledgemap 的 `data.json`，通读其层级树，产出**映射笔记**：它的哪些节点归入我们哪个大区、哪些丢弃 | `tools/import-notes.md` |
| M0-3 | 手工产出首版 `graph.json`：**基础层 25~35 个节点** + 6 个大区入口节点 + 主干树边 + **至少 15 条跨边**（跨边是核心卖点，必须够密才看得出价值） | `data/graph.json` |
| M0-4 | 加 **5~8 个活跃层节点**（emerging）+ **3~5 条 news 条目**（挂在概念详情页里），用于验证叠层视觉 | 同上 |
| M0-5 | `index.html` + Cytoscape：主干树布局、按大区着色、跨边按类型着色、默认只显示 base 层 | 可打开的网页 |
| M0-6 | 交互：点节点 → 概念卡片（定义/大区/来源/"查看详情"）→ 详情页（body、案例、相关知识、活跃层条目） | 同上 |
| M0-7 | 视图控制：搜索框、层过滤（base/L1/L2）、大区过滤、跨边总开关 + 按类型开关 | 同上 |
| M0-8 | 验证 + 打磨（见 §5） | 截图 + 结论 |

**M0 完成标准（验收）**
1. 双击 `index.html` 能打开，无需服务器、无需联网。
2. 默认视图是干净的基础层主干树，不是毛线球。
3. 打开跨边后，能一眼看出"RAG 用到了词嵌入"这类**跨分支联系**——这是 aiknowledgemap 做不到的事。
4. 点任一节点能走到详情页，且详情页内容不是空壳。
5. 切到 emerging/news 层，能看出"新东西挂在老骨架上"的叠层感。
6. 我（用户）看完能回答：**这个结构是我想要的吗？哪里别扭？**

### M1 — 半自动入库

| # | 任务 |
|---|---|
| M1-1 | 定稿 `PROMPT_TEMPLATE.md`：给定一份资料 + 现有节点清单，输出「新增节点 / 新增边 / 更新字段」的结构化提案 |
| M1-2 | 定义 diff 提案格式 `proposal.json`，含去重匹配结果（命中了哪个已有节点、置信度） |
| M1-3 | 跑通端到端：拿 2~3 篇真实资料（一个网址、一个视频、一个文档）走完 资料→提案→审核→合并 |
| M1-4 | 去重匹配调优：先做 title+aliases 精确/模糊匹配，观察漏配率再决定要不要上嵌入向量 |
| M1-5 | 基于真实数据细化 **D2 升降级规则** |

**M1 完成标准**：丢一个网址给我，10 分钟内你能拿到一份看得懂、改得动的提案，确认后地图立刻更新，且**没有长出重复节点**。

### M2 — 打磨与分享
时间衰减（news 变暗/下沉/归档）、视觉打磨、搜索体验、移动端可看、GitHub Pages 部署。

### M3（可选）— 全自动
定时抓取源 → 自动生成提案 → 你只做审核。M1 稳定后再评估。

## 5. 验证方式

M0 不写单元测试（纯静态展示层，测试性价比低）。验证靠**实际驱动网页**：
- 用浏览器打开 `index.html`，逐条走 M0 验收标准 1~6，截图记录。
- 检查控制台无报错。
- 故意点几个边缘情况：没有跨边的叶子节点、没有 body 的节点、news 条目为空的节点——不能崩、不能显示空白面板。

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| **毛线球**：跨边一开就糊 | 默认关闭跨边；按类型分色+独立开关；聚焦模式只显示选中节点的邻域 |
| **内容长歪**：导入的学术树和用途分区打架 | M0-2 先出映射笔记、你过目，再动手填 `graph.json`；宁可少而准 |
| **入库长出重复节点** | aliases 字段从一开始就认真填；提案必须显式列出"疑似重复"供审核 |
| **`file://` 限制** | M0 直接用 `graph.js` 内嵌方案绕开 |
| **范围膨胀** | v1 明确非目标：无账号、无后端、无定时抓取（SPEC §1） |
