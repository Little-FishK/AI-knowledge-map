## 1. 目标回顾（一句话）

一个**纯静态网页**，把 AI 知识组织成 **主干树 + 跨边** 的地图，纵向分 **基础层 / 活跃层L1 / 活跃层L2** 三层叠加；
每个概念点开有**卡片→详情页**（定义、案例、相关知识、来源）；
新资料（网址/视频/文档）通过 **Claude Code 会话内的半自动入库流程** 变成可审核的 diff，合并进 `graph.json`。

## 3. 文件结构（目标形态）

```
ai_knowledge_map/
├─ index.html            # 单页应用：图渲染 + 卡片 + 详情面板
├─ assets/
│  ├─ app.js             # 加载 graph.json、Cytoscape 初始化、交互逻辑
│  ├─ style.css          # 视觉：分区配色、边类型配色、卡片/详情面板
│  └─ cytoscape.min.js   # 本地内嵌（保证双击即开、离线可用）
├─ data/
│  └─ graph.json         # 唯一数据源 { nodes: [], edges: [] }
├─ docs/
│  ├─ SPEC.md            # 设计规格
│  ├─ KNOWLEDGE_STRUCTURE.md
│  ├─ PROMPT_TEMPLATE.md # 入库抽取用的提示词模板
│  └─ plan.md            # 本文件
└─ tools/
   └─ (M1) 入库中间产物：proposal-*.json（审核用，合并后可删）
```

**关键约束**：`index.html` 双击能直接打开。若浏览器 `file://` 协议禁止 `fetch('data/graph.json')`，则退化为把 JSON 内嵌进一个 `data/graph.js`（`window.GRAPH = {...}`）用 `<script>` 引入——**M0 直接采用内嵌方案**，避免起本地服务器。

## 4. 里程碑与任务

### M0 — 原型：验证结构好不好用 ★ 当前目标

目的：**先验证"树骨架+跨边+叠层"这套结构在真实内容上好不好用**，不追求内容全。

| # | 任务 | 产出 |
|---|---|---|
| M0-1 | `git init`，建目录骨架，写 `.gitignore` | 仓库可提交 |
| M0-2 | 取 aiknowledgemap 的 `data.json`，通读其层级树，产出**映射笔记**：它的哪些节点归入我们哪个大区、哪些丢弃 | `tools/import-notes.md` |
| M0-3 | 手工产出首版 `graph.json`：**基础层 ~43 个节点**（清单见 [concept-checklist.md](../tools/concept-checklist.md)）+ 6 个大区标记 + **至少 20 条边**，覆盖 11 种边类型中的大多数 | `data/graph.json` |
| M0-4 | 加 **5~8 个活跃层节点**（emerging）+ **3~5 条 news 条目**（挂在概念详情页里），用于验证叠层视觉 | 同上 |
| M0-5 | `index.html` + Cytoscape：**力导向布局（fcose）**、按大区着色、边按 11 种类型着色带箭头、默认只显示 base 层 | 可打开的网页 |
| M0-6 | 交互：点节点 → 概念卡片（定义/大区/来源/"查看详情"）→ 详情页（body、案例、相关知识、活跃层条目） | 同上 |
| M0-7 | 视图控制：搜索框、层过滤（base/L1/L2）、大区过滤、按边类型开关、**聚焦模式**（点节点只显示其 N 跳邻域——网状结构下的主力降噪手段） | 同上 |
| M0-8 | 验证 + 打磨（见 §5） | 截图 + 结论 |

**M0 完成标准（验收）**
1. 双击 `index.html` 能打开，无需服务器、无需联网。
2. 默认视图是基础层的完整网络，**看得清**（靠力导向布局 + 大区着色，不是毛线球）。
3. 能一眼看出"RAG 缓解幻觉""上下文窗口约束 Agent 记忆"这类**有类型的跨领域联系**——这是三个参考源全都做不到的事，也是本项目唯一的差异化价值。
3b. 聚焦模式可用：点一个节点，噪声显著下降。
4. 点任一节点能走到详情页，且详情页内容不是空壳。
5. 切到 emerging/news 层，能看出"新东西挂在老骨架上"的叠层感。
6. 我（用户）看完能回答：**这个结构是我想要的吗？哪里别扭？**

## 4.5 写作规约（2026-07-19 补，源于一次真实的返工）

### 正文骨架
每个节点的 `body` 按固定四段写，缺任何一段都算没写完：

1. **是什么** —— 定义，一句话能说清就别写三句
2. **为什么会这样** —— 机制。**这一段最容易被跳过，也最有价值**
3. **它约束/影响了什么** —— 和别的概念的因果关系
4. **怎么应对 / 怎么用** —— 可操作的建议，最好带优先级

> 反面教材：早期版本在「上下文窗口」里写了一句「这被称为中间迷失」就结束了——
> 说了现象，没说成因，没说对策。读者拿到一个名词，然后无路可走。

### 内联引用
正文里提到其他概念时用 `[[node-id]]`，渲染成可点的链接。
**不要重复解释别的节点已经讲过的东西**——链过去就行。这既是给读者的路径，
也是防止正文无限膨胀的闸门。

### 节点粒度：写作时才能发现的那一半
**清单定骨架，写作发现器官。**

节点清单（`tools/concept-checklist.md`）是在动笔之前定的，且颗粒度继承自外部目录
（roadmap.sh / aiknowledgemap）。这导致一个系统性偏差：**外部目录里没有的概念，
清单里也不会有**——即使它对理解这个领域很关键。

而「需要哪些节点」这件事，只有在写正文、要向读者解释某个机制时才会暴露。

> **规矩：写正文时，如果发现自己在解释一个「有自己的成因和对策」的东西，停下来——它该是个节点。**

判据仍是 SPEC §3.1：有独立身份、值得单独一张卡片、能与其他概念连线。

补网工具：`node tools/audit-mentions.js` 扫出正文里被强调但不是节点的词。
**但它只是线索生成器**——实测误报率高（会抓到小标题和举例），漏报也不少
（没加粗的概念抓不到）。别指望它替你做判断。

## 5. 验证方式

M0 不写单元测试（纯静态展示层，测试性价比低）。验证靠**实际驱动网页**：
- 用浏览器打开 `index.html`，逐条走 M0 验收标准 1~6，截图记录。
- 检查控制台无报错。
- 故意点几个边缘情况：没有跨边的叶子节点、没有 body 的节点、news 条目为空的节点——不能崩、不能显示空白面板。

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| **毛线球**：网状结构下边一多就糊 | **聚焦模式为主力**（点节点只显示邻域）+ 按边类型分色与开关 + 大区折叠 + 按层过滤。43 节点尚可直接看，200+ 必须依赖这些 |
| **内容长歪**：导入的学术树和用途分区打架 | M0-2 先出映射笔记、你过目，再动手填 `graph.json`；宁可少而准 |
| **入库长出重复节点** | aliases 字段从一开始就认真填；提案必须显式列出"疑似重复"供审核 |
| **`file://` 限制** | M0 直接用 `graph.js` 内嵌方案绕开 |
| **范围膨胀** | v1 明确非目标：无账号、无后端、无定时抓取（SPEC §1） |
