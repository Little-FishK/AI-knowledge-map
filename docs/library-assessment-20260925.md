# 专业资料库评估报告

日期：2026-09-25（第二版，修正初版中已过时的缺口判断）
范围：`data/library*.js`、`tools/validators/library*.js`、`tools/shared/library-data-files.js`、`docs/*POLICY*.md`、`origin/gh-pages`、线上站点
方法：按真实加载链逐文件计数 + 门禁与浏览器加载集合严格比对 + 跨分支逐字节比对 + 线上抓取 + 机制文档通读

---

## 一、结论摘要

专业资料库是这个项目**设计水平最高、工程落地最不一致**的模块。

它的审核机制设计已经接近专业数据库的治理范式：九类来源各自独立、五套成文机制、证据分级、负面能力声明、机制自我纠错留痕。资料卡正面告诉你"这份资料**不能**支持什么"，这在 AI 学习资源里极为罕见。

但同一批数据在三个地方的条数互不相等——**全新 clone 716 条 / 本地工作区 1829 条 / 线上 2457 条**，而全部文档统一写 1829。其中 **1113 条（61%）来自从未提交到 Git 的文件**。

需要明确的是：**初版报告里"14 个文件登记缺口导致门禁看不见 396 条"的判断已经过时。** 项目其后重构出了单一共享清单，门禁现在覆盖与浏览器完全一致的全部 50 个文件并且通过。真正剩下的缺口在**链接存活校验**——它仍硬编码自己的加载表，漏掉 32 个文件、1277 条（69.8%）。

---

## 二、设计层：机制质量（评级：优秀）

### 2.1 九类独立机制，互不污染

`docs/LIBRARY.md` 开篇声明：某一级来源的准入门槛不得改变其他一级来源的审核结论，跨来源只共用 ID / 网址 / 归属 / 站内关联等机械检查。实现上成立——`tools/validators/library.js` 对 `knowledge-base` 走 `reviewMode: "source-specific"` 分支，其余八类各按自己的机制校验。

至少五套成文且互不相同的机制：

| 一级来源 | 机制 | 核心判据 |
|---|---|---|
| 官方技术资料 | `official-technical-importance-v2` | 六道判断：官方性→知识对应→重要性硬门槛→边际增量→时效性→建卡粒度 |
| 学术投稿 | 重要性审核 + 评价机制白名单 | 需外部 AI 重大贡献证据 |
| 标准与监管 | 单层六门槛 | 通过即收录，**不设评分、排名或配额** |
| 黑客马拉松 | 五项硬门槛 | 身份/相关性/产物可访问/知识增量/奖项 |
| 专业知识库 | `source-specific` | 按各二级来源自身的数据库与方法收录 |

机制标识实测分布（official 类 1391 条）：`official-technical-importance-v2` 527 · `microsoft-official-value-score-v1` 312 · `nvidia-...` 264 · `meta-ai-...` 141 · `google-deepmind-...` 135 · `official-knowledge-matrix-v1` 12。**每个品牌一条独立机制标识，而非共用一个通用标识**——这是 v2 改造的落地证据。

### 2.2 证据分级与负面能力声明

- `discoveryOnly=true`：**239 条（13.1%）** 被显式限定为"只能用于发现"，不得作为证据。
- `reviewStatus` 直接写入结论边界，例如：`重要性审核待补：缺乏 AI 重大贡献独立证据；上线不代表通过`（51 条）、`六步审核通过；NeurIPS 2025 Best Paper；未独立复现`（3 条）、`重要性审核暂缓：NeurIPS 2024 Best Paper Runner-up；当前机制未启用 Runner-up；上线不代表通过`（1 条）。
- 字段覆盖率实测 **100%**：`summary` / `evidenceUse` / `limitations` / `accessedAt` 各 1829/1829。
- 资料卡正面展示"**使用边界**"。线上实测 `vall-e-paper` 一卡写道："作者的声音与提示条件有限；不能把实验结果推广到全部声音克隆系统。"——主动声明自己不能证明什么。

### 2.3 拒绝把名次当权威，且机制能推翻自己

`docs/LIBRARY.md` 明确 Kaggle 记录"不把赛事名次等同于同行评审或独立复现"。更值得记录的是**一次自我纠错**：`Guiding a Diffusion Model with a Bad Version of Itself` 原判 NeurIPS 2024 Best Paper，经官方奖项分组复核实为 Runner-up，随即降级为"重要性暂缓"并保留在案。机制能推翻自己的结论，是治理成熟的标志。

### 2.4 迁移纪律

`tier` 字段的 S/A/B 被显式标注为"v1 遗留，不是当前准入依据"，冻结保留并写明迁移条件（待「一手/首创/应答/归属」四道闸门覆盖全部二级来源后删除）。没有假装旧字段仍然有效，也没有直接删掉了事。

### 2.5 已建立的"防复发"机制（初版报告漏掉了这一层）

项目在初版报告指出的登记缺口之后，做了结构化修复：

- 新建 `tools/shared/library-data-files.js`，把资料库文件清单收敛为**单一事实源** `LIBRARY_DATA_FILES`；
- 在其中提供 `assertBrowserLibraryBundle()`：解析 `assets/app/library-view.js` 的 `bundle` 数组，与 `LIBRARY_DATA_FILES` 逐项比对，不一致就抛出**指明缺哪个文件**的错误；
- `tools/validators/library.js`、`tools/readiness/site-artifact.js`、`tools/readiness/inventory.js`、`tools/i18n/inventory.js` **四处均改为 import 该共享清单**；
- 严格比对结果：门禁加载 50 个文件，浏览器加载 51 个（多一个 `data/software.js`，属软件目录数据），**差异集合为空**。

也就是说，"6 处登记点各自维护清单"这个结构性隐患已经被消除。**但这项修复尚未提交**（`tools/shared/library-data-files.js` 在 git 中仍是未跟踪状态）。

## 三、落地层：数据一致性（评级：不合格）

### 3.1 同一个资料库，三个数字

| 口径 | 条数 | 说明 |
|---|---|---|
| 全新 `clone` HEAD 后可见 | **716** | 只有已提交的数据 |
| 本地工作区 | **1829** | README 与全部文档写的都是这个数 |
| 线上实际 | **2457** | GitHub Pages 实测 |

三个数字没有任何两个相等。README 第 90 行与 `docs/LIBRARY.md` 等处统一写 1829，而 1829 只对这一台机器的这个工作区成立。

### 3.2 61% 的内容从未进入版本控制

- 来自**已提交**文件的条目：**716**
- 来自**未提交**文件的条目：**1113（61%）**
- 未跟踪的 library 数据文件：**27 个**

未提交的包括 `library-official-{meta-ai,nvidia,anthropic,openai}-importance-*`（共 20 个文件）、`library-hackathon-kaggle.js`（157 条）、`library-knowledge-base-{core,expanded}.js`（117 条）、`library-springer-nature.js`。

### 3.3 线上比本地多 624 条，且方向双向不一致

发布分支 `origin/gh-pages` 独有一个 `data/library-hackathon-reviewed.js`（1.27 MB，624 条 = devpost 539 + lablab 85），**开发分支完全没有这个文件**。反向地，学术投稿线上 87 条 < 本地 101 条（两分支 `library-arxiv.js` 内容不同）。

线上分类计数（实测）：官方技术资料 1409 · 黑客马拉松 782 · 知识库与评测 117 · 学术投稿 87 · 标准与监管 58 · **其余四类各 1** —— 合计正好 2457。

### 3.4 九类来源的覆盖度极不均衡

官方技术资料与黑客马拉松两类占线上总量的 **89%**，而「专家与行业分析」「公开视频与讲座」「权威创作者」「开源项目与代码仓库」**四类各只有 1 条**。

门禁把这一点列为待补事项（warning，不阻断）：industry-analysis 的 9 个二级来源中只有 1 个登记了资料、0 个达到 10 篇；public-talks 7 个中 1 个；creator 8 个中 1 个；open-source 8 个中 1 个；hackathon 6 个中 2 个。对照 knowledge-base（16 个中 15 个有资料、4 个达 10 篇），差距明显。

所以"九类一级来源"目前是**结构完整、内容严重偏科**。文档对此是诚实的（"收录数量没有上限，已入库数量不表示系统检索完成"），但页面首屏并列展示九类，容易让读者误以为九类都已完成。

### 3.5 门禁已覆盖全量（初版判断已过时，此处更正）

初版报告依据当时的记忆判断"补登记那 14 个文件会让门禁报出 618 个问题"。**该判断在当前代码上已不成立**，实测：

```
$ node tools/validators/library.js
专业资料库 1829 条 · 一级来源 9 类 · 二级来源 85 个
来源治理元数据 85 条（S=31 A=25 B=29）
官方技术资料分布：openai=258 anthropic=269 google-deepmind=135
                  microsoft=312 meta-ai=141 nvidia=264 …
✓ 专业资料库校验通过          exit=0
```

曾经的三类问题都已消解：
- **机制标识**：meta-ai / nvidia 现在各用自己的 `-official-value-score-v1`，且校验器已接受，不再落到默认分支被判无效；
- **域名白名单**：`dev.meta.ai`（141 条全部使用）已可放行；
- **幽灵节点**：门禁不再报"关联了不存在的节点"。

结论：**结构性盲区已修复，且门禁口径（1829）现在等于浏览器口径（1829）。**

### 3.6 仍然存在的真实缺口：链接存活校验漏检 69.8%

`tools/validators/library-links.js` 是唯一没有改用共享清单的登记点——它自己 `require` 了 20 个 data 文件，**遗漏全部 32 个品牌 importance 文件**。逐条计数结果：

| | 条目 | 占比 |
|---|---|---|
| 链接存活校验**覆盖** | 552 | 30.2% |
| 链接存活校验**未覆盖** | **1277** | **69.8%** |

未覆盖的正是体量最大的官方技术资料：anthropic-01（119 条）、anthropic-04（106）、google-deepmind-02（81）、openai-04（69）、openai-03（63）、microsoft-03（50）、nvidia-06（49）……

后果是具体的：**这个模块 70% 的原始链接从未做过存活检查**。而 `docs/LIBRARY.md` 恰好用一整节讲链接会停运、跳转、内容漂移，并明确"`tools/validators/library.js` 只能校验网址格式，无法发现停运"。设计意图很清楚，只是覆盖没跟上。

### 3.7 参考记录：幽灵节点 id 的残留风险

初版记录曾出现 6 个图中不存在的节点 id（`computer-vision` 29 次 / `diffusion-model` 11 / `api` 9 / `image-segmentation` 7 / `security` 4 / `benchmark` 1）。图有 130 个节点，最近似的是 `computer-use`、`diffusion`、`image-generation`。当前门禁已不报此项，说明已处理；但这类 id 只能靠人工对齐，**没有"从图谱 id 生成候选"的自动约束**，属于长期复发风险点。

## 五、如果只做三件事

1. **提交那 27 个未跟踪的 library 文件**（含 `tools/shared/library-data-files.js` 这项修复本身）。否则仓库不是可复现的产物，而"716 条"就是对克隆者的真实体验。同时决定 `library-hackathon-reviewed.js` 归哪条分支——线上独有数据意味着发布分支已领先开发分支。
2. **让 `library-links.js` 改用共享清单**。它已经是唯一漏网的登记点，改造成本极低（一处 import），收益是 1277 条链接进入存活监测。
3. **统一口径**：README 与文档里的 1829 改为从数据生成，或至少注明"以线上为准"。三个数字里有两个是错的，会持续误导后续所有维护。

## 六、总体判断

在这个项目里，资料库最能体现作者的真实水平——因为它展示的是"知道一个信息源该被怎样对待"的判断力，而不是写代码的速度。五套互不相同的审核机制、`discoveryOnly` 分级、拒绝把黑客马拉松名次当同行评审、主动写"使用边界"、机制推翻自己结论时留痕、以及**在缺口被指出后立刻建立共享清单与一致性断言**——这些都不是 AI 会主动提出的设计，需要人来定标准。

同样真实的是执行层的欠账：61% 从未提交、链接校验漏 70%、三个口径互不相等。这正是重型 AI 编排的典型故障模式——**生成能力跑在治理前面**，而且越是被反复修改的模块（资料库两个月内经历 v1→v2 机制迁移、多轮重审、分支分叉）越容易积累这类不一致。

放到 AI 学习网站的坐标系里：一个资料卡正面写着"使用边界"、审核状态写着"上线不代表通过"的资料库，其**可信度表达方式已经超过绝大多数同类站点**。它当前的问题不是"说大话"，而是"账没对齐"——数字对不上、数据没提交、链接没查全。这三件事都属于工程卫生，不需要重新设计，只需要收尾。
