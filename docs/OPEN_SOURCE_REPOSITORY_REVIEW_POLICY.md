# 开源项目与代码仓库审核机制

版本：1.0（试行）｜日期：2026-09-24｜原则：双轨审核、能力覆盖、证据优先、持续复核

本机制适用于专业资料库一级来源“开源项目与代码仓库”。它同时服务两个不同目标：

1. **零基础 AI 开发工具集：**自动发现并持续补齐初学者完成 AI 开发所需的全部核心能力；
2. **顶级开源项目集：**收录在技术能力、实际效用、工程成熟度或生态影响上达到高门槛的开源 AI 项目。

两个目标使用同一组基础门槛，但采用不同的通过标准和展示标签。一个项目可以同时进入两条轨道，也可以只进入其中一条。

## 1. “集齐”与“最强”的准确含义

“集齐”指**能力覆盖完整**，不是收尽互联网上每一个 AI 工具。只要零基础用户从准备环境到完成、评测和分享一个可运行 AI 项目的关键任务都有至少一个合格工具承接，就达到覆盖目标。同质化替代品进入候选池，不因存在而自动进入正式工具集。

“最强最有用”指项目通过本机制定义的高门槛，允许多个不同路线同时通过，不做固定 Top 10、同类限额或强制排名。项目可以因技术领先、定义品类、不可替代的工程价值、广泛生产采用或卓越的教育与开发价值而通过，但热度本身不能替代证据。

本机制中的“开源”至少要求存在可核验的 OSI 批准许可证或同等明确的开源软件许可证。只有“源码可见”、禁止商用、限制用途、权重开放但代码闭源，均不得标为开源；可作为其他来源类型候选，但不进入本一级来源的正式开源项目集。

## 2. 审核对象与唯一归类

审核单位是“**项目身份 + canonical repository + 许可证 + 可复现版本或提交**”，不是单个网页，也不是 GitHub、GitLab 或 Hugging Face 整个平台。

只有独立社区项目或无法归入更高优先级来源的项目进入本类。继续遵守《专业资料库来源政策》的唯一归类优先级：

- 论文的官方实现归“学术投稿”，仓库作为论文资料入口；
- 厂商或机构自己的官方仓库归“官方技术资料”；
- 黑客马拉松项目首先归“黑客马拉松”；
- 独立社区项目的主仓库、发行版、RFC、代码、Issue 和已确认实现记录归本类。

镜像、Fork、包注册表页面、演示站和文档站通常只是同一项目的关联入口，不重复建卡。实质分叉只有在形成独立维护、独立发布和不同技术路线后才作为新项目审核。

## 3. 三阶段流程

所有候选依次经过“候选池 → 基础门槛 → 双轨审核”。

### 3.1 候选池：自动发现，不自动收录

候选发现采用多路取并集：

1. canonical 仓库与组织目录；
2. PyPI、npm、crates.io、conda、Docker Hub 等发行记录；
3. 基金会项目目录和成熟度清单；
4. 现有软件目录、教程、节点和资料条目的反向缺口；
5. 论文、技术文档、公开评测中的实现引用；
6. 维护良好的 Awesome 清单、社区讨论、趋势榜和推荐列表。

第 6 类只作发现线索。搜索排名、Stars、Forks、下载量、社交媒体热度、奖项或他人推荐均不能让项目自动通过。

每次发现批次必须冻结检索日期、入口、查询条件和分页范围，保存原始候选数、去重数、无法确认数和未覆盖入口。自动化只能创建或更新候选记录，不能直接把项目发布为正式收录。

### 3.2 六项共同硬门槛

六项逐项记为 `pass`、`pending`、`fail`。任何明确 `fail` 都不能进入两条正式轨道；优势不能抵消硬门槛。

| 门槛 | 必须确认的内容 | `pending` 的典型情形 | `fail` 的典型情形 |
|---|---|---|---|
| 1. 项目身份 | canonical 仓库、维护主体、主页/文档/发行入口可相互印证 | 主仓库迁移或同名项目关系不清 | 只有镜像、冒名仓库或来源不可追溯 |
| 2. 开源许可 | 根目录或发布包有明确许可证，许可证与实际组件边界一致 | 多组件许可或模型权重条款待核 | 无许可证、仅 source-available 或禁止必要使用 |
| 3. AI 开发相关性 | 项目直接支持 AI 应用、模型、数据、训练、推理、评测、部署或治理工作 | 只是通用工具，AI 用途是否实质成立待核 | 仅在宣传中提 AI，没有可验证的 AI 开发用途 |
| 4. 可用产物 | 有可获取代码及可定位版本；关键用途可按文档安装或运行 | 构建依赖、模型或数据暂不可得 | 空壳仓库、仅概念演示、关键代码缺失或结果不可运行 |
| 5. 维护与风险透明 | 能识别维护状态、已知限制、依赖与安全报告入口；存档项目必须显著标识 | 长期无活动但稳定性和替代关系未核 | 已知恶意行为、供应链冒充或隐瞒严重风险 |
| 6. 身份与版本去重 | 已核对旧名称、Fork、包名、版本、迁移及既有条目关系 | 疑似重命名或实质分叉待确认 | 明知是同一项目的镜像或发行入口却重复建卡 |

“维护活跃”不是绝对硬门槛。功能完备、依赖稳定、无需频繁更新的成熟项目可以通过；但必须准确标注 `active`、`maintenance`、`stable-inactive`、`archived` 或 `unknown`，不得把停止维护的项目包装成活跃项目。

## 4. 轨道 A：零基础 AI 开发工具集

### 4.1 先审能力覆盖，再审具体工具

工具集以能力矩阵为主索引，首版至少覆盖：

1. 环境准备与包管理；
2. 编辑器、Notebook 与 AI 编程助手；
3. 模型/API 调用与统一客户端；
4. Prompt、结构化输出与工具调用；
5. 本地模型下载、运行与硬件适配；
6. 数据获取、清洗、标注与版本管理；
7. Embedding、向量检索与 RAG；
8. Agent、工作流与 MCP/工具集成；
9. 微调、训练与实验跟踪；
10. 评测、可观测性与调试；
11. 安全、隐私、护栏与红队测试；
12. 服务化、部署、监控与分享演示；
13. 图像、音频、视频等多模态开发；
14. 学习样例、模板与端到端 starter project。

能力矩阵可以拆分或新增，但不能因某个热门产品存在就宣称相邻能力已覆盖。每个能力还要标记操作系统、云端/本地、命令行/图形界面、编程语言、硬件和外部账号要求。

### 4.2 初学者适用六项测试

通过共同硬门槛后，候选工具按以下项目实测：

| 项目 | 核心问题 | 计分 |
|---|---|---|
| 首次成功 | 零基础用户能否仅按官方或项目文档完成最小可用结果 | 0–5 |
| 安装摩擦 | 安装步骤、依赖、硬件、账号、密钥和地域限制是否可接受且说清 | 0–5 |
| 教学质量 | 是否有循序渐进的 quickstart、错误排查和可运行示例 | 0–5 |
| 安全默认值 | 是否避免默认暴露端口、泄露密钥、执行不可信代码或产生不可逆副作用 | 0–5 |
| 迁移价值 | 学到的概念和工作流能否迁移到同类工具，而非只会点特定按钮 | 0–5 |
| 可达性 | 免费起步路径、主流平台支持、无障碍和中文/低英语门槛是否足够 | 0–5 |

最低要求：总分至少 21/30，且“首次成功”“安全默认值”均不得低于 3。评分必须绑定测试环境、版本、日期、步骤和结果，不接受只读 README 后主观打分。

### 4.3 工具集角色与选取规则

- `starter-core`：某项核心能力的默认入门工具；
- `starter-alternative`：因操作系统、硬件、语言、隐私、本地化或学习路线不同而保留的必要替代；
- `advanced-next`：对初学者不是最短路径，但适合作为进阶迁移目标；
- `watchlist`：有潜力但尚未满足实测或稳定性要求。

每个能力至少一个 `starter-core` 才算已覆盖。只有当替代工具解决了默认工具无法解决的明确用户约束时，才设 `starter-alternative`。其余同质项目留在候选池或进入轨道 B，避免“大全”退化为选择困难清单。

自动补齐的工作方式是：先计算能力矩阵中的空缺与脆弱覆盖，再优先审核能填补空缺、平台差异或单点失效的候选；不是按 Star 数从高到低不断加项目。

## 5. 轨道 B：顶级开源项目集

### 5.1 五个质量维度

通过共同硬门槛后，按五个维度评分，每项 0–5，并保存可核验依据：

| 维度 | 关注内容 | 可接受证据示例 |
|---|---|---|
| 技术实力 | 能力边界、正确性、性能、扩展性、设计质量 | 可复现实测、独立基准、架构与代码证据 |
| 实际效用 | 是否解决真实高频或高价值问题，是否能稳定完成任务 | 生产案例、可复现工作流、依赖和集成证据 |
| 独特性 | 是否定义品类、形成不可替代方法或显著推进现有路线 | 首次发布记录、独立技术比较、生态后续采用 |
| 工程成熟度 | 测试、发布、文档、兼容性、安全响应和维护治理 | CI、发行记录、安全政策、贡献与治理记录 |
| 生态影响 | 是否成为基础依赖、事实标准或广泛采用的关键组件 | 反向依赖、跨项目集成、基金会/社区治理、长期采用 |

默认通过线为 19/25，且“技术实力”和“实际效用”均不得低于 4。除此之外，至少满足以下一项：

- 独特性达到 5；
- 工程成熟度达到 4 且生态影响达到 4；
- 有高质量独立复现证明其在关键任务上形成显著优势。

阈值用于保持一致性，不生成公开名次。分数接近但证据不足的项目进入 `watchlist`，不得通过“很火”“业内都在用”补足缺失证据。

### 5.2 明确禁止的替代指标

- Stars、Forks、下载量和 Discord/微信群规模只能作采用度线索；
- Benchmark 第一名必须核对任务、数据、硬件、版本、基线和可复现性；
- 大公司使用、名人推荐、融资或奖项不能证明技术质量；
- 提交频率不能单独证明健康，低质量高频提交也不能加分；
- README 中的自我宣传不能作为独立验证。

## 6. 证据规则与可支持断言

仓库自身属于项目实现事实的一手来源，可支持：许可证、API、功能是否存在、版本、提交、维护者声明、官方兼容范围和已公开的设计决策。

以下断言必须有独立证据或本项目复测，不能只引用仓库自述：

- “最快”“最强”“最安全”“生产级”“行业标准”；
- 性能、准确率、成本、资源占用和可扩展性比较；
- 用户规模、市场份额和生产采用范围；
- 安全性、隐私性、可靠性和合规结论；
- 相对竞品的优越性。

每条关键证据记录 URL、页面或文件定位、版本/提交、查阅日期、证据归属方和它能支持的最窄断言。项目维护者的基准标为 `self-reported`，独立复现标为 `independent`，本项目实测标为 `first-party-test`。

## 7. 决定与展示状态

| 状态 | 含义 | 动作 |
|---|---|---|
| `admitted-starter` | 通过轨道 A | 按具体能力和角色进入零基础工具集 |
| `admitted-elite` | 通过轨道 B | 进入顶级开源项目集 |
| `admitted-both` | 同时通过 A 与 B | 两处展示，共用同一项目身份记录 |
| `watchlist` | 无硬门槛失败，但证据、实测或稳定性尚不足 | 保存缺口和下次复核触发条件 |
| `merge-update` | 与既有项目、版本、Fork 或入口重复 | 合并身份和版本关系，不重复计数 |
| `ineligible` | 共同硬门槛失败或明确不属于本类 | 记录原因，可按正确一级来源重新归类 |

“未进入零基础工具集”不等于项目不优秀；“进入顶级项目集”也不等于适合初学者。前端和数据字段必须保留这一区别。

## 8. 复核、降级与退出

### 8.1 定期与事件触发

- `starter-core` 每 90 天做一次可安装性和最小成功路径复测；
- `starter-alternative` 与 `advanced-next` 每 180 天复测；
- 顶级项目至少每 180 天核对维护、版本、许可证、安全和核心证据；
- 发现许可证变化、仓库归档、维护权转移、供应链事件、严重漏洞、安装失败、关键能力移除或更优替代时立即复核。

### 8.2 降级规则

- 某次网络或临时构建失败先标记 `degraded`，不能立即删除；
- 连续两次独立复测失败且无可行修复路径，移出 `starter-core`；
- 严重安全风险、许可证失效或仓库身份异常可立即暂停推荐；
- 顶级项目失去维护但仍有不可替代的历史或工程价值时，可转为 `historical-elite`，显著标注，不冒充当前首选；
- 所有替换保留历史记录、替代理由和接替项目，不物理抹除旧结论。

## 9. 自动化边界与人工责任

自动化可以：发现候选、解析仓库元数据、识别许可证、记录发行与提交活动、检查链接、运行隔离环境中的安装测试、计算覆盖缺口并生成待审记录。

自动化不得：直接发布正式收录、根据热度生成“最强”结论、在非隔离主机执行不可信安装脚本、自动接受许可证解释、自动忽略安全告警，或把 README 宣传改写成独立结论。

涉及下载和执行候选代码时，必须使用无生产凭据、最小权限、受限网络和资源配额的临时环境；记录镜像、依赖锁、命令、退出码和产物哈希。需要云账号、付费资源或真实密钥的步骤必须单独授权，不得作为无人值守审核的默认动作。

## 10. 最小审核记录

每个项目至少保存：

- canonical 仓库、项目主页、维护主体、旧名称和镜像/Fork 关系；
- 许可证名称、许可证文件定位、例外条款和组件边界；
- 审核版本、提交 SHA、发行版、包名、镜像与查阅日期；
- 项目类别、解决的问题、关联节点、关联软件和目标用户；
- 六项共同门槛及逐项证据；
- 轨道 A 的能力覆盖、测试环境、步骤、结果、评分与角色；
- 轨道 B 的五维评分、外部证据、限制与比较边界；
- 最终状态、决定理由、复核日期、复核触发器、替代与历史关系；
- 审核人与自动化工具版本；自动发现、自动检测和人工判断分别留痕。

## 11. 完成口径和质量指标

### 11.1 零基础工具集

只有同时满足以下条件，才可以称“当前能力矩阵已集齐”：

1. 所有必需能力都有至少一个通过实测的 `starter-core`；
2. 每个工具均有版本化的零基础最小成功路径；
3. 操作系统、硬件、云端/本地、账号和编程语言限制已展示；
4. 没有逾期复核、已知失效或未处置的严重安全问题；
5. 候选发现批次完整报告搜索范围和未覆盖入口。

建议持续报告：能力覆盖率、脆弱单点数、首次成功率、P50/P90 首次成功时间、安装失败率、90 天复测通过率和安全暂停数量。

### 11.2 顶级开源项目集

不能宣称“已经收齐全世界所有最强项目”。每轮只能声明“截至某日，在已声明发现范围内，所有候选均获得处置”。批次报告至少包含候选总数、去重数、两轨通过数、同时通过数、观察数、不合格数、重新归类数和证据不足数。

机制有效应满足：

- 新手工具不会因热度高却无法安全跑通而入选；
- 专业顶级项目不会因不适合初学者而被错误淘汰；
- 小而关键的基础项目不会被 Star 数淹没；
- 镜像、Fork、包和仓库不会重复计数；
- 所有“最强”判断都能回到独立证据或版本化复测；
- 项目失效后能被及时降级，并为用户指出替代路径。

## 12. 与现有目录的关系

本机制审核的是专业资料库中的开源项目资料对象，不直接替代 `docs/SOFTWARE.md` 的软件目录规则。轨道 A 的通过结果可以向软件目录提出新增或更新候选，但仍需按软件目录的独立卡、分组卡和教程规则落地。

资料库收录也不自动修改概念节点、理解页或教程正文。仓库能够证明实现存在，不天然证明理论正确、性能领先或适合所有用户；跨页面引用必须服从本机制记录的版本、许可证、测试环境和证据边界。

本版先建立审核规则和记录模板，不自动批准现有 `llama.cpp` 种子条目，也不声称已经完成候选发现或能力覆盖审核。
