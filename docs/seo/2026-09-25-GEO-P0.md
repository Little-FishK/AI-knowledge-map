## 2. 第 0 层：先让缺口可被验证

### 2.1 度量必须先统一

评估阶段用的是 `curl | sed | wc -c`，有两个错误：`wc -c` 数的是**字节**（中文 3 字节/字）却标成"字符"；逐行 `sed` 无法匹配跨行 `<script>` 块，把 JS 源码算进了"可读文本"。

现在只有一处度量实现：`tools/readiness/crawlable-text.js`，**门禁与复核脚本共用**，不会再分叉。更正后：

| 路径 | 爬虫可读字符 |
|---|---|
| `/library/` | **313**（本地预览产物）／327（线上） |
| `/software/` | **315**／329 |
| `/` | **350** |
| `/about/` | 900 |
| `/zh/` | 9,216 |
| `/search/` | 43,195（本地）／72,996（线上） |

### 2.2 阈值 700 是量出来的，不是拍的

- 应用外壳（`/`、`/library/`、`/software/`）实测 **313–350** 字符，全是导航；
- 最薄的**真实内容页** `/about/` 是 **866**；
- 概念页最低 3,807。

**700 ≈ 外壳的 2.2 倍，且低于任何有真实内容的页面**，因此它能区分"空"与"薄"，而不会逼任何页面去凑字数。阈值写在 `crawlable-text.js` 顶部，并注明"改动前先用 `check-crawlable.js` 重测"。

### 2.3 门禁契约：`crawlableVia` 不是豁免

`verifyCrawlable(root, manifest)` 对每个 `indexable !== false` 的页面要求：

> 服务端渲染可读文本 ≥ 阈值；**或**在 `seoPages` 中声明 `crawlableVia`，指向承载其记录的静态页。声明的每一页必须（a）存在于本次产物、（b）可索引、（c）自身达标。任一不满足即失败。

关键点：**声明不是放行条**。它强制"交互外壳 → 静态承载页"这对关系必须真实存在且被维护。`/library/` 声明了 18 个分类页；删掉其中任何一个，发布即失败。

**为什么不用方案里写的"往 `/library/` 外壳静态注入导航"**：外壳的 `#library-view` / `#software-view` 容器在 CSS 里是 `display:none`，且启动后会被 `innerHTML =` 整体覆盖。往里塞文本，等于把用户看不到的内容喂给爬虫——这是伪装，不是优化。改用具名附属页，既诚实又不产生重复内容。

- **最大单页 383 KB**（`official/microsoft`）。略超方案里"单页 ≤ 300 KB"的目标，但低于既有 `/search/` 线上 334 KB 的量级；**注意**：线上是 2457 条，最大页会更大。若需压低，把 `libraryPages({splitAt})` 调小即可再拆一层（该参数已开放）。

每条记录输出的字段：原始链接（`title` → 一手 URL）、`publisher`、`collection`、`contentKind`、`authorityTier`、`reviewStatus`、`summary`、`evidenceUse`（证据用途）、`limitations`（使用边界）、`accessedAt`（链接复核时间）、`discoveryOnly` 徽标。

两处刻意的诚实设计：

1. **二级来源登记表列出「已登记但暂无收录」的来源**，注明"暂无收录条目"，避免把"没收录"读成"不存在"。例如 `industry-analysis` 登记 9 个二级来源，实际只有 1 个有条目——这一栏直接把这个缺口摆在页面上。
2. **幽灵节点被过滤**。数据里有 6 个图谱中不存在的节点 id（`computer-vision`、`diffusion-model`、`api`、`image-segmentation`、`security`、`benchmark`），本轮一律丢到白名单外，绝不生成死链；`linkedNodes` 指向未发布的概念时，回退到地图锚点（与既有 `conceptHref` 同一策略）。

## 7. 遗留与需要维护者决定的事

### 7.1 门禁还没挂到 CI 那一步（重要）

CI 的执行点是 `.github/workflows/publish-website.yml`：

```
node tools/verify-website.js site-release --production
```

`verifyCrawlable` 目前挂在 **`promote-website.js`** 与新的 **`seo-crawlable-release.js`** 上，另有 `npm run check:crawlable` 手动入口。**没有**加到 `verify-website.js`，原因是：

- 仓库里的 `site-release/` 是 258 页的旧产物，**没有 `library/`、`software/` 两个视图外壳**，且与线上 `gh-pages` 不同步；
- 一旦把断言加进 CI 那一步，下一次部署会被自己的门禁挡住（首页 350 字符 + 缺少外壳），而我又不能在本地重建成生产产物。

**建议的下一步（择一）**：

1. 由维护者用一次完整生产构建生成含视图外壳的产物，跑
   `node tools/seo-crawlable-release.js <新产物> .site-next` 后 `npm run promote:website .site-next`，再把 `verifyCrawlable` 加进 `verify-website.js`；
2. 或在 CI 里加一步执行 `seo-crawlable-release` 再发布。

### 7.2 `seo-crawlable-release.js` 本次未能端到端跑通

它要求源产物已含 `library/` 与 `software/` 外壳（否则目录页的面包屑与外链会指向不存在的页面——这个前置检查是第一次试跑时被链接校验抓出来后补上的）。本地 `site-release/` 不满足，所以本机无法执行它。**它的逻辑与构建路径共用同一批模块，模块本身已在真实数据上验证；但脚本自身的清单记账（`manifest.files` / `seoPages` / `sitemap` 重写）尚未在真实产物上执行过。** 请勿把它当作已验证工具直接用于线上。
