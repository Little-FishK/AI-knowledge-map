## 4 上下文窗口（context-window）

### 4.1 什么是上下文窗口：16K 数值例子

本节回答：模型一次到底能「看进去」多少东西？。 上下文窗口是模型单次处理时能容纳的 token 总量上限 。要注意，这个窗口里装的 不只是你这句提问 ，而是这一次要一起喂给模型的 全部内容 ：。 窗口里装着； 例子。 系统提示 / 指令； 「你是一个客服助手…」。 对话历史； 之前来回说过的每一句。 检索来的材料； RAG 捞回来的文档片段。 它正在生成的回答； 输出也占窗口。 。 上下文窗口可以理解为一次调用中模型能直接看到的内容预算，用于解决一次调用里哪些信息能直接影响下一步生成的容量问题；它输入系统规则、历史、检索证据、工具结果和输出预留，先按分词器计数，再按产品策略接受、裁剪或压缩，输出一个不超过上限的布局。窗口大小只表示容量上限，不表示每个位置的信息都能被同样准确地使用。原始信息一旦滑出窗口，本次生成就不能再直接用到它。 这些加起来一旦超过上限，系统就必须拒绝、裁剪或压缩；若应用采用“丢掉最早内容”的策略，开头信息会先消失，但具体行为取决于产品实现。 图示：十六千 token 窗口的预算分配与超预算重排。 图 1 上下文窗口是共享预算，不是“输入最多 16K、输出永远另算”。实际计数规则因服务而异，设计时应同时核算输入、输出预留和工具往返。 数值例子 在 16K 预算里，规则 1K + 历史 7K + 证据 6K + 计划输出 4K = 18K，超出 2K。若粗暴截掉最早 2K，可能正好丢掉用户姓名或约束；更稳的方案是把历史压成 3K、只检索 4K 高价值证据，总占用 12K，留下 4K 给工具结果波动或更长回答。

### 4.2 关键澄清：它不是「记忆」

开头那个例子的真正原因，藏在一个常见误解里：模型是不是把对话「记住」了？。 基础推理调用通常是无状态的。 模型不会自动保留上一次请求；应用需要把相关历史、摘要或外部记忆重新放进本次输入。聊天产品可以在服务端保存会话，所以用户体验上像“记得”，但真正参与当前生成的仍是被装配进本次上下文的内容。某句话若既未保留、也未摘要或检索回来，模型本次就无从使用。 无状态可以理解为模型每次调用都不自动保留上一次的内容，用于解决它为何看似记得对话却会突然失忆的问题；它输入本次显式提交的消息与取回内容，先把相关历史、摘要或检索结果重新装进输入，再据此生成，输出只以这些内容为条件的回答。回答能提到旧信息，说明该信息本轮仍在窗口里，但若既未保留也未检索回来，模型本次就不是真的记得。 这解释了两件事 ① 为什么用 API 做多轮对话，每次都要 把历史一起发过去 ——因为模型不会自己存；② 为什么长对话越聊越贵——历史越长，每次重发的 token 越多，而 计费按 token 算 。

### 4.3 为什么不能无限大

既然窗口越大越方便，为什么厂商不干脆做成无限？。 对 标准全局自注意力 ，n 个位置会形成 n² 个注意力分数，朴素实现的相关算量和显存因此呈平方增长。实际推理还受 KV 缓存、带宽、位置外推和训练分布影响；滑窗、稀疏注意力与高效内核可以改变复杂度或常数。所以平方开销是重要约束，但不是唯一原因。 平方级开销可以理解为每个位置都要与所有位置两两算注意力带来的成本，用于解决窗口为什么不能无限放大的问题；它输入序列长度，先让每个位置与全部位置两两算分，再对这张分数表做归一化，输出的计算与显存随长度平方增长。长度扩大十倍位置对约扩大一百倍，说明代价是超线性的，但这解释的是标准全局注意力的主要瓶颈，不是所有实现的唯一约束。 一笔账 1 千 token 的输入，注意力约算 100 万对；10 万 token 就是约 100 亿对。每把窗口拉长一档，都要付这种超线性的代价——这正是长上下文又慢又贵的根源。

### 4.4 注意力计算、KV 容量和有效长度不是一回事

同样宣称支持 16K，为什么有的请求慢、有的并发一高就 OOM，还有的虽然跑完却答错？。 这一节比较的是同一个声称长度背后的四种不同限制，用于解决为什么同样支持长度却有的慢、有的并发就崩、有的答错的问题；诊断输入是请求长度、并发、硬件、证据位置和任务结果，先分别核算计算与读写、缓存容量、训练长度和装配，再定位真正的瓶颈，输出对四类问题的分别判断。接口返回成功只表示输入被接收，不表示模型能有效利用整段长度，因此不能用一类指标替代另一类。 限制； 它约束什么； 典型观察； 不能由什么替代。 注意力计算/IO； 处理长前缀的时间和中间读写； 输入越长，首 token 越慢； 显存放得下不代表算得快。 KV cache； 活跃 token 与并发请求容量； 单请求能跑，并发后 OOM/驱逐； FlashAttention 不会消除长期 KV。 位置与训练分布； 模型是否学会在该长度取用信息； 短文本好，长文本准确率下降； API 接受 16K 不证明有效利用 16K。 应用装配； 关键证据是否进入且摆在可用位置； 换顺序或去噪后答案改变； 换更长窗口不修复错误证据。 。 公式：KV 缓存字节数 B 下标 K V 约等于二乘层数 L、KV 头数 H 下标 K V、头维度 d 下标 h、已缓存 token 数 n 和每元素字节数 b。 B KV 是单个请求的 KV 缓存字节数；系数 2 表示每层同时保存 Key 和 Value。 L 是层数， H KV 是每层 KV 头数， d h 是每个头的维度， n 是已经缓存的 token 数， b 是每个数值元素占用的字节数。这个近似式用于估算容量，不包含模型权重、临时工作区和内存碎片。 例如 32 层、8 个 KV 头、头维度 128、FP16、16K token： 2×32×8×128×16000×2 ≈ 2.10×10⁹ 字节，约 1.95 GiB/请求，还没算模型权重、激活工作区和碎片。采用分组查询注意力、KV 量化或分页管理会改变数字，但“上下文长度同时消耗并发容量”这条关系仍在。 声明窗口 ≠ 有效窗口。 接口能接收某个长度，只证明输入没有被立即拒绝；要按长度、证据位置、任务类型和语言画准确率曲线，并同时记录首 token 延迟、KV 占用和失败率。

### 4.5 「塞得进」不等于「用得好」

就算模型支持很长的窗口，把所有资料一股脑塞进去，就万事大吉了吗？。 并不是。 长窗口有两个陷阱：其一， 中间迷失 ——放在上下文 中段 的信息，利用率明显低于放在开头和结尾，模型容易「看漏」中间（见「中间迷失」节点）；其二，塞进大量 无关内容 会稀释注意力、混入噪声，反而让回答变差。 有效上下文可以理解为模型在当前任务里真正能取用并用对的信息，用于解决把资料塞满窗口为什么不等于用好的问题；它输入候选材料及其顺序，先由注意力从大量内容中挑线索，再据此作答，输出带证据的答案。同一份材料放开头结尾还是中段会明显改变结果，说明位置和噪声都在起作用，但一次答对并不表示整段窗口都被可靠使用。 一句话 长上下文是一种 能力 ，不是「无脑往里塞」的许可。 放什么、放多少、放在哪 ，比「能放多少」更影响效果——关键材料尽量放在开头或结尾。

### 4.6 怎么应对窗口限制

当要处理的内容超过窗口，或长对话开始失忆，有哪些办法？。 窗口治理可以理解为在内容超预算时决定保留、检索、压缩和排序的一套方法，用于解决内容装不下或长对话失忆时该怎么办的问题；它输入超预算材料、任务目标和失败代价，先保护不可丢的规则与当前任务，再检索高价值证据、压缩可恢复历史并留出输出余量，输出一份可用的窗口布局。答案质量、证据覆盖和成本一起变好，才表示治理有效，但摘要可能漏细节、检索可能漏召回。 只放相关的（RAG） ：不把整个知识库塞进去，而是 检索 出与当前问题最相关的少量片段再喂给模型（见「RAG」「检索」）。 精心分配预算（上下文工程） ：决定每次调用窗口里到底放什么、按什么顺序——比雕琢单条提示更上层（见「上下文工程」）。 压缩与摘要 ：把过长的历史 压缩成摘要 再带上，腾出窗口（见「上下文压缩」）。 外挂记忆 ：让 Agent 把装不下的信息存到外部、需要时再取回（见「Agent 记忆」）。

### 4.7 把整条因果链连起来

从一次调用的共享预算，推到无状态、计算代价、有效利用与外部记忆。 上下文窗口是单次能看见的 token 上限，装着提示+历史+检索+输出，窗口外看不见。 （§1） 。 模型本身没记忆，「记得前面」是因为前面还在窗口里被重新喂入；被挤出就真忘了。 （§2） 。 窗口不能无限大：标准全局注意力的平方开销、KV 缓存、硬件、位置表示与训练长度共同形成约束。 （§3） 。 计算、KV 容量、有效利用和应用装配是四个不同瓶颈，声明长度不能互相替代它们。 （§4） 。 就算窗口够长，塞满也不等于用好：有中间迷失、有噪声稀释。 （§5） 。 应对：RAG 只放相关的、上下文工程分配预算、压缩摘要、外挂记忆。 （§6） 。 过关标准 如果你能讲清「模型为什么其实没有记忆、却像记得对话」，并说出「窗口为什么不能无限大、以及塞满为什么不等于用好」，你就抓住了它的内核。

### 4.8 常见误解

这些误解把产品保存的会话、模型可见上下文、声明容量和有效利用混为一谈。 误解； 更准确的理解。 模型能记住整段对话； 它没有记忆；靠把历史重新塞进窗口才「记得」，挤出即忘。 窗口只装我的提问； 还装系统提示、历史、检索材料、以及正在生成的输出。 窗口越大总是越好； 越大越慢越贵，还有中间迷失；关键是放对内容。 把资料全塞进去最保险； 噪声会稀释注意力、中段易被忽略，往往更差。 窗口不够只是厂商抠门； 标准注意力平方开销很重要，但缓存、硬件、位置表示与训练长度也会约束可用窗口。 。

### 4.9 检查你是否真的理解

请为一个 16K 请求分配规则、历史、证据、工具结果和输出预算，并说明裁剪顺序。 上下文窗口里到底装着哪些东西？。 模型「记得前面说过的话」的真实机制是什么？超出窗口会怎样？。 为什么窗口不能做成无限大？。 为什么 API 接受 16K 输入，不能证明模型能有效使用全部 16K？。 内容超出窗口或长对话失忆时，有哪些应对手段？。 参考答案 系统提示/指令、对话历史、检索来的材料、以及模型正在生成的输出。 模型没记忆，每次把窗口内全部内容重新读一遍；前面的话还在窗口里才「记得」，一旦被挤出窗口就真的没了。 标准全局注意力会形成 n² 个位置对，且 KV 缓存、带宽、位置外推和训练长度也有限；高效或稀疏变体能缓解但不能免费扩展。 声明容量只说明输入被接受；位置/训练分布、证据装配、中间迷失和噪声仍会降低实际任务准确率，需要按长度和位置实测。 用 RAG 只放相关片段、用上下文工程分配预算、压缩摘要历史、给 Agent 外挂记忆。

## 4.1 中间迷失：上下文放得下，为何模型仍可能找不到？（lost-in-middle）

### 4.1.1 1. “中间迷失”具体指什么？

直觉 当相关信息位于长上下文不同位置时，模型表现可能明显变化，位于中段时常更差。 中间迷失是一个需要实验确认的经验位置效应。实验输入是同一问题、证据和干扰文档的不同位置版本，输出是各位置桶的准确率或引用命中率；如果只移动证据就引起稳定变化，才支持位置敏感。U 形曲线表示首尾在该实验中优于中段，不表示每个模型、长度和任务都有同一形状。 经典实验把同一条关键证据放在上下文开头、中间或结尾，其他条件尽量不变。部分模型呈现类似 U 形的位置曲线：首尾利用较好，中部较弱。这是经验现象，不意味着每个模型、每项任务或每个长度都必然如此。 例子： 在 30 份候选文档中只有一份包含答案。若仅改变这份文档的位置，准确率随位置变化，就说明系统对位置敏感。

### 4.1.2 2. 上下文窗口与有效上下文有什么区别？

辨析 窗口长度说明最多能输入多少 token，不保证每个 token 都被稳定、等价地利用。 容量指标的输入是请求 token 数，输出是接口是否接受；有效利用评测的输入还包括证据位置、干扰和任务，输出是正确率与引用。前者由服务上限判定，后者必须通过任务实验测得。因而“支持 128K”只能解释为可接收容量，不能解释为任意位置都能可靠取证。 “支持 128K”是容量声明；“能从 128K 任意位置可靠取证”是任务表现。有效上下文还受任务难度、干扰项、检索需求、提示结构和模型版本影响。因此，不能用厂商窗口数字替代自己工作负载上的位置与长度评测。

### 4.1.3 3. 怎样把位置效应测成一条曲线？

数学 固定证据和问题，只改变证据的相对位置，再重复足够多样本。 曲线实验接收多个可配对的问题实例和位置、长度、干扰设置，输出每个条件的准确率、置信区间和样本量。每道题生成首、中、尾版本并随机化其他顺序，使题目自身成为对照；曲线差异若小于统计波动，不能宣称出现位置效应。 公式：准确率 A 是证据位置 p、上下文长度 L 和干扰强度 d 的函数。 A 是当前条件下测得的任务准确率； p 是证据在上下文中的归一化相对位置，0 靠近开头、1 靠近结尾； L 是上下文总 token 长度； d 是相似干扰项的数量或强度。这个写法表示准确率可能随三个变量共同变化，并不是预先假定它们之间存在某个固定代数公式。 将 p 归一化到 0 至 1，并分别报告不同长度 L 与干扰强度 d。需要随机化无关文档顺序、控制总 token 数、记录模型版本和解码参数。只比较一个开头样本和一个中间样本，无法排除样本难度和偶然波动。

### 4.1.4 4. 为什么会发生？

原理 研究观察到位置偏差，但其成因可能同时来自训练分布、模型机制与任务设计。 机制诊断的输入是已复现的位置曲线、注意力或检索轨迹和受控消融，输出是仍然成立的候选解释。通过分别改变训练长度、干扰相似度和提示结构观察曲线如何变化，可以缩小原因范围；注意力权重相关只能作为线索，不能被解释为唯一因果机制。 可能因素包括首因/近因偏置、长距离检索困难、相似干扰项竞争，以及提示没有明确指出证据的结构。不同架构和训练方法会改变表现。注意力权重可作为诊断线索，却不能单独证明“模型因为某个注意力头失效而遗忘中间”。 不要过度解释： 现象得到复现，不等于存在一个适用于所有模型的单一机制答案。

### 4.1.5 5. 如何降低关键证据被淹没？

工程 核心策略是减少无关上下文，并让任务与关键证据更容易彼此定位。 缓解流程输入原始候选、问题和 token 预算，输出去重、重排、带来源标记的紧凑上下文。它先筛掉无关内容，再把高价值证据放到任务附近并保留可追溯引用；效果应解释为证据更易定位，而不是模型窗口能力被永久改变。若召回阶段漏掉正确证据，后续重排和位置调整都无法补救。 先检索、重排和去重，只装配解决当前问题所需的片段。 用标题、编号、来源与分隔符建立清晰结构，避免“文本墙”。 将问题在证据之后重申，或把最高价值证据放在任务附近；具体位置以实验为准。 复杂任务拆成检索、核验、综合多个阶段，保留中间引用。 对超长资料先生成可追溯索引，而非不可核验的一段摘要。

### 4.1.6 6. 缓解方案怎样验证才可信？

工程 不能只测试“答案刚好在最前面”的理想布局，应覆盖位置、长度和干扰的组合。 验证输入是基线与候选方案在同一批位置、长度、干扰组合上的结果，输出是分桶质量、引用、延迟和成本差异。只允许缓解方案本身变化，并保存最终请求以检查证据集合；平均分上升但某个高风险位置桶下降时，方案仍不能通过。 建立位置基线 → 加入长度梯度 → 加入相似干扰 → 应用重排/结构方案 → 对比准确率与引用 → 分模型版本回归。 同时记录正确率、证据引用是否命中、延迟和 token 成本。若准确率上升但引用错误，模型可能凭先验猜对；若只在单一模板上改善，方案可能过拟合提示格式。

### 4.1.7 7. 哪些失败不能简单叫“中间迷失”？

边界 若证据未被检索、被截断、版本错误或问题本身含糊，根因不一定是位置。 归因排查的输入是失败请求、最终装配内容和检索解析日志，输出是数据管道故障或模型位置利用问题。只有确认正确证据确实存在且仅改变位置会改变结果，才把失败解释为中间迷失；无法构造这一对照时应保留“原因未定”。 排查顺序应先确认最终请求中确实包含正确证据，再检查 token 截断、权限过滤、文档解析、召回与排序，最后才用位置置换判断模型利用问题。这样能避免用一个流行术语掩盖普通的数据管道故障。

### 4.1.8 8. 在产品中应设什么回归测试？

实践 模型、提示和检索器更新都可能改变有效上下文，因此位置测试应进入持续评测。 持续回归接收固定的可置换任务集与每次系统版本，输出按位置、长度、任务和风险分桶的趋势及告警。升级后重复同一装配与评分流程并比较基线；总平均稳定但关键位置桶越过最低门槛时仍须阻断发布。测试集也要定期更新，避免只对固定模板过拟合。 保留一组可置换的多文档问答、键值检索与多跳任务；每次升级绘制分桶位置曲线，而非只报总平均分。对高风险答案要求引用证据，并在引用缺失或冲突时触发补检索或人工复核。

### 4.1.9 9. 案例推演：一条位置曲线怎样算出来？

案例推演 把同一份退款例外证据放在 30 个等长文档的首部、中部和尾部，怎样区分真实位置效应与样本偶然？。 图示：答案证据在开头中间结尾时形成U形准确率曲线。 图 1 示意性的 U 形位置曲线。红线是原始长上下文，绿虚线是检索重排后的结果；真实形状必须在具体模型、长度和任务上测量，不能把这张图当通用常数。 证据位置； 正确 / 60； 准确率； 95% 区间之外还要控制。 开头 0–10%； 51； 85%； 文档顺序、总 token、问题措辞。 中间 45–55%； 34； 57%； 同一证据、相似干扰项与解码参数。 结尾 90–100%； 48； 80%； 模型版本、随机种子与重复次数。 中间 + 重排； 46； 77%； 成本、引用正确率和是否只适配模板。 。 数值例子： 原始中段为 34/60≈56.7% ，重排后 46/60≈76.7% ，绝对提升 20 个百分点。但若重排同时删除了 8 篇干扰文档，就不能把全部提升归因于“位置更靠后”；应再做只改位置、不改文档集合的消融。 最好采用配对实验。 同一个问题实例分别生成开头、中间和结尾三个版本，使证据、干扰项、总长度和答案完全相同，只改变位置；这样每道题可作为自己的对照，减少题目难度差异。若任务需要两条分散证据，还应单独测试“两条都在中间”“一首一尾”“彼此相邻”等布局，因为多跳综合的失败不一定等同于单条事实检索失败。样本量较小时，百分比波动可能只是偶然，应同时给出置信区间，并在多个提示措辞上复验。 产品门槛也应按风险设定：普通推荐可以容忍少量位置敏感，高风险政策或合规回答则应在每个位置桶都达到最低正确率与引用命中率，不能让较高总平均掩盖中段失效。 不要只报总平均： 若开头样本多、中间样本少，总分会掩盖最危险位置。至少按相对位置、上下文长度和干扰强度分桶，并报告样本量或置信区间。

## 4.2 上下文学习（in-context-learning）

### 4.2.1 什么是上下文学习

本节回答：不做任何训练，怎么可能让模型「学会」一个它没专门练过的新任务？。 上下文学习的输入是任务说明、零个或多个输入—输出示例以及一个新查询，输出是模型按提示中临时规律生成的答案。模型在一次前向计算中利用示例，不更新参数；结果只说明当前请求中成功遵循了映射，删除示例或换一次请求后约定不会自动保留。 办法出奇简单： 把任务的几个示例直接写进提示里 ，模型读完就照着做。按给几个示例，分成三档：。 档位； 提示里给几个示例； 例子。 zero-shot（零示例）； 0 个，只给任务描述； 「判断下面评论的情感：又贵又难吃」。 one-shot（单示例）； 1 个； 给 1 组「评论 → 情感」，再问新的。 few-shot（少示例）； 几个； 就是上面那个最小例子。 。 图示：few-shot 提示的构成：几组示例加一个查询。 图 1 few-shot 提示的骨架：前面几行用「输入 → 输出」演示任务，最后一行只给输入、把输出留空。模型要做的，还是它唯一会做的事——预测下一个 token，而此刻「最可能的下一个 token」正好是「正面」。 。 1.1 运行示例：连标签含义也由上下文临时定义 把熟悉的“正面/负面”换成任意标签 zorp / blip ，就能更清楚地看到模型究竟从提示里恢复了什么：。 提示行； 模型可提取的信息。 “太棒了” → zorp； zorp 与正向情感关联。 “又贵又难吃” → blip； blip 与负向情感关联。 “服务很周到” → ?； 沿临时映射应输出 zorp。 。 这不是把 zorp 的新含义永久写入权重，而是在当前 token 序列里利用示例建立临时映射。删除前两行后，模型没有理由在下一次请求中继续按这个约定回答。 「学习」二字要小心 它并没有像人那样把知识「记住」。这里的「学」是 当场照着示例办 ，全程不改一个权重； 对话一结束就忘 ，下次还得把示例重新给一遍。后面第 2、7 节会把这层含义说透。

### 4.2.2 它和微调的根本区别

你可能会问：让模型「学会新任务」，不是已经有「微调」了吗？这两者差在哪？。 比较的输入是任务稳定性、样本量、延迟、调用规模和维护约束，输出是临时提示适配或参数训练方案。上下文学习每次把示例作为 token 参与前向计算；微调则用损失和梯度更新权重。前者适合快速试验，后者适合长期固化，但两者也可以组合使用。 差在一件根本的事： 改不改权重 。微调是在训练阶段用数据 永久改造 模型的参数；上下文学习是在使用阶段靠一段提示 临时适配 ，参数一动不动。 图示：微调改权重、上下文学习不改权重。 图 2 微调是一次「改造模型」的工程，结果写进权重、对之后所有请求都生效；上下文学习是一次「临时借用」，只在这一段提示里有效，请求一结束就没了。 。 ； 上下文学习； 微调。 改权重吗； 不改； 改。 要什么； 一段带示例的提示； 一批标注数据 + 一次训练。 多快见效； 即时； 要训练，慢。 能持续多久； 一次性，用完就忘； 永久，之后请求都带着。 容量； 受上下文窗口限制，示例塞不多； 可用海量样本。 成本结构； 每次请求都为示例付 token； 训练一次贵，之后每次请求省。 。 一句话记住分工 上下文学习是 运行时的临时适配 ，微调是 训练时的永久改造 。任务少、要立刻用、经常变，选前者；任务固定、样本多、要长期稳定省成本，选后者。

### 4.2.3 它凭什么成立

最关键的一节：一个训练目标只是「预测下一个词」的模型，凭什么看几个例子就会照做，还没人教过它「学习」？。 机制视角的输入是带重复格式和映射关系的 token 序列，输出是符合该局部模式的下一个 token 分布。预训练让模型练习补全大量列表、问答和对照表，因此示例可以帮助它定位当前任务模式。不过这是一种解释力较强的工作模型，不是已经证明的唯一内部算法。 先把疑点摆明 模型从没被显式训练过「读示例、归纳规律、应用到新输入」。上下文学习是一种 没被直接教、却自己冒出来的 能力。它从哪来？。 线索藏在预训练数据里。互联网文本中 充满了「重复的模式」 ：一份格式统一的列表、一串「问：… 答：…」、一段一问一答的对话、一张「英文—中文」对照表。要把这些文本的下一个词 猜准 ，模型别无选择，必须学会一件事：。 识别当前正在进行的模式，并接着这个模式往下写。 看到前面是「A → 甲、B → 乙」，要续写「C → ___」，最可能的下一个 token 当然是「按同样的映射，C 对应的那个」。few-shot 提示，正是 人为造出 这样一个模式：给几组「输入→输出」，模型识别出「哦，现在在做 X→Y 的映射」，于是对新输入照做。 所以上下文学习不是一种新能力，而是 「预测下一个词」被逼出来的副产品 ——和推理、翻译一样（见「大语言模型」深读页第 6 节）。 一个更精确的视角：示例在「定位任务」 示例的主要作用，可能不是「从零教你这个任务」，而是告诉模型： 在你预训练学过的成千上万种模式里，现在要调用的是哪一种 。模型早就见过无数情感分类式的文本，示例只是把它「拨」到那个频道上。这个视角能解释下一节那个反直觉的发现。 诚实说一句 「上下文学习内部到底在发生什么」仍是 活跃的研究课题 ，有多种解释（任务定位、隐式地在前向传播里做类似梯度下降的更新等），尚无定论。上面给的是能站得住、也够用的直觉，不是盖棺结论。

### 4.2.4 反直觉：示例标签「对不对」没那么重要

既然靠示例学，那示例的标签是不是必须全对？本节讲一个让很多人意外的实验发现。 该对照实验输入原始 few-shot 提示及分别打乱标签、格式、标签集合或输入分布的版本，输出各版本任务分数。每次只改变一项，比较性能下降幅度；下降小表示该项在当前任务影响较弱，不表示它在所有任务都不重要。专业任务与新知识映射仍可能高度依赖正确示例。 研究者做过一个对照：把 few-shot 示例的标签 故意打乱、随机配 （「太棒了 → 负面」这种错配），再看模型表现。结果—— 性能常常只掉一点点 。但如果动的是另外三样东西，性能会 大幅下滑 ：。 动什么； 对性能的影响； 说明什么。 把示例标签打乱（错配）； 影响较小； 示例不是靠「提供正确知识」起作用。 破坏输出格式（分隔符、排版乱）； 影响大； 示例在演示「答案长什么样」。 换掉标签集合（正/负 → 无关词）； 影响大； 示例在圈定「可能的答案范围」。 用无关的输入分布； 影响大； 示例在演示「输入大概是什么样」。 。 结论 few-shot 示例主要在演示 任务的「样子」 ——输入长什么样、答案什么格式、标签有哪几种——而 不是 在给模型灌输一条条正确知识。这正好印证第 3 节的「任务定位」：示例是把模型拨到对的频道，正确的判断力它早在预训练里就有了。 别误读成「示例可以乱写」 这说的是「标签个别错配」影响不大， 不是 鼓励你给错示例。格式、标签集合、输入分布都要 对且一致 ；在更难、更专业的任务上，示例的正确性依然重要。把它当成「给模板」，而不是「随便给」。

### 4.2.5 怎么把示例给好

既然效果全靠这几个示例，那到底怎么给，才最有效？。 示例选择接收候选示例、当前查询和 token 预算，输出数量适中、类别覆盖、顺序稳定且格式统一的提示。先保证正确与一致，再优先选与查询相似且覆盖边界的样本，并用多个顺序复测；结果应看目标切片上的稳定收益，而不是只看某一次排列。 数量 ：从 0 到 1、到几个，提升最明显；再往上 边际递减 ，而且每个示例都占上下文窗口的预算——不是越多越好。 选择 ：挑 和当前查询相似 、质量高的示例；若是分类，尽量 覆盖各个类别 ，别让模型误以为答案只有一种。 顺序 ：模型对示例顺序 敏感 ，还常有「离查询越近影响越大」的近因偏置。别把同类示例堆在一起，打散更稳。 格式 ：用 一致、清晰 的分隔符和排版（如统一的「输入：… 输出：…」）。第 4 节已说明：格式一致往往比标签个别正确更影响结果。 图示：示例数量与效果：0到几个提升大，之后趋平。 图 3 示例不是越多越好：0→1→2 通常提升最大，再加就趋平，而每个示例都在花上下文窗口的预算。挑得准，比堆得多更重要。 。 它属于更大的一层 「往窗口里放哪些示例、怎么排」本质是 上下文工程 的一部分；给单条提示配示例，则是 提示工程 里最常用的一招。上下文学习，就是这招之所以有效的原理。

### 4.2.6 一种特殊的用法：让示例演示「怎么想」

前面示例只给了「输入 → 答案」。如果示例里连「怎么一步步想出答案」也写出来，会怎样？。 few-shot 思维链的输入是包含中间推理格式的示例和新问题，输出是模型仿照该格式生成的步骤与答案。它通过模式续写诱导更长的中间计算，但生成步骤看似合理不等于事实正确；应以最终答案、可验证中间结果和任务边界共同验收。 那模型就会 照着「先推理、再给答案」这个模式 来答新问题——这就是 few-shot 思维链。你没有教它推理，只是用示例设定了「输出里应该包含推理步骤」这一模式，模型便照办。 它依然是上下文学习 思维链之所以能靠几个示例触发，正因为上下文学习让模型「照着示例的样子续写」。当示例的样子是「带推理过程的解答」，模型续写出来的，也就是带推理过程的解答。（详见「思维链 CoT」的说明。）。

### 4.2.7 边界与代价

它这么方便、又不用训练，那为什么还需要微调？它的天花板在哪？。 边界判断输入是窗口容量、提示敏感性、知识新颖度、请求规模和稳定性要求，输出是继续用 ICL、转向微调或两者组合的决策。若增加示例只提高 token 成本却不再改善分桶质量，或换顺序就越过业务阈值，就说明临时适配已接近实用边界。 受窗口限制 ：示例都挤在上下文窗口里，塞不了太多；示例一多，又慢又贵，还可能触发「中间迷失」（长上下文里中段信息被忽略）。 不稳定 ：对示例的 措辞、顺序、格式 都敏感，换个排列结果就变，难复现、难保证。 不持久、不更新知识 ：什么都没写进权重， 每次请求都得把示例重放一遍 ；它也不会因此真正「记住」新知识。 不等于真掌握 ：一旦查询 超出示例覆盖的范围 ，容易崩。任务复杂、专有、样本多时，微调通常更稳，长期看每次请求还更省 token。 更适合上下文学习； 更适合微调。 任务多变、要立刻试； 任务固定、长期跑。 只有几个示例； 有大量标注样本。 不想训练、不想维护模型； 要稳定、可复现、低单次成本。 原型验证、临时需求； 规模化、对格式和风格要求严。 。 务实建议 两者不是对立，而是 阶梯 ：先用上下文学习快速验证「这事模型能不能做」，跑通、量上来了、要长期稳定省成本，再考虑微调固化下来。

### 4.2.8 把整条因果链连起来

把全页串成一条链，逐环检查每个结论从何而来。 把几个示例写进提示，模型读完就照做——这就是上下文学习（zero / one / few-shot）。 （§1） 。 它和微调的根本区别是「改不改权重」：临时适配 vs 永久改造。 （§2） 。 它之所以成立，是因为「预测下一个词」逼模型学会了「识别模式并接着写」，示例把它拨到对的任务频道。 （§3） 。 所以示例主要在演示「任务的样子」（格式/标签集合/输入分布），而非灌输正确知识——标签个别错配影响不大。 （§4） 。 因此给示例讲究：数量适度、选相似且覆盖全、打散顺序、格式一致。 （§5） 。 把示例的「样子」换成带推理过程，就顺手得到 few-shot 思维链。 （§6） 。 但它受窗口所限、不稳定、不持久、超出示例范围易崩——这划出了它与微调的分界。 （§7） 。 过关标准 如果你能讲清「为什么一个只会猜下一个词的模型能靠几个例子学会新任务」，并说出「示例主要在演示任务的样子、而不是灌输知识」，你就抓住了上下文学习的内核。

### 4.2.9 常见误解

误解； 更准确的理解。 上下文学习会更新模型； 不改任何权重；用完就忘，下次得重给示例。 示例越多越好； 0→几个提升最大，之后边际递减，还占窗口预算。 示例标签必须全对才行； 标签个别错配影响不大；真正关键是格式、标签集合、输入分布要对且一致。 它和微调是同一件事； 一个是运行时临时适配，一个是训练时永久改造。 它是模型的一个「附加模块」； 它是「预测下一个词」被逼出来的副产品，不是单独训练的功能。 换个示例顺序结果应该一样； 模型对顺序敏感，排列不同结果可能明显不同。 。

### 4.2.10 检查你是否真的理解

zero-shot、one-shot、few-shot 分别指什么？。 上下文学习和微调最根本的区别是什么？由此各带来哪些取舍？。 用一句话解释：为什么「只会预测下一个词」的模型能靠几个示例学会新任务？。 把 few-shot 示例的标签随机打乱，性能常常掉得不多，这说明示例主要在起什么作用？。 既然标签个别错配影响不大，那示例里哪几样东西是不能乱的？。 为什么示例不是越多越好？至少说出两个原因。 few-shot 思维链为什么也算上下文学习的一种？。 什么情况下应该从上下文学习转向微调？。 参考答案 提示里分别给 0 个、1 个、几个「输入→输出」示例；示例越多，越是在「演示」任务该怎么做。 根本区别是改不改权重：上下文学习不改（临时、即时、用完就忘、受窗口限制），微调改（持久、要训练、可用海量样本、单次请求更省）。 因为「预测下一个词」逼它学会了「识别当前模式并接着写」，几个示例正好构造出一个「输入→输出」的模式，模型对新输入照做。 说明示例主要在演示「任务长什么样」（格式、标签范围、输入样子），而不是在提供正确知识；它是把模型拨到对的任务频道。 输出格式、标签集合（可能的答案范围）、输入分布——这三样要对且一致。 其一，0→几个之后提升边际递减；其二，示例占上下文窗口预算，多了又慢又贵、还可能中间迷失。 因为它靠「把示例的样子设成带推理过程的解答」来触发，模型照着这个样子续写，本质仍是照示例办事。 任务固定、样本多、要长期稳定和低单次成本，或对格式/风格要求严、查询常超出少量示例覆盖范围时。

## 4.3 采样与解码参数：从 logits 到最终序列（sampling-params）

### 4.3.1 生成是一条反复闭环，不是一次分类

第一个 token 的一次随机差异，为什么会改写后面整段回答？。 自回归解码循环的输入是当前提示和已生成前缀，输出是一个新 token 或停止信号。模型先给全词表 logits，解码器变形、过滤并选择一个 token，再把它追加为下一步输入；因此某一步的微小分叉会改变之后每一步的条件分布。单条输出只是这条路径的结果，不代表其他采样路径相同。 图示：自回归生成从 logits 变形、过滤、采样并反馈上下文的循环。 每一步的选择都会成为下一步条件，因此序列概率是沿路径的条件概率乘积；局部“第二名”可能打开完全不同的后续分支。

### 4.3.2 logits 只是相对分数，softmax 才给概率

给所有 logits 同时加 100，概率为什么不变？。 softmax 接收整个词表的相对 logits，输出和为 1 的下一 token 概率分布。指数化放大分数差，再用总和归一化；所有 logits 同加常数只会让分子分母同乘一个因子。概率表示当前前缀下的模型偏好，不是事实正确率，也不能直接当整段答案置信度。 公式：候选 i 的概率 p i 等于 e 的 z i 次方除以所有候选 j 的 e 的 z j 次方之和，也等于所有 logit 同减常数 c 后的对应比值。 e 是自然指数函数的底数， i 是当前候选编号， zᵢ 是候选 token i 的原始 logit， pᵢ 是 softmax 后抽到该候选的概率， j 遍历词表中的全部候选， c 是同时从所有 logits 减去的常数，通常取最大 logit 以避免指数溢出。分子分母同乘相同因子后比值不变，所以平移全部 logits 不改变概率。 softmax 只依赖 logit 差。数值实现通常减去最大 logit 再指数化，避免溢出。概率是“在当前提示与已生成前缀下，模型相对偏好哪个 token”的度量，不是事实正确率，也不等于完整答案的置信度。 贪心解码选择最大 logit；随机采样按归一化概率抽取。若分布为 [0.7,0.2,0.1]，采样很多次的频率趋近该比例，但单次完全可能选择 0.1 的候选。

### 4.3.3 手算温度：同一排名怎样变尖或变平

对 logits [2,1,0]，温度从 0.5 调到 2 会发生什么？。 温度缩放输入原始 logits 和正数 T，输出尖锐度改变的新概率分布。先用每个 logit 除以 T，再做 softmax；T 小时高分候选占比上升，T 大时尾部占比上升。它不增加模型知识，且 T=0 通常是服务自定义的贪心特判而非公式中的合法除数。 公式：温度 T 下候选 i 的概率 p i 等于 z i 除以 T 后的 softmax。 T 是大于 0 的温度， zᵢ 是候选 i 的 logit， pᵢ(T) 是缩放后候选 i 的抽样概率。小 T 放大 logit 差使分布变尖，大 T 缩小差异使分布变平；正温度不会改变候选排序。 温度 T； 缩放后 logits； softmax 概率（约）； 分布形状。 0.5； [4,2,0]； [0.867,0.117,0.016]； 很尖，第一名占主导。 1； [2,1,0]； [0.665,0.245,0.090]； 原始相对差异。 2； [1,0.5,0]； [0.506,0.307,0.186]； 更平，尾部更容易被选。 。 正温度除法不改变 logit 排名，所以纯 top-k 的成员不变；但概率累计速度改变，top-p 的集合可能改变。T→0 的数学表达不可直接除零，服务通常把 temperature=0 特判为贪心或采用自己的最小值。

### 4.3.4 top-k：固定候选数，不看概率间隔

保留前 3 名，在模型极确定与极犹豫时为什么不是同一强度？。 top-k 接收候选分数和整数 k，输出只含排名前 k 的支持集及重归一化概率。它把其余候选分数置为负无穷后重新归一化；实际抽样概率必须读截断后的数值。固定候选数不感知概率间隔，因此在极尖或极平分布上都可能过松或过严。 top-k 把排名 k 之后的 logits 设为负无穷，再对剩余候选归一化。它容易解释、计算稳定，但候选数量与分布形状脱钩：若第一名概率 0.99，仍保留 k−1 个极弱项；若前 100 个几乎均匀，k=3 又会任意删除大量同等合理选项。 原始概率； top-2 保留； 重归一化。 0.665 / 0.245 / 0.090； 0.665 / 0.245 / 0； 0.731 / 0.269 / 0。 。 截断后的数值才是实际抽样概率。记录 logprobs 时必须说明返回的是原始模型分布、温度后分布，还是截断重归一化后的分布。

### 4.3.5 top-p：固定累计质量，候选数随犹豫变化

p=0.8 时，为什么低温只留一个候选，高温可能留下三个？。 top-p 接收已排序概率和累计阈值 p，输出累计质量首次达到阈值的最小候选前缀。分布尖时集合自动缩小，分布平时集合扩大；保留下来的概率还要再次归一化。阈值边界是否包含、并列顺序和最低候选数属于具体实现，不能只凭参数名假定。 按概率从大到小累加，保留使累计概率首次达到阈值 p 的最小前缀。沿用本页 logits：。 T； 概率； top-p=0.8 的最小集合。 0.5； [0.867,0.117,0.016]； 只需第 1 个（0.867≥0.8）。 1； [0.665,0.245,0.090]； 前 2 个（累计 0.910）。 2； [0.506,0.307,0.186]； 前 2 个（累计 0.813）。 。 top-p 会在确定位置自动收缩，在不确定位置扩大，比固定 k 更适应分布形状；但“达到阈值的 token 是否包含”、并列排序和最低保留数仍取决于实现。

### 4.3.6 参数组合的先后会改变最终分布

temperature、penalty、top-k、top-p 同时打开时，谁先执行？。 解码管线的输入是原始 logits、生成历史和全部参数，输出是最终支持集与抽样分布。惩罚会改分数甚至排名，温度会改累计速度，截断再删除候选，所以交换步骤可能产生不同结果。参数组合只能按服务实现解释，实验时应从单一机制开始逐项加入。 图示：采样处理顺序对候选概率的影响。 温度改变累计概率，惩罚还可能改变排名；在截断前后应用会得到不同候选集。许多 API 不承诺统一顺序。 同时设 top-k 与 top-p 常取两者交集，可能比任一单独策略严格得多。默认值也可能隐式开启某种截断；做可归因实验时从单一机制开始，再逐项组合。

### 4.3.7 重复惩罚修改的是历史相关分数

为什么减少“的的的”也可能破坏代码变量和固定术语？。 重复惩罚接收已生成 token 历史和当前 logits，输出对出现过的 token 调整后的分数。presence 看是否出现，frequency 看次数，硬 n-gram 则直接禁用特定续写。较低重复率不等于语义更好；代码、引用和术语需要精确复用时，惩罚可能删除唯一正确候选。 常见概念； 典型作用； 主要风险。 presence penalty； 某 token 出现过即施加一次惩罚； 必要复用也被压制。 frequency penalty； 随出现次数增加惩罚； 长文术语一致性下降。 repetition penalty； 按实现对已见 token 的 logit 乘/除； 正负 logit 处理与 tokenizer 边界复杂。 no-repeat n-gram； 硬禁止重复 n-gram； 语法、引用与代码可能无路可走。 。 “词”的重复在 token 层可能跨多个片段；大小写、空格前缀和形态变化又可能是不同 token。惩罚不是语义去重器，应按任务检查必要重复、循环长度和事实一致性。

### 4.3.8 停止条件决定边界，不决定内容完整性

EOS、停止字符串和 max tokens 有什么本质区别？。 终止器接收新 token、已解码文本、语法状态和剩余预算，输出继续生成或停止及结束原因。EOS 在 token 层触发，停止串在文本匹配层触发，max tokens 是硬预算，语法接受态只证明结构完成。停止成功不能解释为内容完整或语义正确，流式跨块与引用中误命中仍需处理。 机制； 触发位置； 失败模式。 EOS token； 模型采样到专用终止 ID； 模板 ID 错或被过滤，模型不停。 停止字符串； 解码文本匹配字节/字符序列； 跨 token/流式块边界，截掉用户内容。 最大新 token； 达到硬预算； JSON、代码或句子中途截断。 语法接受态； 约束解码器确认结构完成； 格式完成但语义仍可能错误。 。 停止串可能由多个 token 组成，也可能出现在引用文本中。流式服务必须跨块保留匹配状态，并明确返回中是否包含停止串。结构化任务应把 finish reason、解析成功和内容校验分开记录。

### 4.3.9 贪心、采样、束搜索分别优化什么

每步选最高概率，为什么不保证整条序列概率最高？。 序列策略接收每一步的候选分布，输出一条或多条完成序列。贪心只保留局部第一名，束搜索保留若干累计高分前缀，随机采样按分布保留多样路径；最终应按任务质量解释，而非把高模型概率等同正确。束宽、长度偏置和开放生成退化限制了束搜索的适用范围。 贪心只做局部最优，早期最高 token 可能通向低概率后续；束搜索同时保留若干累计分数较高的前缀，近似寻找高序列概率，但长度偏置与模式坍缩需处理。随机采样不追求最高概率序列，而是从模型分布保留多样路径。 策略； 优点； 适合； 边界。 贪心； 快、低随机； 简单抽取、基线； 局部最优、可能循环。 束搜索； 探索多个高分前缀； 传统翻译等目标较窄任务； 贵，开放生成常显得单调。 截断采样； 多样且避开极低概率尾部； 对话、创作、多候选； 结果是分布，需重复评测。 。

### 4.3.10 按任务选择参数，而不是寻找万能配方

“代码用 0、创作用 1”为什么仍只是粗略经验？。 参数选择接收任务成功标准、风险、成本和模型服务实现，输出候选解码配置与外部验收方案。先建立低随机基线，再围绕目标指标扫描单个机制并复测组合；低温只让既有高分路径更稳定，无法修复知识错误、偏见或错误算法。 任务； 起始思路； 必须配套的验证。 分类/抽取； 低随机或约束候选； 标签 token、校准、解析与拒答。 结构化 JSON； 约束解码优先，低随机辅助； schema 合法与字段语义分别测。 代码补丁； 较窄候选，可生成多个； 编译、测试、安全扫描。 事实问答； 随机性不是核心控制； 检索引用、工具与事实核验。 创意发散； 适度提高熵，多候选； 新颖性、约束满足与人工选择。 自洽推理； 独立采样多条路径； 答案可比较、成本与系统性偏差。 。 降低温度只能让模型更稳定地选择它原本偏好的答案。 如果最高概率路径是幻觉、偏见或错误算法，temperature=0 会稳定复现错误，而不是修复知识。

### 4.3.11 固定 seed 为什么仍未必完全可复现

随机数相同，分布或执行顺序稍变会发生什么？。 复现输入是 seed、完整请求、模型与 tokenizer 版本、解码实现和执行环境，输出是可比较的 token 路径。seed 只固定随机数序列；任一概率边界或抽取顺序变化都可能让同一随机数选中不同 token。托管服务的固定 seed 通常只能提供近似复现，不构成逐字一致保证。 seed 只固定某个随机数生成器的序列。模型权重、tokenizer、提示字节、浮点内核、并行归约、批处理、解码实现或服务更新只要改变，累计概率边界就可能越过同一个随机数，后续路径全部分叉。某些硬件算子本身也不是位级确定。 复现实验应保存模型/服务版本、完整请求、默认参数、seed、输出 token ID 与 logprobs；托管 API 若只提供“尽力而为”的 seed，应把结果视为近似复现而非证明。

### 4.3.12 随机系统应该怎样评测

一次生成的好坏为什么不能代表某组采样参数的总体质量？。 随机解码评测接收固定输入集、系统版本和参数候选，输出多次独立采样的质量、多样性、方差、成本与失败分布。先固定其余条件逐项扫描，再重复采样并用解析器、测试或证据做外部验证；均值不能掩盖最坏失败，高字符串差异也不自动等于有价值的多样性。 固定输入集与版本： 保存精确提示、模板、模型和 tokenizer。 建立贪心基线： 先看模型最偏好路径的质量和失败。 一次只扫一个机制： 温度、top-p、top-k、惩罚分别形成曲线。 重复独立采样： 报告均值、方差、分位数、最坏失败与成功率。 同时测质量和多样性： 不同字符串不一定是有价值差异。 记录结束原因： EOS、stop、长度截断、错误要分开。 按任务外部验证： 代码跑测试、事实查证据、结构过解析器。 做交互消融： 组合参数后移除一项，确认收益不是偶然。

## 4.4 Logprobs 与置信度：模型偏好不等于答案可信（logprobs）

### 4.4.1 概率为什么取对数

连乘很多小概率为何要改成求和？。 序列 logprob 的输入是每个位置在既定前缀下的 token 概率，输出是整段候选可相加比较的对数分数。对数把条件概率连乘变成求和并缓解下溢；分数越高只表示模型越偏好该 token 序列，不能推出事实更正确。 公式：序列 x 一到 x n 的对数概率等于各位置 t 的条件对数概率之和。 P 表示模型给事件分配的概率， log 是自然对数， xₜ 是位置 t 的 token， x<t 是它之前的前缀， n 是序列 token 总数， t 是求和位置索引。每项都不大于 0，所以总 logprob 越接近 0，模型对整段序列的相对偏好越高。 对数把连乘变求和，避免浮点下溢；logprob 越接近 0，token 概率越高。

### 4.4.2 token 分数不等于答案分数

一句答案的置信度如何从多个 token 得到？。 答案聚合接收多个 token logprob，输出总和、平均值、最弱位置或任务自定义分数。总和随长度下降，平均值可能掩盖关键低概率 token；因此先定义任务单位和候选规范，再用验证集选择聚合方式。自由文本存在同义表达时，单一字符串分数边界尤其明显。 总和偏爱短序列，平均值又可能掩盖一个关键低概率 token。分类最好比较受控标签的完整 token 序列；自由文本还存在多个语义等价表达。

### 4.4.3 高概率也会自信地错

模型熟练复述错误信息时 logprob 会怎样？。 事实诊断输入是模型高分回答与独立证据，输出是语言偏好和事实正确性的分别判断。训练频率、提示暗示和流畅模式都能提高 logprob，即使命题错误；罕见但正确的名字又可能低分。因此必须用检索、工具或人工证据验证世界事实。 训练数据中的常见说法、提示暗示和语言流畅度都会提高概率，即使事实错误。反之，正确但罕见的名字可能低概率。因此 logprob 不是事实验证器。

### 4.4.4 校准把分数映射到频率

“置信 0.8”应满足什么经验含义？。 校准接收原始分数和独立数据上的真实标签，输出分数到经验正确率的映射。把相近分数分桶后，标为 0.8 的桶应长期约八成正确；这只在目标任务和分布上成立，模型、提示或输入分布变化后必须重新校准。 在一组预测中，声称 0.8 的样本应约有 80% 正确。温度缩放、等距回归等可在独立校准集拟合映射；模型、提示或分布变化后需重校准。

### 4.4.5 选择性预测

低置信时系统应该做什么？。 选择性预测输入校准分数、错误代价和覆盖要求，输出自动回答、补检索、升级、澄清或拒答动作。阈值把更多低分样本交给安全回退，通常降低覆盖；是否值得必须用风险—覆盖曲线和业务成本判断，而非只看准确率。 低于阈值可补检索、升级模型、请求澄清或转人工。阈值按错误代价与覆盖率选择：拒答越多通常风险更低，但产品可用性下降。

### 4.4.6 分词与接口陷阱

为什么比较“是”和“否”不能只读一个 token？。 接口核验输入实际 tokenizer、候选完整文本和 API 返回位置，输出每个规范标签的完整序列分数。空格、共享前缀与多 token 切分都会改变可比范围；top-k 未返回不等于概率为零，跨模型原始 logprob 也没有共同刻度。 标签可能包含空格或被拆成多 token，候选也可能共享前缀。必须用实际 tokenizer 汇总完整序列，并确认 API 返回的是所需位置和候选集合。 跨模型 logprob 不宜直接比较。 词表、分词和训练分布不同。

### 4.4.7 完整手算：概率、logprob 与序列分数怎样互换

两个token概率0.8和0.25组成的答案有多大联合概率？。 手算输入两个条件概率，输出联合概率、总 logprob、平均 logprob 和几何平均概率。先相乘得 0.20，再分别取对数相加得 −1.609；这些数值描述同一序列偏好，但不同聚合偏好不同长度，不能混作答案正确率。 自回归条件概率相乘：P=0.8×0.25= 0.20 。自然对数分别是 log0.8≈−0.223、log0.25≈−1.386，总 logprob≈ −1.609 ，再取exp恢复0.20。平均logprob为−0.805，对应几何平均概率exp(−0.805)≈0.447。 聚合； 数值； 偏好。 总logprob； −1.609； 短序列。 平均logprob； −0.805； 平均流畅，但可掩盖关键低点。 最小token logprob； −1.386； 暴露最弱位置，噪声大。 。 比较候选时必须先定义任务单位；标签分类与自由文本不能共用一个未经验证的聚合公式。

### 4.4.8 原创图：token信号必须经过任务校准才能触发行动

API返回的局部概率怎样变成可用的系统决策？。 决策链输入 token logprobs、任务单位、校准数据与业务代价，输出可审计的自动回答或回退动作。它依次做序列或语义聚合、独立校准和风险阈值决策；任何一层变化都要重放全链，不能把原始局部概率直接展示成可信度。 图示：token logprob经过序列聚合任务校准和风险阈值形成系统动作。 图 1 logprob只是原始信号；聚合、校准和成本阈值共同决定可执行动作。

### 4.4.9 候选标签必须比较完整序列概率

“Yes”是一个token，“No answer”是两个token，怎样公平比较？。 候选比较输入共同提示和多个完整标签，输出各标签整段条件 logprob。用 teacher forcing 逐 token 累加，并按预先规定的标签与长度规则比较；tokenizer 改变后需重新计算，跨模型应先分别校准再比较预期风险。 对每个候选，把共同提示固定，teacher-force整段标签并累加条件logprob。不能只读首token，因为候选可能共享前缀，也不能把API top-k之外的候选当概率0。若任务允许不同长度表达，应规定规范标签或用长度校正并在验证集确认。 公式：候选 c 的分数等于从 t 等于一到候选长度的每个 token 条件对数概率之和。 c 是一个完整候选标签， |c| 是它的 token 数， cₜ 是第 t 个候选 token， c<t 是候选已给出的前缀， prompt 是所有候选共用的提示， p 是当前条件下的 token 概率， score(c) 是整段候选的总 logprob。 不同tokenizer会改变分段、序列长度和归一化空间，因此跨模型原始分数没有共同刻度。做模型路由时应分别校准，再比较预期风险，而非直接比较平均logprob。

### 4.4.10 语义不确定性要先合并等价表达

“巴黎”“Paris”“法国首都巴黎”该算三种答案吗？。 语义聚合输入多次生成的字符串与任务等价判定器，输出意义簇及每簇累计概率。规则、执行结果或语义蕴含把等价表达合并后，簇间分布才更接近任务不确定性；聚类器会误合并或误拆分，必须用人工标注验证。 对自由生成，多次采样的token序列概率分散到大量同义表述。可先用规则、执行结果或语义蕴含把答案聚成意义簇，再累加簇概率；聚类器自身会误合并/误拆分，必须标注验证。 任务； 等价判定； 风险。 数学； 解析并代数化简； 格式/单位。 代码； 测试行为； 测试不完备。 事实问答； 实体规范化/蕴含； 别名与细节丢失。 开放建议； 语义聚类； 边界主观。 。

高概率描述模型熟悉度，不自动描述世界真相。 误区； 更准确的理解。 logprob高就是事实正确； 只表示当前模型偏好。 平均token概率就是答案正确率； 需任务级标签与校准。 比较首token足够； 候选可能多token或共享前缀。 8/10一致等于80%可靠； 采样相关且需经验校准。 阈值一次设定长期有效； 提示、模型和分布变化会失准。 。 层级； 依赖与延伸。 先修； 概率、对数、tokenization、softmax。 本页核心 ； 序列分数、语义聚合、校准、选择性预测。 相邻； 不确定性校准、自一致性、模型路由。 工程； API候选覆盖、阈值、漂移监控。 。 不要把内部概率展示成未经证实的“可信度”。 高影响场景要用独立数据校准并提供安全回退。

### 4.4.12 从分数到行动：覆盖率—风险曲线比单一阈值更重要

把阈值从−1.2提高到−0.5，系统究竟会变安全还是只是更少回答？。 覆盖率—风险分析输入验证集校准分数、真实标签与动作成本，输出每个阈值的覆盖率、已接收错误率和期望成本。按分数排序逐步扩大自动集合即可画曲线；阈值升高若只降低覆盖却不降低风险，说明分数排序或校准在该切片失效。 在验证集上按校准分数从高到低排序，逐步扩大自动回答集合。每个覆盖率点都计算已回答样本中的错误率：这形成覆盖率—风险曲线。阈值升高通常降低覆盖率，但风险未必单调下降；若高分区域恰好包含模板化幻觉，曲线会暴露校准失败。产品决策应比较期望成本，而不是只追求一个漂亮的准确率。 公式：阈值 tau 下的期望成本等于错误接收成本乘错误且接收概率，加拒答成本乘拒答概率，加升级验证成本乘升级验证概率。 E[cost(τ)] 是阈值 τ 下的平均业务成本； τ 是自动接收阈值； Cerr 、 Cabstain 、 Cverify 分别是错误接收、拒答和升级验证一次的代价； P 是验证集上对应动作事件的经验概率。各项必须使用同一评测周期与任务切片。 切片； 为何单独画曲线； 建议动作。 短答案 / 长答案； 长度改变聚合分数； 分别归一化与校准。 常见域 / 新域； 分布漂移导致过度自信； 新域先检索或转人工。 低损失 / 高损失错误； 相同错误率的业务代价不同； 采用不同阈值。 模型或提示版本； 分数刻度可能整体移动； 版本级回放与重校准。 。 上线后还要记录分数、动作、最终标签和切片；只监控平均logprob无法发现某一语言、任务或答案长度上的局部失准。若真实标签延迟到达，可先监控分数分布与拒答率漂移，但它们只能触发调查，不能代替正确率回流。

### 4.4.13 把因果链连起来

这个概念怎样从问题一路连接到可验证的实践？。 模型输出 token 概率。 对数使序列分数可加。 长度与分词影响聚合。 独立数据映射到正确频率。 阈值换取覆盖与风险。 分布变化后持续重校准。

### 4.4.14 误区与自测

你能否不用背术语，解释它的机制、边界与验证方法？。 logprob 为何通常是负数？。 总序列分数为何偏短？。 高 logprob 证明事实正确吗？。 校准 0.8 的含义？。 阈值提高的代价？。 假设“Logprobs 与置信度：模型偏好不等于答案可信”在离线示例上表现正常、上线后核心结果却下降，你会怎样按输入、内部变换、输出反馈和适用边界定位问题？。 如何为“Logprobs 与置信度：模型偏好不等于答案可信”设计一个最小对照实验，证明观察到的改善来自核心机制，而不是数据、提示、权限或评测口径同时变化？。 为什么不能只用一个平均分判断“Logprobs 与置信度：模型偏好不等于答案可信”已经可靠？应怎样按场景切片并设置失败边界？。 。 参考答案 概率在 0 到 1，对数不大于 0。 每个负 logprob 相加会随长度降低。 不能，只表示模型更偏好。 该分桶长期约 80% 正确。 拒答/升级增加，覆盖率下降。 先保存同一失败样本及环境，确认输入、权限和前置条件没有漂移；再记录关键中间状态，检查机制是否按本页描述完成变换；随后把原始输出与独立指标、人工终验对照；最后用边界样例和对照实验复测。只有定位到首次偏离预期的环节，才能判断应修改数据、机制、评测还是使用边界。 固定数据、模型版本、提示、权限、预算和评测，只改变一个与核心机制直接相关的因素，并在多个样本与随机种子上重复；同时保存中间状态和失败样本。若差异只在目标因素变化时稳定出现，才支持机制解释，否则应继续排查混杂变量。 平均分会隐藏少数类别、极端输入、成本、延迟和安全失败。至少按难度、输入类型、长度或规模、风险等级及已知边界切片，同时报告质量、资源和失败率；高风险硬约束不能被其他切片的高分抵消。

## 4.5 提示工程（prompt-engineering）

### 4.5.1 什么是提示工程

本节回答：不训练、不改模型，怎么让它稳定产出我想要的结果？。 提示工程可以理解为不改模型、只设计输入措辞与结构来提高命中率的手艺，用于解决怎样不训练就让模型稳定产出想要结果的问题；它输入任务目标、受众、上下文、边界和输出要求，先把这些讲清并写成可提交的提示，再交给模型执行，输出可被测试的提示与结果。输出更符合要求通常表示约束命中率提高，但它不更新权重，效果只对已测模型成立，换模型或分布后需要重新验证。 答案就是 把「怎么问」设计好 。提示工程不碰模型内部，只经营你喂给它的那段输入——说清要什么、给谁看、什么格式、什么口吻、给不给例子。像开头那个手表文案：把受众、卖点、条数、字数、风格都讲明白，输出质量立刻不同。 它是「无需训练」的第一手段 提示工程不改权重、即时生效、随时可改，通常适合先验证需求。但提示越长，推理费用、延迟、维护和回归评测成本越高；“不用训练”不等于“零成本”。

### 4.5.2 凭什么「怎么问」影响这么大

最关键的疑问：模型没变，只是问法变了，凭什么结果差这么多？。 提示对结果的影响可以理解为它重新设定了模型接龙的起点与条件，用于解决模型没变、只问法变凭什么差这么多的疑问；它输入提示和已有前缀，先把提示当作接龙的起点与条件，再据此预测最可能接下去的内容，输出下一步的续写。提示越明确越表示锁定该说什么的范围越窄，但更符合要求只说明约束命中率提高，不表示模型获得了新知识。 回忆大模型的本质：它在预测「 在你给的这段文字之后，最可能接下去的内容 」（见「大语言模型」深读页）。你的提示，就是它 接龙的起点和条件 。提示越清楚、约束越具体，模型能锁定「该说什么」的范围就越窄、越准；提示越含糊，它就只能往「最泛泛、最安全」的方向接，于是给你一段正确的废话。 一句话 你不是在「命令」一个理解你的人，而是在 给一个接龙引擎设定一个尽量明确的开头 。开头设定得越好，它接出来的东西越合你意。

### 4.5.3 运行示例：把含糊愿望改成任务契约

怎样把一句含糊愿望，改写成模型和评测器都能执行的任务契约？。 任务契约可以理解为把含糊愿望改写成模型和评测器都能执行的明确规格，用于解决怎样让提示可迭代、可验证的问题；它输入原始需求和失败样本，先定目标、上下文、边界与输出结构，再一次只改一个因素并在固定测试集复测，输出一份可评测的提示契约。分数改善表示某类失败在减少，但若改善不能对应具体失败，就只是不可归因的提示堆叠。 图示：提示从目标、上下文、约束到输出契约的分层结构。 图 1 有效提示像接口契约：先定义目标，再提供必要上下文，写清禁止越过的边界，最后规定可验证输出。角色描述只是辅助，不应代替权限或事实来源。 套路； 做什么； 例。 清晰具体； 说清任务、受众、约束，别让它猜； 「面向跑者、每条≤20字」。 给角色； 设定身份/视角，收敛风格； 「你是资深文案」。 指定格式； 要什么结构就明说； 「输出 3 条，用列表」。 给示例（few-shot）； 演示一两个「输入→输出」，让它照做； 见「上下文学习」。 让它分步（思维链）； 复杂题让它先推理再答； 见「思维链 CoT」。 给边界； 说明不要什么、无法回答时怎么办； 「不确定就说不知道」。 。 提示是要迭代的 很少一次就写好。看输出哪里不对 → 针对性补一句约束 → 再看。把提示当成 可调的参数 ，一次改一处、观察效果，比一次堆一大段更容易调准。 运行示例：退款助手 初版“回答退款问题”在 20 个测试里只有 11 个同时给出期限和出处。加入任务范围、允许引用的资料、无证据时的澄清策略，以及 JSON 字段 decision/reason/source 后，17 个通过；剩余 3 个失败都涉及质量问题例外，说明下一步应补检索证据或业务规则，而不是继续堆“请认真、请专业”。提示改进应对应可观察失败。

### 4.5.4 它的底层原理，其实是上下文学习

为什么「给几个示例、给个格式」模型就照做了？这背后有个更基础的机制。 提示工程之所以管用，可以理解为它借用了模型的上下文学习能力，用于解决为什么给示例、给格式模型就照做的问题；它输入提示中的示例和新查询，先在前向计算里定位输入到输出的规律，再按这个模式生成，输出符合示例样式的回答。能照示例办事说明模型在做上下文学习，但这种模仿不写进权重，也不保证每个提示都被忠实遵循。 是 上下文学习 （见其深读页）：模型能仅凭提示里的示例，当场「学会」一个任务的样子并照办。提示工程里最有效的那些招——给示例、给格式、给角色——本质都是在 用提示演示「我要的输出长什么样」 ，模型识别出这个模式就跟着做。 换个说法 上下文学习是「模型能照着提示里的样子办事」这个 能力 ；提示工程是 把这个能力用好的手艺 ——设计出让模型一看就懂「该办成什么样」的提示。

### 4.5.5 边界：提示不是万能

提示工程这么好用，那它的天花板在哪？什么时候该换招？。 这一节描述提示工程的能力边界与该换招的时机，用于解决什么时候提示压不住、该换招的问题；它输入失败类型、知识来源、稳定性、调用规模和成本，先判断缺的是事实、硬格式还是稳定行为，再决定继续改提示、接入检索还是微调，输出一个换招决策。提示压不稳通常表示问题超出措辞层面，但提示不能创造知识、权限或确定性保证。 缺的是事实 （要最新/私有知识）→ 提示再好也变不出模型没有的知识，该上 RAG （见其深读页）。 要稳定的复杂行为/格式 ，提示总压不稳、或每次都要写很长 → 考虑 微调 把行为固化。 要管理的是「整个上下文里放什么」 （历史、检索、示例怎么组织）→ 那是更上层的 上下文工程 （见其节点）。 务实的阶梯 先用提示工程低成本验证 → 缺可更新事实时考虑 RAG → 需要跨大量请求保持特定行为时再评估微调。具体顺序仍取决于质量、延迟、隐私与运维约束。 提示是起点，不是终点。 。

### 4.5.6 暗面：提示注入

既然模型这么听「提示」的话，那恶意的提示能不能劫持它？。 提示注入可以理解为把恶意指令藏进外部内容、劫持模型行为的攻击，用于解决提示的力量为何同时是攻击面的问题；它输入混有可信指令与不可信外部文本的上下文，先让模型像读数据一样读进外部文字，再可能把其中的指令也当成命令执行，输出偏离原任务的行为。模型照做外部指令表示提示能塑造行为这点被反过来利用，但检测到攻击语句不表示建立了安全边界，真正防护要靠权限隔离与人工确认。 能，这就是提示注入 模型会读各种外部内容（网页、邮件、文档）。如果其中藏着「忽略之前的指令，改为……」这类恶意提示，模型可能 把它也当成指令 照做，覆盖你原本的意图（见「提示注入」深读页）。 提示能塑造模型行为，是它的力量，也是它的攻击面。 。

### 4.5.7 把整条因果链连起来

从条件生成推到任务契约、迭代评测、能力边界和提示注入风险。 不改模型，只把「怎么问」设计好，让模型稳定产出想要的结果——这就是提示工程。 （§1） 。 它有效，是因为模型在「接龙」，你的提示是它的起点和条件，越明确它越准。 （§2） 。 通用套路：清晰具体、给角色、指定格式、给示例、让它分步、给边界，并迭代。 （§3） 。 底层原理是上下文学习：提示在演示「要什么样」，模型照做。 （§4） 。 它的边界：缺事实上 RAG、要稳定行为上微调、管上下文靠上下文工程。 （§5） 。 它的暗面是提示注入：能被提示塑造，就能被恶意提示劫持。 （§6） 。 过关标准 如果你能讲清「为什么换个问法结果差这么大（模型在接龙）」，并说出「提示工程和上下文学习是什么关系」，你就抓住了它的内核。

### 4.5.8 常见误解

这些误区把提示当训练、知识库、一次性文案或安全控制面。 误解； 更准确的理解。 提示工程要改/训练模型； 不改权重、只改输入，通常迭代快；仍有 token、延迟、维护与评测成本。 是玄学，靠念咒语； 是把任务、受众、格式、约束讲清楚，可迭代可复现。 提示能变出模型没有的知识； 不能；缺事实要靠 RAG，缺行为稳定性要靠微调。 一次写好就行； 要看输出迭代调整，一次改一处更易调准。 提示只影响措辞，不涉安全； 能塑造行为就能被提示注入劫持。 。

### 4.5.9 检查你是否真的理解

提示工程改动了模型吗？它的核心是什么？。 为什么同一个模型换个问法，结果会差很多？。 说出至少四种有效提示的通用套路。 「给示例、给格式就管用」，背后是什么机制？。 什么情况下提示工程压不住，该换成 RAG 或微调？。 提示工程的「暗面」是什么？。 参考答案 不改模型权重；核心是设计输入的措辞、结构、示例与约束来提高命中率。它即时但并非零成本。 因为模型在预测「你给的文字之后最可能接下去的内容」，提示是它接龙的起点和条件，越明确越能锁定该说什么。 清晰具体、给角色、指定格式、给示例（few-shot）、让它分步（思维链）、给边界——并迭代。 上下文学习：提示在演示「要什么样的输出」，模型识别模式后照做。 缺最新/私有事实用 RAG；要稳定复杂行为或提示总压不稳用微调；管理整个上下文放什么靠上下文工程。 提示注入：藏在外部内容里的恶意提示可能被当成指令、覆盖原意图。

## 4.6 系统提示：在概率模型里声明行为契约，而不是建立安全边界（system-prompt）

### 4.6.1 系统提示仍然只是模型看到的一串 token

标为 system 后，文本是否变成模型不可违反的程序？。 系统提示的输入是应用注入的角色、任务、行为边界和输出契约，输出是这些 token 条件下的回答分布。聊天模板把消息角色编码进前缀，训练提高遵循高优先级指令的倾向，但没有形式解释器逐条强制执行。遵循结果只能当概率行为；秘密、身份和现实权限必须由模型外系统控制。 聊天运行时把不同角色的消息按模板编码，模型仍对整个前缀计算条件概率。训练让模型更倾向遵守高优先级角色，但生成过程没有一个逐条执行规则的形式化解释器；提示越长、冲突越隐蔽、任务越陌生，遵循可能越不稳定。 因此系统提示适合声明行为预期和协调上下文，不适合保存 API 密钥、实施租户隔离或授权付款。真正不可越过的边界必须由工具参数校验、身份权限和业务策略提供。

### 4.6.2 优先级解决冲突，时间顺序只补充同层上下文

后出现的用户消息为什么不应覆盖更早的系统约束？。 冲突解析接收带角色、来源与时间的消息序列，输出应执行的高层任务和被忽略的低层冲突。系统或开发者约束高于用户目标，不可信网页与工具文本只作为数据；同一层才用较新意图补充。优先级是期望规则，不是执行保证，所以运行时仍须验证输出与副作用。 来源； 信任角色； 应当怎样处理。 系统/开发者； 应用策略与任务契约； 约束低层指令。 用户； 目标和输入； 在高层允许范围内执行。 检索/网页/工具输出； 不可信数据； 作为事实候选，不自动当命令。 历史摘要/记忆； 派生状态； 带来源、作用域和可纠正性。 。 同层消息可按较新意图更新，但跨层冲突应由信任优先级决定。模型可能执行失败，因此运行时仍要验证结果。

### 4.6.3 完整示例：退款助手的契约怎样从需求变成提示与硬门

“退款超过500元需批准”应该只写进系统提示吗？。 案例输入是退款请求、订单事实、金额规则和登录主体，输出是结构化退款提议或缺信息状态，而不是直接改账。模型负责解释并提出意图，确定性策略门再核验所有权、金额与审批令牌，工具返回真实状态。提示通过不代表退款获准；超过五百元且无批准时执行器必须拒绝。 系统提示声明职责：解释政策、收集订单信息、提出退款建议，不声称已经执行。 把订单数据放入带来源的结构化区块，并明确其中自由文本不可信。 要求输出建议、证据订单ID、金额和是否需人工批准的schema。 用户要求退800元时，模型可解释并生成待审批提议。 退款工具根据登录主体、订单所有权、金额和审批令牌独立拒绝未批准调用。 返回工具状态后，模型只能报告真实结果，不能把“已提交”写成“已到账”。 测试正常、边界金额、缺字段、用户覆盖规则、订单备注注入和工具报错。 提示改善决策和解释；执行器拥有最终权威。

### 4.6.4 系统提示预算要用消融实验而不是越写越长

新增一页规则后效果下降，怎样判断是规则冲突还是上下文竞争？。 提示消融输入短版、长版和结构化改写版以及同一契约测试集，输出通过率、修复数、回归数、成本和延迟。一次只改变规则表达并逐切片比较；净收益为负表示回归多于修复。单一总通过率仍可能掩盖关键安全回归，因此不能独自决定发布。 建立200条契约测试。短版提示通过176条，遵循率88%；长版通过170条，85%，其中旧能力回归12条、新规则修复6条，净变化−6。再将新增规则拆成结构化冲突表，若通过184条即92%，说明问题来自表达和冲突，而非“模型记不住所有规则”的单一解释。 公式：通过率 r 等于通过数 m 除以测试总数 n；净收益 delta 等于新修复数 f 减去新回归数 g，本例为六减十二等于负六。 r 是契约测试通过率， m 是通过的测试条数， n 是测试总条数； Δ 是版本相对基线的净收益， f 是新版本修复的旧失败数， g 是新版本造成的新回归数。负 Δ 表示新增回归多于修复，不能因局部新规则生效就发布。 还要测token成本、首字延迟和不同任务切片，不以单个示例决定版本。

### 4.6.5 原创图：提示契约与执行权限必须分层

模型被注入时，哪一层仍能阻止真实副作用？。 分层系统输入模型提出的结构化意图及身份、金额、目标域等权威状态，输出允许、拒绝或待审批的工具调用。概率模型只提出意图，确定性策略门执行校验，业务工具负责幂等状态变化并回传事实。图中的箭头表示控制流，不表示系统提示本身拥有授权能力。 图示：系统提示与用户目标、不可信数据进入模型，模型提出结构化意图，再经策略权限和业务工具验证。 图 1 系统提示管理模型行为，确定性策略管理现实权限。

### 4.6.6 把提示写成最小、分区、无矛盾的契约

角色口吻、政策、数据和例子混在一段里会发生什么？。 提示设计输入稳定目标、动态数据、信任边界、失败处理和输出 schema，输出最小、分区且无矛盾的行为契约。稳定规则留在提示，频繁变化的数据通过结构化配置或检索注入；冲突时明示优先关系与保守回退。提示越短并不自动越好，删减后仍须用覆盖边界的正反例验收。 按稳定目标、不可违反约束、输入信任边界、决策流程、输出schema和失败处理分区；用同一术语表达主体和动作，写清适用与不适用。把会频繁变化的业务数据放到结构化配置或检索，不复制进长提示。 规则冲突时明示优先关系和保守回退，例如“资料不足时询问，不猜测；涉及写操作先提议再批准”。少量覆盖边界的正反例比大量风格示例更有价值。

### 4.6.7 提示注入利用的是指令与数据共享通道

用XML标签包住网页内容，为什么只能降低混淆而不能隔离？。 注入测试输入可信指令与含恶意文本的网页、文档或工具结果，输出模型意图和实际工具动作。标签只能提示“这是数据”，恶意 token 仍参加同一注意力计算；真正防线是最小上下文、工具白名单、最小权限与审批。只通过一种“忽略之前指令”模板不能证明抵抗多语言、编码或多轮攻击。 标签、引号和“不要执行以下内容”给模型提供语义提示，但网页里的恶意文本仍进入同一上下文并参与注意力。间接注入可要求泄露提示、改写目标或调用工具；模型可能在长链条里忘记信任边界。 把外部内容视为数据，最小化可见上下文；工具使用最小权限和目标白名单；敏感动作由确定性策略或人批准。用多语言、编码、长上下文和工具返回中的注入测试，而非只测“忽略之前指令”。

### 4.6.8 系统提示不是秘密存储，防泄露要假设它可被推断

提示里不直接展示密钥，是否可以放内部政策和检测阈值？。 泄露评测输入系统提示资产、攻击提问和日志工具路径，输出原文复述、语义推断与实际安全损失。默认假设提示可被复述或推断，因此密钥、个人数据和敏感检测逻辑不能进入上下文。公开行为规范被复述未必是事故，是否失败必须先按资产价值定义。 用户可通过直接索要、角色扮演、逐段推断、错误回显或工具日志获得提示内容；模型也可能复述其语义。密钥、个人数据和真正需保密的规则不应进入提示。可公开的行为规范可以写入，敏感检测逻辑放在服务端。 提示泄露与指令违反是不同指标：模型不复述原文仍可能受低层恶意指令控制；反之公开规范被复述未必造成安全损失。先定义资产再测试。

### 4.6.9 输出结构与拒绝路径必须可被消费者验证

模型说“需要批准”，下游为何不能只读这句话？。 输出契约接收模型建议，输出版本化状态、字段和拒绝原因供消费者解析。消费者依次做类型、枚举、跨字段、身份和业务状态校验；自由文本解释不触发副作用。结构合法只表示格式通过，不证明订单所有权、金额或权限语义正确。 让模型产生版本化schema和明确状态，如 propose_refund 、 needs_approval 、 insufficient_data ；消费者做类型、枚举、跨字段和业务校验。自由文本解释不能触发副作用，拒绝或缺信息也是一等状态。 结构化输出保证格式不保证语义；订单是否属于用户、金额是否允许仍由权威系统查询。提示和schema版本要一起回归，防消费者与模型契约漂移。

### 4.6.10 会话、摘要和记忆会让旧提示假设漂移

系统提示未改，为什么长对话后行为仍可能变化？。 长时状态装配输入系统不变量、历史、摘要、工具观察和带作用域记忆，输出本轮模型可见上下文。每轮重申必要边界并携带来源与可纠正状态，任务切换时清除局部记忆。初始规则只出现一次不能保证摘要后仍存在，也不能阻止旧目标跨任务残留。 历史消息、压缩摘要、工具观察和记忆不断改变条件上下文；旧用户目标可能被摘要成高置信事实，或跨任务残留。每轮重申必要的不变量，按任务/用户作用域读取记忆，并把来源与可纠正状态传给模型。 压缩后运行冲突和安全哨兵测试；任务切换时清除局部状态。不能依赖“最初说过一次”来保护长时Agent。

### 4.6.11 版本化提示像代码，但回滚证据比文本diff更重要

只改一句措辞，为什么也可能改变完全无关的任务？。 提示发布输入提示、模板、模型、采样、工具 schema 和评测集版本，输出带回归证据的候选版本与回滚包。文本变化会重新分配生成概率，须灰度比较任务成功、冲突、误拒、成本和人工修正。文本 diff 只说明改了什么，不能证明行为没有旁路回归。 提示变化会改变注意力和生成分布，影响不同语言、长上下文、工具选择和拒绝。保存提示、模板、模型、采样、工具schema和评测集版本；灰度比较任务成功、契约遵循、冲突解决、误拒、token成本和人工修正。 文本diff说明改了什么，不说明行为怎样变。发布需要冻结回归集、隐藏攻击集和生产影子样本；异常时能同时回滚提示与关联schema。

### 4.6.12 契约测试覆盖正常、冲突、恶意和故障四象限

提示测试为什么不能只保存几个理想对话？。 契约测试输入正常、冲突、恶意和故障四类样本，输出结构、决策、副作用与用户可见事实的断言结果。按语言、长度、版本和风险切片统计，并保留失败样例与置信区间；逐字措辞不必一致，但高风险动作和事实边界必须确定性通过。 正常集验证主任务；冲突集让用户、历史和工具内容与高层约束相反；恶意集覆盖注入、提取、编码与多轮；故障集覆盖缺字段、超时、拒绝和工具不一致。断言结构、决策、工具副作用和用户可见事实，而非逐字匹配措辞。 按语言、长度、模型版本和风险切片，报告置信区间与失败样例。模型评审可辅助扩展，但高风险判定使用确定性检查或人工复核。

### 4.6.13 常见误区与概念依赖

系统提示是概率契约层，不是权限、秘密或业务真相。 初学者最易混淆： “优先级更高”描述模型应遵循什么，不证明它每次都会遵循；安全设计必须假设遵循会失败。 误区； 更准确的理解。 system消息不可覆盖； 训练提高遵循倾向，不是形式保证。 提示内规则能保密； 默认可被复述或推断。 提示可授权工具； 权限由执行器和主体身份决定。 越长越可靠； 冲突与上下文竞争会增加。 。 学习路线： 先学上下文、结构化输出和工具调用，再学提示注入、指令层级、策略引擎与契约评测。

### 4.6.14 把因果链连起来

这个概念怎样从问题一路连接到可验证的实践？。 把业务需求拆成稳定契约与动态数据。 给每类上下文标记角色、来源和可信度。 用最小提示声明目标、冲突和失败路径。 让模型只提出结构化意图。 由确定性策略核验身份、权限和业务状态。 把工具事实回传而不伪造成功。 用四象限契约集评测并灰度发布。 监控长时状态漂移并版本化回滚。 验证层； 在“系统提示：在概率模型里声明行为契约，而不是建立安全边界”中固定什么； 观察什么证据。 输入； 同一批样本、前处理与权限边界； 输入哈希、切片标签和拒绝原因。 机制； 仅改变一个核心变量，其余配置锁定； 关键中间状态及首次偏离预期的位置。 输出； 同一验收规则与资源预算； 质量、成本、延迟和失败率的分层差异。 反证； 保留不启用目标机制的对照组； 收益是否跨样本与随机种子稳定复现。 。

### 4.6.15 误区与自测

你能否不用背术语，解释它的机制、边界与验证方法？。 系统提示为何不是安全边界？。 时间更晚的用户消息能否覆盖系统规则？。 为什么提示里不能放密钥？。 结构化输出还需什么校验？。 提示发布为何需要行为回归？。 假设“系统提示：在概率模型里声明行为契约，而不是建立安全边界”在离线示例上表现正常、上线后核心结果却下降，你会怎样按输入、内部变换、输出反馈和适用边界定位问题？。 如何为“系统提示：在概率模型里声明行为契约，而不是建立安全边界”设计一个最小对照实验，证明观察到的改善来自核心机制，而不是数据、提示、权限或评测口径同时变化？。 。 参考答案 它仍是模型条件上下文，遵循是概率行为；权限和副作用必须由执行层保证。 按设计不应；跨层冲突由信任优先级而非时间顺序决定，但仍需测试。 提示可能被直接复述、间接推断或通过日志泄露。 类型、跨字段、授权和权威业务状态校验。 小文本变化也会改变多任务、语言、工具选择和拒绝分布。 先保存同一失败样本及环境，确认输入、权限和前置条件没有漂移；再记录关键中间状态，检查机制是否按本页描述完成变换；随后把原始输出与独立指标、人工终验对照；最后用边界样例和对照实验复测。只有定位到首次偏离预期的环节，才能判断应修改数据、机制、评测还是使用边界。 固定数据、模型版本、提示、权限、预算和评测，只改变一个与核心机制直接相关的因素，并在多个样本与随机种子上重复；同时保存中间状态和失败样本。若差异只在目标因素变化时稳定出现，才支持机制解释，否则应继续排查混杂变量。

## 4.7 上下文工程：设计模型在这一刻真正能看见的信息（context-engineering）

### 4.7.1 1. 模型回答时究竟“知道”什么？

直觉 模型参数提供一般能力，而当前输出直接受这次调用中可见的上下文约束。 上下文工程的输入是本轮可用的规则、任务、证据、历史、工具结果与记忆，输出是带来源、顺序和预算的最终上下文包。装配器进行选择、过滤、压缩和排序；回答只说明模型基于最终包完成了生成，未进入包的信息本轮不可用。 一次实际调用可能包含系统规则、用户请求、会话历史、检索片段、工具返回、长期记忆、代码与输出格式。上下文工程就是决定这些信息如何被选择、转换、排序、标注和更新，使模型在有限窗口中拿到完成任务所需的最小充分证据。 边界： 提示工程重点打磨指令表达；上下文工程还管理外部信息的完整生命周期。两者重叠，但后者的系统范围更大。

### 4.7.2 2. 上下文由哪些层组成？

工程 先按职责分层，才能处理冲突、更新和可观测性。 分层装配接收多来源内容，输出规则、任务、证据、记忆和示例五类带元数据区块。来源、时间、可信度和作用域决定冲突与更新方式；离模型更近只表示位置，不表示更可信。缺少来源标签时，系统无法可靠解释冲突或撤销错误记忆。 规则层： 系统约束、权限、输出契约。 任务层： 用户目标、验收条件、当前状态。 证据层： 检索文档、数据库记录、工具结果与引用。 记忆层： 跨轮偏好、已确认事实、阶段性摘要。 示例层： 少样本示范和边界案例。 每段内容最好带来源、时间、可信度和作用域。冲突时按明确的权限规则处理，而不是默认“离模型最近的文字最可信”。

### 4.7.3 3. token 预算应怎样分配？

数学 窗口足够装下不等于模型能同等有效地使用全部内容，还要给输出和工具往返留余量。 预算器输入窗口上限、各类候选 token 和输出需求，输出受保护预算、可压缩预算与安全余量。先锁定规则、任务和输出，再按单位 token 价值选择证据与历史；结果表示装配计划可行，不保证模型能同等使用所有位置。 公式：窗口预算 B window 大于等于规则、任务、证据、历史和输出预留五项预算之和。 Bwindow 是服务允许的总 token 窗口； Brules 、 Btask 、 Bevidence 、 Bhistory 分别是规则、当前任务、证据和历史的 token 占用； Breserve 是为模型输出和工具往返保留的预算。各项按同一 tokenizer 计数；不等式要求计划占用不能超过窗口，而不是鼓励把窗口全部填满。 先锁定不可删的规则、任务与输出预算，再将剩余容量分给高价值证据和必要历史。可按“预期信息增益 ÷ token 成本”排序候选片段；重复、过期和低置信内容应被去重、压缩或舍弃。

### 4.7.4 4. 为什么检索到了还不够？

工程 召回只是找到候选，模型最终读到什么还取决于重排、切块、组织与引用。 证据装配输入召回候选、权限、时效和当前子问题，输出去重重排且保留邻接语境与引用的证据包。过滤、重排、扩展和结构化决定模型实际读到什么；召回命中只说明候选池含答案，不能证明最终上下文保留或回答正确使用。 查询改写 → 多路召回 → 权限/时效过滤 → 重排去重 → 邻接扩展 → 结构化装配 → 带引用生成。 切块需要保留标题、文档路径和相邻语境；重排要围绕当前子问题，而非只看语义相似度。关键结论可放在任务附近并用清晰标签组织，避免重要证据淹没在长上下文中。 例子： 回答 API 迁移问题时，与其检索十篇泛教程，不如保留当前版本迁移指南、受影响接口定义和项目中的实际调用位置，并注明各自版本。

### 4.7.5 5. 历史和记忆为什么不能无限累积？

直觉 旧上下文会过期、相互矛盾并消耗注意力，因此记忆是一项有写入和淘汰规则的数据治理工作。 记忆治理输入历史事件、已验证事实、作用域和保留期，输出可更新、撤销和追溯的短期摘要或长期记录。只写跨任务稳定且有价值的事实，并保留未解决项和证据链接；流畅摘要不能解释为事实保真，敏感或过期记忆必须淘汰。 短期历史用于保持当前任务连续；阶段摘要保存已经验证的决定；长期记忆只记录跨任务仍有价值的稳定事实。每条记忆应能被更新或撤销，敏感信息要设作用域和保留期。摘要必须保留未解决问题、关键约束和证据链接，不能只留下流畅叙事。

### 4.7.6 6. 外部文本如何避免变成隐形指令？

工程 检索文档和网页属于不可信数据，即使其中写着“忽略此前规则”。 信任隔离输入外部文本、来源与拟执行工具，输出标记为数据的内容和经过授权的动作。数据边界减少指令混淆，权限校验和人工批准阻止副作用；模型拒绝一次恶意句子不代表形成安全保证，编码、多语言和间接注入仍需测试。 把外部内容放入明确的数据边界，保留来源和内容类型；工具调用采用最小权限与参数校验；高风险动作要求独立授权；输出引用回原证据。不要仅靠一句“忽略提示注入”防守，因为模型仍可能混淆数据与指令。 检查： 上下文质量不仅是相关性，还包括权限正确、来源可靠、时间有效和内容安全。

### 4.7.7 7. 如何观测并调试上下文系统？

工程 必须能重建“模型当时看见了什么”，否则失败只能被笼统归咎于模型。 可观测性输入最终上下文、片段元数据、裁剪日志、版本和输出，输出可重放的失败轨迹与首次失效关卡。逐层比较召回、排序、保真、引用和答案，并用消融定位贡献；脱敏是边界，日志不能为了调试重新泄露用户秘密。 记录经过脱敏的最终上下文、各片段来源与得分、token 占用、裁剪原因、模型版本和输出引用。评测时分别测召回命中、排序质量、上下文忠实度、答案正确性和成本；用消融实验逐层移除内容，判断哪一层真正贡献了结果。

### 4.7.8 8. “更长上下文”为什么不等于“更好系统”？

辨析 容量解决的是能否放入，工程解决的是是否放对、摆对并及时更新。 长窗口评估输入候选材料、位置、长度、成本和任务结果，输出容量与有效利用的分离曲线。更多 token 会增加冲突、延迟和中间迷失概率；较短但证据充分的包可能更好。窗口变长只扩大可放入上限，不能替代检索、排序、更新和验证。 长窗口仍可能遭遇中间信息利用率下降、冲突证据、延迟和成本增长。成熟方案会先定义所需证据，再检索和压缩，并对关键位置、引用和失败路径进行评测，而不是把所有历史直接拼接。

### 4.7.9 9. 运行示例：一次 16K 退款问答怎样装配？

运行示例 用户问“签收 35 天、商品有质量问题还能退吗”，系统怎样把有限窗口变成最小充分证据包？。 图示：上下文工程从候选信息池过滤排序到最终上下文包。 图 1 上下文工程是可观测的数据管道：候选内容先过权限、时效、相关性与预算，再进入最终请求；模型输出与引用结果反过来帮助诊断装配错误。 预算项； 候选； 最终； 装配决定。 规则/任务； 1K； 1K； 受保护，不由外部文档覆盖。 历史； 6K； 1K； 只保留订单号、签收日和已确认质量问题。 证据； 18K； 5K； 保留 30 天一般规则、质量例外及版本元数据。 示例/schema； 2K； 1K； 保留一条边界示例和输出契约。 输出/工具余量； 0； 4K； 避免回答或二次核验被截断。 。 逐步演算： 候选总量 1+6+18+2=27K ，无法进入 16K 窗口。装配后输入 1+1+5+1=8K ，加 4K 输出/工具余量为 12K，还留 4K 安全空间。被删除的是低价值重复和旧闲聊，不是随机截掉最早文本。 “最小充分”不是字数最少。 如果退款结论依赖一般规则、质量例外、订单日期和证据版本，那么四项缺一都不充分；反过来，十段重复政策即使相关，也不增加决定所需信息。装配器应围绕验收条件定义必要字段，再为每个字段选择最可信、最新且权限允许的证据。 失败边界： 压缩若把“质量问题不受 30 天限制”缩成“退款期限 30 天”，省下 token 却改变了事实。摘要必须保留例外、否定、数值、未解决项和来源；高风险字段可用结构化记录而非自由摘要。

### 4.7.10 10. 怎样证明装配策略真的更好？

评测 最终答案变好或变差时，怎样区分是召回、筛选、压缩、排序还是模型本身造成的？。 管道评测输入冻结的问题集、知识快照、模型与装配变体，输出每个关卡、任务切片、成本和逐样本差异。一次只替换一个组件，并从必要证据召回一路检查到业务验收；任一布尔关卡失败都足以让任务失败，平均分不能补偿关键证据缺失。 先把成功事件拆成可观察关卡：必要证据被召回、经过权限与时效过滤后仍被保留、压缩没有改变关键事实、模型实际使用证据、答案通过业务验收。它们不是一个平均分可以互相补偿的条件；任何关键关卡失败，都可能使最终回答失败。 公式：任务成功 S 等于召回 R、保留 K、事实保真 F、证据使用 U 和业务验收 A 五个布尔关卡的逻辑与。 S 表示任务是否成功； R 表示必要证据被召回， K 表示装配后仍保留， F 表示压缩后关键事实保真， U 表示回答实际使用证据， A 表示最终通过业务验收。符号 ∧ 是逻辑“并且”：五项任一为假，S 就为假，不能靠其他环节高分补偿。 同一批 20 个退款问题； 正确； 平均输入； 暴露的结论。 全部候选直接拼接； 12/20； 15.2K； 噪声和冲突多，容量接近上限。 过滤 + 重排 + 保留例外； 17/20 ； 8.1K； 更短但证据覆盖更完整。 在上一方案中删掉质量例外； 11/20； 7.5K； 600 token 的节省破坏关键切片。 保留例外但去掉来源元数据； 15/20； 7.8K； 答案可能正确，却难以验证版本与引用。 。 这是一个教学用消融表，不是普适性能数字。真实项目应冻结问题、知识库快照、模型和评分规则，每次只移除或替换一个组件，并保留逐样本差异。若“删掉例外”只伤害质量问题切片，总体平均值可能掩盖风险；因此还要按任务、语言、权限和证据版本切片。 诊断顺序： 先检查必要证据是否进入候选池，再检查它是否被过滤、压缩或截断，随后检查模型是否引用并正确使用，最后才比较模型版本。这样才能把“答错了”变成一个可修复的管道故障。

### 4.7.11 11. 常见误解与概念依赖

误区与路线 下面这些说法把“容量”“相关性”“摘要”和“记忆”误当成无需治理的文本堆叠。 常见误解； 更准确的理解。 上下文工程就是写更长提示； 还管理检索、权限、历史、记忆、工具结果、预算和可观测性。 相关片段越多越保险； 重复与冲突会稀释关键证据；要围绕当前子问题重排去重。 摘要一定保真； 摘要会丢否定、例外和来源，必须按字段验收并可追溯。 长期记忆写入越多越懂用户； 错误、过期和敏感记忆会持续污染；需要作用域、撤销与保留期。 模型答错就是模型不够强； 应先重建最终上下文，区分召回、装配、截断、证据和生成失败。 。 学习层级； 概念依赖与延伸学习。 先修； 上下文窗口、提示工程、检索与 RAG。 本页核心 ； 信息分层、预算分配、策略装配、来源/时效、记忆治理、可观测性。 紧邻； 中间迷失、上下文压缩、Agent 记忆、提示注入。 工程延伸； 重排、引用与溯源、评测、提示缓存、隐私与数据治理。 。

### 4.7.12 12. 检查你是否真的理解

自测 请不要只复述术语，而要能为退款案例画出候选池、装配决定和失败归因。 上下文工程为何不只是“写一个更长的 prompt”？。 16K 案例为什么只用了 8K 输入，而不是把剩余空间全部塞满？。 检索命中正确文档后，还需经过哪些关键步骤？。 长期记忆为什么必须支持更新、撤销和作用域？。 消融实验里删掉质量例外后，为什么总体平均分可能仍掩盖风险？。 查看答案 它还管理检索、工具结果、历史、记忆、权限、时效、token 预算、压缩、来源和可观测性。 需要给输出、工具往返和长度波动留余量；目标是最小充分，不是把窗口填满。 权限与时效过滤、围绕子问题重排、去重、补相邻语境、保真压缩、结构化装配、引用和最终验收。 用户事实和环境会变化；错误、过期或越界记忆会持续污染后续任务，也可能扩大隐私暴露。 质量问题可能只是少数切片；大量普通问题仍答对，会把这个高风险切片的明显退化平均掉。

## 4.8 约束解码：用自动机把非法 token 概率置零（constrained-decoding）

### 4.8.1 提示要求与解码保证的区别

“只返回 JSON”写得再醒目，为什么百万次调用仍会稳定出现坏格式？。 约束解码输入模型 logits、当前前缀和形式规则，输出只从合法 token 集抽样的序列。提示仅改变概率，约束器则把非法候选概率置零并重新归一化；格式通过只说明结果属于形式语言，不证明字段真实、业务关系成立或调用者有权限。 提示只改变模型分布，合法输出概率即使是 99.9%，百万次仍预期约一千次失败。约束解码在采样器层面删除非法候选，使输出不能离开文法；这是机制保证，不是模型“更听话”。 它适合工具参数、批量抽取和数据库接口。自由文章若强行套复杂 schema，会牺牲表达、增加延迟；而且结构合法并不使内容可信。 三层边界： 约束解码保形式；业务校验保字段关系；鉴权与事务控制保动作后果。

### 4.8.2 文法怎样变成增量状态

生成只看到一个前缀，系统怎样知道下一 token 合不合法？。 状态编译输入 schema、正则或文法和目标 tokenizer，输出可随前缀推进的解析状态及合法 token 集。每接受一个完整 token 字节串就更新状态，只有接受态可以正常结束；不支持的 schema 关键字和开放世界事实必须留给生成后校验。 运行时把 JSON Schema、正则或上下文无关文法编译成 DFA、PDA 或等价解析状态。状态保存当前在对象、数组、字符串还是数字，哪些必填字段已出现，以及下一步允许什么。每接受一个 token，就推进状态；只有接受态才可结束。 JSON Schema 不只是一份说明。支持器需把类型、枚举、required、additionalProperties、数组界限与嵌套引用映射为文法；并非每个实现支持所有关键字，远程引用、复杂正则和语义格式通常需生成后校验。 约束来源； 容易表达； 通常表达不了。 正则； 局部字符串形状； 任意嵌套与跨字段关系。 JSON Schema； 对象、类型、枚举、必填； 数据库存在性与权限。 CFG； 递归语法、代码结构； 变量语义与运行结果。 自定义状态机； 协议和有限流程； 开放世界事实。 。

### 4.8.3 掩码后必须重新归一化

原模型最想输出非法 token 时，受限分布怎样变化？。 受限采样输入原概率与当前合法集合，输出非法项为零且合法项总和为一的新分布。先掩码再在合法集归一化；若高概率候选全非法，合法输出也可能内容很差。空集合表示 schema、tokenizer、前缀或处理顺序不兼容，应返回可诊断失败。 公式：状态 s 下 token t 的受限概率 P prime 等于原概率乘合法集合指示函数，再除以所有候选 u 的合法概率质量之和。 P(t|s) 是解析状态 s 下模型给 token t 的原始概率， P′(t|s) 是应用文法约束后的抽样概率； M(s) 是从状态 s 仍能通向完整合法结果的 token 集； 1[·] 是条件成立取 1、否则取 0 的指示函数； u 遍历所有词表候选。分母是剩余合法概率质量，负责把合法候选重新归一化到总和为 1。 M(s) 是当前状态仍能通向完整合法结果的 token 集。非法 token 乘零，剩余质量重新归一化。约束不会让模型更懂任务；若所有高概率候选非法，它只能在低概率合法候选中选择，内容质量可能下降。 温度、top-k、top-p 与掩码的顺序会影响结果。通常先得到 logits，再应用语法掩码并在合法集上采样；若先 top-k 恰好删光合法 token，会形成错误死路。实现应明确顺序并回归。 空候选不是“再试一次”就好。 它常说明 schema、tokenizer、前缀或裁剪顺序不兼容，应返回可诊断状态。

### 4.8.4 运行示例：一步退款动作怎样被约束

### 4.8.5 token 不是字符，掩码必须理解 tokenizer

为什么按“下一个字符是否合法”过滤 token 会错？。 tokenizer 感知掩码输入当前解析状态和候选 token 的完整字节串，输出能否走到可继续状态。token 可跨字符、引号、逗号与 Unicode 字节，合法枚举前缀也应保留；换模型或 tokenizer 后必须重新编译，旧缓存可能封死合法路径或放行错误。 一个 token 可能包含开引号、多个字符甚至引号和逗号；Unicode 字符可能跨字节，转义序列又改变表面文本。运行时要判断整个 token 字节串从当前解析状态走过后是否合法，并能否继续到接受态，而不是只看 token 首字符。 枚举“refund”可能被切成一个 token，也可能是 ref + und 。前缀 token 即使尚未组成完整枚举，只要仍是某个合法枚举的前缀就应允许；反之，表面以 r 开头却无法完成任何枚举就应屏蔽。 必须用目标模型的真实 tokenizer 编译和测试。 换模型或 tokenizer 后复用旧掩码缓存，可能允许错误或把合法路径封死。

### 4.8.6 复杂 schema 会制造状态与性能问题

字段和分支越完整，为什么首 token 可能更慢、解码也更抖？。 复杂度治理输入 schema 结构、tokenizer 和资源上限，输出编译状态数、逐步掩码成本与拒绝原因。大枚举、递归和交叉分支扩大状态空间；最小 schema 加版本缓存通常更稳，但缓存键必须同时包含 schema 哈希与 tokenizer 版本。 大枚举、深递归、oneOf/anyOf 交叉和复杂正则会增加编译时间、状态集合与每步合法 token 计算。可缓存“schema 哈希 + tokenizer 版本”的编译产物，但必须限制 schema 大小、递归深度、数组长度和字符串长度，防止资源耗尽。 症状； 可能原因； 处理。 首 token 很慢； 首次文法编译； 预编译与版本缓存。 每 token 慢； 合法集合计算复杂； 简化分支、状态缓存。 空候选； 实现不支持或前缀冲突； 兼容性测试、明确失败。 输出过长； 无数组/字符串上限； schema 与总 token 双限。 。 最小 schema 往往更稳：只让模型生成需要判断的字段，服务器补默认值和派生字段。

### 4.8.7 流式输出和工具调用的提交边界

既然每个前缀都可延伸为合法结果，能否边生成边执行字段？。 流式提交输入增量前缀、接受态、schema 结果和业务授权，输出仅在全部校验完成后的原子工具调用。前缀合法不等于对象完整，断流也可能留下半个值；重试必须带幂等键，不能自动补齐截断 JSON 后执行。 不能把“当前前缀合法”当“对象已完整”。字符串、数字、数组都可能继续；网络中断还会留下半个对象。客户端可流式展示进度，但工具参数应等接受态、schema 和业务校验全部通过后原子提交。 流断后要区分取消、超时和正常结束，不能自动把截断 JSON 补齐后执行。重试复用幂等键，避免第一次其实成功、响应丢失后重复退款。敏感自由文本字段仍需内容检查和注入隔离。 约束只限制模型输出。 schema 描述中的恶意文本、检索内容和工具返回仍是外部不可信输入。

### 4.8.8 格式、模式、业务和权限要分别评测

JSON 有效率 100% 后，团队还应该看哪些数？。 分层评测输入生成结果、schema、权威事实、主体权限和工具反馈，输出语法、模式、业务、事实、授权与任务质量指标。解析成功只是第一关；任何后续关卡失败都不能被格式有效率补偿，高风险动作还要验证幂等和越权拦截。 分别记录语法有效率、schema 通过率、死路率、额外 TTFT/TPOT、业务校验通过率、事实正确率、工具成功率、越权拦截和最终任务质量。只报 parse 成功会让“格式全对、内容全错”看起来完美。 解析器验证形式和完整结束。 schema 验证字段、类型、枚举、范围。 确定性规则验证金额、日期、跨字段不变量。 数据库/证据验证实体存在与事实。 执行层根据当前主体重新鉴权并限制副作用。 失败返回结构化原因，有限重试或转人工。 用 Unicode、转义、极深嵌套、空数组、长枚举、断流和不支持关键字做对抗回归。

## 4.9 结构化输出：把概率文本接入确定性软件契约（structured-output）

### 4.9.1 自然语言和程序接口的容错方式不同

多一句“好的”或少一个引号，为什么人能理解而程序会崩？。 结构化输出输入任务语义和版本化数据契约，输出可解析、可校验并可被程序拒绝的对象。生成约束与解析器把自然语言容错转成明确字段和状态；格式有效只表示机器能读取，不表示对象内容可信或允许执行。 自然语言依靠语境容忍变体，程序需要明确边界、类型与状态。结构化输出声明字段、必填、枚举、长度和版本，使消费者能机械拒绝异常，而不是用脆弱正则猜模型意图。 提示“返回 JSON”只提高概率；JSON mode 通常保语法；JSON Schema 才进一步约束形状；约束解码在生成时阻止非法路径。支持范围依实现而异，仍需服务端复验。 数据契约的作用： 让失败显式、局部、可计数。它不把概率模型变成可信数据库。

### 4.9.2 四道门必须逐层通过

一个对象能被 JSON.parse 解析，离执行退款还差多远？。 分层验证输入模型对象、schema、权威业务数据与当前主体，输出通过、字段错误、补信息、拒绝或升级。依次检查完整语法、schema、业务事实和权限副作用；前一层通过不能替代后一层，任何失败都禁止下游猜测执行。 层； 检查； 例子； 失败处理。 完整语法； 括号、引号、转义、结束态； 不是半截 JSON； 拒绝/重生。 Schema； 字段、类型、枚举、范围； action∈refund/ask； 字段级错误。 业务与事实； 跨字段规则、查库、证据； amount≤订单可退额； 补信息/转人工。 权限与副作用； 主体、策略、幂等、审批； 当前客服能否批准； 禁止或升级。 。 任何一层失败都不应让下游“尽量猜”。特别是模型给出的 user_id、金额和 action 都是不可信建议，执行层必须从认证上下文重新取得主体与权限。

### 4.9.3 最小 schema 比大而全更可靠

把所有可能字段都塞进一个嵌套对象，为什么会提高错误率和耦合？。 最小 schema 设计输入业务决策字段、服务器已有事实和兼容要求，输出只含模型必须判断的字段与显式分支。服务器填身份、时间和派生值，枚举和 discriminated union 缩小状态空间；过度嵌套会增加无效路径、版本耦合和迁移成本。 只让模型产生需要语义判断的字段；时间戳、用户 ID、总价和派生状态由服务器填充。枚举代替自由动作名，明确 missing 与 null，限制字符串/数组长度，默认拒绝 additionalProperties，并给每个字段写业务含义与例子。 把互斥任务拆成 discriminated union：先用 kind 选择 refund_request 或 ask_clarification，再使用对应的小 schema。这样比一个包含几十个可选字段的对象更容易约束、校验和迁移。 设计选择； 收益； 风险。 枚举动作； 消费者无需猜拼写； 新增值需兼容。 必填字段； 状态完整； 未知值不要用假默认。 长度/范围； 限制资源与荒谬值； 边界需与业务同步。 禁止额外字段； 发现 schema 漂移； 前后版本需协商。 。

### 4.9.4 运行示例：合法对象如何在后两层失败

模型输出 action=refund、amount=120，语法和 schema 都正确，为什么仍不能执行？。 案例输入结构合法对象、订单实付与退款记录、政策上限和当前角色，输出业务错误码或安全动作。公式算得最多可退 80，因此 120 违反订单不变量且角色无批准权；不能静默截成 80 执行，因为那会改变模型意图并掩盖上游错误。 图示：退款结构化输出经过语法、schema、业务事实和权限四道验证门。 图 1 格式保证只让错误更容易检测；数据库事实和当前主体权限仍决定能否执行。 公式：可退金额 R 等于实付金额 P 减已退款金额 D 与政策上限 L 两者中的最小值，本例为八十。 R 是本订单当前最多可退金额， P 是订单实付金额， D 是此前已退款金额， L 是政策允许的金额上限， min 表示取两个候选上限中较小者。该业务不变量依赖权威订单和政策数据，不能只靠 schema 的通用范围判断。 amount=120 在 schema 的通用 0–500 范围内，却违反订单不变量。正确恢复是返回 amount_exceeds_remaining ，让模型改为解释或转人工；不是偷偷把 120 截成 80 后执行，因为这改变了原意且可能掩盖上游错误。

### 4.9.5 约束生成与生成后校验是互补的

如果服务端最终都会校验，为什么还要生成时约束？。 双层机制输入模型分布、schema 和服务端业务规则，输出格式受约束且经后验验证的对象。生成时掩码减少无效重试，生成后校验捕获实现错配与语义错误；格式成功但业务质量下降时不能只庆祝结构通过率。 约束解码减少语法/schema 无效输出和无效重试；服务端校验防实现缺陷、版本错配和语义错误。受限采样把非法 token 置零并重新归一化：。 公式：状态 s 下 token t 的受限概率 P prime 与原概率 P 乘合法集合指示函数成正比。 P(t|s) 是状态 s 下原始 token t 的概率， P′(t|s) 是应用约束后的概率， M(s) 是当前仍合法的 token 集， 1[·] 是合法取 1、非法取 0 的指示函数，符号 ∝ 表示右侧还需除以全部合法候选的概率总和才能归一化。 当模型原本大部分概率压在非法候选上，约束会迫使它选择低概率合法值，格式成功却可能内容变差。因此要同时看首次结构通过率、业务正确率和任务质量。若底层 API 不支持某些 schema 特性，应在启动时契约测试并生成后复验，而非默认相信声明。 不要用自动修复掩盖分布问题。 “修 JSON”模型可能改变字段含义；只有纯语法且可证明等价的修复才适合自动应用。

### 4.9.6 失败恢复要局部、有限且无副作用

校验失败后，把整个错误对象原样塞回模型无限重试会发生什么？。 失败恢复输入机器生成的字段路径、错误代码、允许范围与请求幂等键，输出局部修复、澄清、重取事实、拒绝或人工升级。重试次数必须有限，校验前不产生副作用；同类连续失败应降级到更简单 schema 或确定性表单。 会增加延迟、成本、提示注入面和重复动作。返回机器生成的字段路径、错误代码与允许范围，不回显不可信大段文本；限制重试次数。第一次校验前绝不执行副作用，重试复用请求 ID 和幂等键。 纯语法失败：约束重生或一次修复。 缺必填且可向用户询问：返回 ask_clarification。 事实/业务冲突：重新取权威数据，不让模型猜。 权限不足：禁止执行，必要时升级人工。 同类连续失败：降级更简单 schema 或确定性表单。 记录首次通过率、每字段错误、修复后通过、最终任务失败、重试次数和额外 p95。

### 4.9.7 版本演进是一项分布式契约

生产者升级 schema 后，旧消费者为什么可能静默误读？。 契约迁移输入旧新 schema、生产者消费者版本和历史 trace，输出兼容矩阵与 expand/contract 发布计划。先让消费者接受新旧，再让生产者发送新，最后退役旧；新增枚举和严格额外字段都可能破坏旧逻辑，不能仅按“新增”判断兼容。 schema 需要版本号和兼容政策。新增可选字段通常向后兼容，但消费者若拒绝额外字段则不是；新增枚举值会让旧 switch 落入错误默认分支；删除/改类型是破坏性变化。采用 expand/contract：先让消费者接受新旧，再让生产者发送新，最后移除旧。 变更； 典型风险； 迁移。 新增可选字段； 严格消费者拒绝； 先更新消费者。 新增枚举值； 未知值误执行； 显式 unknown 分支。 字段改名/类型； 破坏读写； 双写/双读后退役。 收紧范围； 旧数据不再合法； 迁移数据并分版本校验。 。 提示、schema、约束编译器和消费者版本要一起记录；回放旧 trace 才能复现当时规则。

### 4.9.8 安全执行不信任模型提供的身份与工具名

schema 已把 action 限定为 refund，为什么提示注入仍可能造成伤害？。 安全执行输入合法参数、认证主体、工具白名单、策略与审批状态，输出以最小权限执行或拒绝。模型提供的身份、工具名和自由文本都不可信，服务器重新鉴权并限制金额与对象；结构化字符串仍可携带注入载荷，消费者必须按目标上下文转义。 攻击者可诱导模型选择语法允许但不合适的动作或金额。工具注册表只暴露当前流程允许的能力；服务器从会话认证取得 user/tenant，不接受模型自报；参数做对象级授权、速率、金额、目的与审批校验。高风险动作先生成计划，由确定性策略门和人工确认后提交。 自由文本字段可能携带 SQL、HTML 或给下一个 agent 的注入，消费者必须按上下文转义并标记不可信。结构化不等于净化；它只是把攻击载荷放进了一个合法字符串。 Confused deputy： 模型可以代表用户建议动作，但不能继承服务账号全部权限。每次工具调用都以最小权限和当前主体重新鉴权。

### 4.9.9 评测应沿整条契约定位失败

“结构化输出成功率 99.9%”还缺哪些能决定上线的数字？。 端到端评测输入模型输出、验证日志、工具结果和业务后果，输出语法、schema、字段、事实、权限、幂等、任务质量、延迟与成本指标。错误预算按最终损失分级，单次越权不能被大量无害格式成功平均掉。 按层报告：完整语法率、schema 首次通过、死路、字段级错误、业务/事实通过、权限拦截、工具成功、重复副作用、最终任务质量、额外延迟和成本。用断流、Unicode、超长数组、未知枚举、旧消费者、新政策和恶意自由文本回归。 错误预算要基于最终后果。大量无害格式重试和一次越权退款不能被同一平均失败率对待；后者设独立硬门槛和即时回滚。 诊断顺序： 先问输出是否完整，再问形状是否正确，再问事实/关系是否成立，最后问当前主体是否能安全执行。

### 4.9.10 常见误区与概念依赖

结构化输出的价值是建立可拒绝的边界，而不是让模型输出天然可信。 误区； 更准确的理解。 JSON mode 等于 schema； 前者常只保证语法，后者约束字段和类型。 schema 通过等于内容正确； 事实和跨字段不变量需外部验证。 自动修复总比失败好； 修复可能改语义，应有限且可证明。 加字段总是兼容； 严格消费者和枚举分支可能破坏。 合法参数就有权执行； 执行层仍需主体鉴权、策略和幂等。 。 层级； 概念依赖与延伸学习。 先修； JSON/Schema、tokenization、API 契约。 本页核心 ； 最小 schema、分层验证、恢复、版本迁移。 生成机制； 约束解码、采样参数、流式输出。 执行安全； 工具调用、身份权限、工作流编排与应用评测。 。

### 4.9.11 把因果链连起来

这个概念怎样从问题一路连接到可验证的实践？。 定义最小版本化 schema。 生成时约束并等待完整接受态。 服务端重新解析与 schema 校验。 验证事实和跨字段业务不变量。 以当前主体鉴权后幂等执行。 按失败层记录并有限恢复/回滚。

### 4.9.12 误区与自测

你能否不用背术语，解释它的机制、边界与验证方法？。 JSON 语法通过与 schema 通过差什么？。 amount=120 为什么示例中不能执行？。 为什么约束生成后仍要校验？。 新增枚举为何可能破坏旧消费者？。 失败重试如何避免重复退款？。 假设“结构化输出：把概率文本接入确定性软件契约”在离线示例上表现正常、上线后核心结果却下降，你会怎样按输入、内部变换、输出反馈和适用边界定位问题？。 。 参考答案 前者只保证可解析，后者还检查字段、类型、枚举和范围。 虽在通用范围内，但订单剩余可退额只有 80，且当前角色无批准权限。 防实现/版本错配，并处理业务、事实和权限等文法无法表达的条件。 旧 switch 可能没有安全 unknown 分支。 校验全部通过前不执行，执行与重试使用同一幂等键。 先保存同一失败样本及环境，确认输入、权限和前置条件没有漂移；再记录关键中间状态，检查机制是否按本页描述完成变换；随后把原始输出与独立指标、人工终验对照；最后用边界样例和对照实验复测。只有定位到首次偏离预期的环节，才能判断应修改数据、机制、评测还是使用边界。

## 4.10 流式输出：把一次生成变成可取消、可恢复的事件协议（streaming）

### 4.10.1 流式改善的是等待形状，不是总工作量

用户 400ms 看见第一个字，为什么服务器仍可能计算 8 秒？。 流式输出输入正在生成的 token 和请求生命周期，输出逐步可见的增量事件及最终状态。它提前传送已产生内容，改善首字和取消体验，却不减少生成完整序列所需的模型工作；前缀可见不能解释为请求已经完成或通过校验。 非流式等完整答案生成后一次返回；流式在 token 或文本增量可用时立即发送。用户可提前阅读、取消或看到工具进度，但模型仍需生成全部 token，网络事件和前端渲染还增加额外开销。 因此分别测首字时间 TTFT、token 间隔 TPOT、完整时间 E2E 和取消生效时间。只宣传“首字快”可能掩盖最终更慢或答案半途失败。 核心边界： 可见不等于完成，前缀合法不等于最终结果有效，客户端断开也不等于上游计算已停止。

### 4.10.2 token、字节块、字符和事件不是同一边界

为什么一个网络 chunk 不能直接当成一个字符或一个模型 token？。 增量解码输入模型 token、UTF-8 字节块和协议帧，输出完整字符与类型化事件。tokenizer、字符编码、网络切块和应用协议各自决定边界，客户端必须跨块保留解码状态；TCP chunk 只表示一次传输分片，不能作为 JSON 或业务提交边界。 模型产生 token，服务端把 token 解码成 UTF-8 字节，再按网络和缓冲策略切块；一个中文字符可能跨字节块，一个 token 可能含多个字符，JSON 转义也可跨事件。客户端必须用增量 UTF-8 解码器，并以协议事件而非 TCP chunk 解析。 单位； 由谁决定； 可否作为提交边界。 token； 模型 tokenizer； 否，可能半个词/结构。 字节 chunk； 运行时/网络； 否，可能拆 UTF-8。 字符/文本 delta； 增量解码器； 只适合展示。 协议事件； 应用 schema； 按事件语义判断。 done + 校验； 业务层； 可成为最终提交边界。 。

### 4.10.3 事件协议要表达生命周期而非只发字符串

连接中途失败时，客户端怎样区分正常结束、取消和错误？。 事件协议输入请求状态与文本、工具、使用量和错误增量，输出带 request id、sequence、版本和终态的事件流。客户端按序去重和状态机处理，只有显式 done 且最终校验通过才完成；EOF 只表示连接关闭，不能推断正常结束。 定义 start 、 text_delta 、 tool_delta 、 tool_complete 、 usage 、 error 、 cancelled 、 done 。每条流有 request id、递增 sequence、协议版本和可选 event id；只有 done 且最终校验通过才标记 completed。 SSE 简单、自动重连但单向；WebSocket 双向且状态复杂；HTTP 分块通用但需自定义帧。选择取决于交互，不改变必须明确帧边界、顺序、幂等与终态。 EOF 不是 done。 连接关闭可能来自网络、代理、服务崩溃或用户取消，不能把已收到前缀自动当完整答案。

### 4.10.4 运行示例：一次 40-token 回答的时间线

排队 120ms、预填充 280ms、每 token 50ms，用户何时看见、何时完成？。 案例输入排队、预填充、token 数和 TPOT，输出 TTFT、完整时间与取消后浪费。首字约 400ms，四十 token 完整约 2.35 到 2.4 秒；一秒取消时约显示十二个 token。只有取消信号传播到模型服务，剩余二十八个 token 的计算才会停止。 图示：流式请求的排队、预填充、首 token、增量、取消和完成时间线。 图 1 流式把 2.4 秒的单次等待改成 0.4 秒开始阅读，但完整计算并未消失。 公式：首 token 时间 TTFT 约等于排队 Q 加预填充 P 加首步解码 D；完成时间 E 约等于 TTFT 加 N 减一乘每 token 时间 TPOT，再加传输渲染 X。 TTFT 是从请求发出到首 token 可见的时间， Q 是排队时间， P 是处理输入前缀的预填充时间， D 是首步解码时间； E 是完整完成时间， N 是输出 token 总数， TPOT 是首 token 之后每个 token 的平均解码间隔， X 是网络传输与前端渲染耗时。它是容量规划近似，真实服务还会受批处理和事件抖动影响。 N=40、TPOT=50ms 时完成约 400+39×50=2350ms，再加传输接近 2.4s。若用户在 1s 取消，已解码约 (1000−400)/50=12 token；若取消未传到模型服务，剩余 28 token 仍浪费成本。

### 4.10.5 背压是慢消费者对快生产者的反馈

浏览器每秒只能渲染 20 次，服务器每秒发 100 个 delta，会发生什么？。 背压控制输入生产速率、消费速率和缓冲水位，输出批量渲染、暂停、合并或取消决策。慢消费者必须把压力逐层传回网关和上游；若上游不能暂停，就用有界队列并超限取消。文本可合并，工具事件则必须保持顺序与语义。 缓冲不断增长，内存和延迟上升，最终断连。客户端可按动画帧或词组批量渲染；中间层设置高水位、暂停读取或合并文本 delta；服务端限制每流缓冲并在超限时取消。 背压要逐层传播：DOM 慢→客户端读取慢→网关发送受阻→应用暂停读取上游；若模型 API 不支持暂停，至少限制缓冲并取消。工具事件不能与文本随意合并，必须保持事件语义。 症状； 原因； 控制。 前端卡顿； 每 token 重排； 16–50ms 批量渲染。 内存增长； 无界队列； 高水位和取消。 延迟越来越大； 代理缓冲/慢客户端； 禁缓冲、心跳、流控。 事件乱序； 并发通道合并； sequence 与单写者。 。

### 4.10.6 取消、超时和重连都需要幂等语义

用户点停止后，为什么工具仍可能完成退款？。 取消与重连输入 request id、sequence、取消信号、幂等键和动作日志，输出已取消、已完成、未知或可重放状态。取消须传播到模型与工具，超时后先查询动作状态再重试；前端停止显示不等于事务撤销，已提交副作用需要补偿或人工处理。 取消信号可能只停止前端显示，没有中止模型或已发出的工具请求。每层接收 AbortSignal/取消 token，工具动作前检查当前状态；不可逆动作使用幂等键和提交日志。超时后结果未知，重试必须先查询动作状态。 SSE 自动重连可携 Last-Event-ID，服务端从短期事件日志重放；客户端按 request id + sequence 去重。若无法重放，明确启动新请求，不把两条回答拼接。连接恢复也不能重复执行 tool_complete。 展示取消不等于事务撤销。 已提交副作用需补偿或人工处理，协议必须如实呈现状态。

### 4.10.7 结构化输出必须缓冲到接受态

工具参数已经流出 {"amount":12，为什么不能提前执行？。 结构缓冲输入 tool_call_delta，输出完整接受态并经 schema、事实和权限校验的参数。数字、字符串和对象前缀都可能继续变化，客户端只能组装和预览；半截回答必须标记 interrupted，不能混入完整答案的训练或评测。 数字还可能变成 120，字符串可能未闭合，对象也可能追加字段。结构化 delta 可用于预览或进度，但执行必须等待完整对象、schema、事实和权限校验。服务可发送专门 tool_call_delta，客户端只组装，不解释半截 JSON。 同理，流式正文中的早期引用可能在后文被否定；持久化最终答案应存原始事件与完成状态，半截回答标记 interrupted，不与完整回答混用训练或评测。 安全审查有时间边界。 只检查单个 chunk 会漏跨块攻击；等全文再检查又失去实时性。可做增量缓冲审查，并对高风险内容延迟展示。

### 4.10.8 安全、Markdown 与 UI 都有增量陷阱

单个 delta 看起来无害，拼接后为什么可能形成脚本、链接或敏感信息？。 增量安全渲染输入跨块文本和内容风险策略，输出纯文本累积、安全 Markdown/HTML 和审核后的展示单元。扫描器维护跨块窗口，前端不能逐块 innerHTML；高风险领域可延迟到句段或全文审核，流式并非所有场景默认更好。 Markdown 链接、HTML 标签、代码围栏和敏感模式可跨事件。先把 delta 当纯文本累积，使用安全渲染器；不要将未完成 HTML 注入 DOM。安全扫描维护跨块窗口，工具和外部文档内容标记为不可信。 用户看到的前缀会影响行为，即使最终系统删除或修正。医疗、金融和高风险指导可先缓冲到句子/段落或完整审查；流式不是所有场景默认更好。无障碍读屏还需要避免每个 token 触发朗读。 风险； 错误做法； 安全做法。 XSS/Markdown； 逐块 innerHTML； 纯文本累积后安全渲染。 跨块敏感词； 每块独立扫描； 滑动窗口/句级缓冲。 高风险误导； 立即展示未审查前缀； 延迟到审核单元。 读屏噪声； token 级 aria 更新； 语义块与节流。 。

### 4.10.9 评测应覆盖完成、取消和故障路径

平均 TTFT 很漂亮，还缺哪些指标才能证明流式可靠？。 流式评测输入端到端事件日志、网络设备并发切片和故障注入，输出 TTFT、TPOT、完成、取消传播、浪费 token、恢复、缓冲、帧率和最终质量。成功必须同时证明安全增量及时、取消节省工作、done 后提交且故障不伪装完成。 测 p50/p95/p99 TTFT、TPOT、完成时间、事件间隙、取消传播延迟、取消后浪费 token、中断率、重连恢复率、重复事件、缓冲峰值、前端帧率和最终质量。按输出长度、网络、代理、设备和并发切片。 故障注入：UTF-8 跨块、事件截断、代理缓冲、乱序、重复、模型错误、工具超时、客户端断网与服务器重启。验收最终状态和副作用，而不只看文本是否“差不多显示”。 成功定义： 用户及时看到安全增量；取消确实节省后续工作；完整结果仅在 done+验证后提交；故障不会静默伪装成完成。

### 4.10.10 常见误区与概念依赖

流式是一种状态协议与资源控制，不是把字符串切碎这么简单。 误区； 更准确的理解。 流式减少总生成计算； 主要改善首字和可取消性，完整 token 仍要算。 一个 chunk 就是一个 token； 网络、字节、字符和 token 边界不同。 断连等于正常完成； 只有显式 done 与最终校验代表完成。 点停止就停止成本； 取消必须传播到上游和工具。 结构前缀合法即可执行； 需接受态、schema、事实和权限全部通过。 。 层级； 概念依赖与延伸学习。 先修； tokenization、自回归解码、HTTP/SSE、UTF-8。 本页核心 ； 事件协议、TTFT/TPOT、背压、取消、重连与提交。 输出； 结构化输出、约束解码、工具调用。 服务； 推理优化、部署、可观测性与安全护栏。 。

这个概念怎样从问题一路连接到可验证的实践？。 为流分配 request id 与序号。 增量解码 token/字节为类型化事件。 客户端按背压安全渲染。 取消沿链路传播并保护副作用。 仅在 done+校验后提交最终结果。 用故障注入和端到端指标回归。

### 4.10.12 误区与自测

你能否不用背术语，解释它的机制、边界与验证方法？。 40-token 示例的 TTFT 和完成时间约多少？。 为什么网络 chunk 不能直接 JSON.parse？。 EOF 为什么不是完成？。 背压应如何处理？。 工具参数何时可执行？。 假设“流式输出：把一次生成变成可取消、可恢复的事件协议”在离线示例上表现正常、上线后核心结果却下降，你会怎样按输入、内部变换、输出反馈和适用边界定位问题？。 。 参考答案 TTFT 约 400ms，完整约 2.35–2.4s。 它可能拆开 UTF-8、转义或结构，必须按事件增量解码。 可能是断网、崩溃、取消或代理关闭，需显式 done。 批量渲染、有界缓冲、暂停/合并读取并向上游传播或取消。 完整接受态后通过 schema、事实、业务和权限校验时。 先保存同一失败样本及环境，确认输入、权限和前置条件没有漂移；再记录关键中间状态，检查机制是否按本页描述完成变换；随后把原始输出与独立指标、人工终验对照；最后用边界样例和对照实验复测。只有定位到首次偏离预期的环节，才能判断应修改数据、机制、评测还是使用边界。

## 4.11 响应预填充：让模型从一个给定的答案前缀继续（prefilling）

### 4.11.1 模型不是重新回答，而是继续已开始的答案

assistant 消息已包含 {"action":"，模型接下来看到的任务发生了什么？。 模型把该文本放在 assistant 侧历史中，预测其后的 next token。开场寒暄、Markdown 围栏或其他结构因与前缀不连续而概率下降，因此短前缀常比长篇“不要寒暄”更直接。 前缀也会锁定假设。预填“退款已批准，因为”会促使模型为既定结论找理由，即使订单不合格；它不是中性格式技巧。 使用原则： 只预填你能独立保证正确且希望固定的最小文本；其余交给约束与校验。 响应预填充输入用户/系统上下文和一段已确认的 assistant 前缀，输出从该前缀之后继续的 token 序列。前缀被放进条件上下文，模型不是重新选择它；结果只表示续写与前缀连贯，不证明前缀中的事实正确。只应预填可独立保证正确的最小骨架。

### 4.11.2 它改变条件，不改变参数

同一 prompt 加一个 assistant prefix，概率分布为什么会变化？。 公式：给定上下文和前缀时完整续写的条件概率。 x 是用户与系统上下文，p 是已提供的回答前缀。模型权重不变，但每一步注意到 p，所以续写分布改变。前缀越具体，可能路径越少；若 p 与模型模板或任务冲突，后续会在一个低概率区域勉强续写。 预填一个“{”只承诺 JSON 风格开头；预填完整 {"action":"refund" 已经替模型做出业务决定。二者风险完全不同。 概率偏置不是硬保证。 模型仍可能闭合对象后追加说明、漏字段或生成事实错误。 条件生成输入上下文 x、前缀 p 和先前续写，输出下一 token 的概率分布与最终续写。模型权重不变，注意力每步都读取 p，因此事件空间和概率改变；更具体的前缀会减少可选路径，但冲突或错误前缀会把续写锚在错误区域。

### 4.11.3 三种相似名称必须分开

response prefill、inference prefill 和 prompt caching 到底各是什么？。 概念； 对象； 目的； 是否改变输出条件。 响应预填充； assistant 文本前缀； 引导开头/结构； 是。 输入 prefill 阶段； 全部输入 token； 计算输入 KV； 不是产品控制，属推理计算。 提示缓存； 共同输入前缀 KV； 跨请求复用计算； 正确实现下否。 约束解码； 每步合法 token 集； 保证形式语言； 是，且为硬屏蔽。 。 “预填充加速”通常指输入计算；本页的“响应预填充”是把答案开头交给模型续写，概念和性能目标不同。 概念消歧输入一个名为 prefill 或 cache 的功能及其作用对象，输出“响应前缀、输入计算、缓存复用或硬约束”中的一种分类。先看它处理 assistant 文本、输入 token、KV 结果还是合法 token 集，再判断它改变内容条件还是只减少计算。名称相似不能推出语义或接口兼容，实际行为仍以服务文档和契约测试为准。

### 4.11.4 运行示例：一个字符怎样重新分配首步概率

无前缀时模型最爱说“当然”，预填 { 后会怎样？。 图示：无响应前缀与预填左花括号后首个续写 token 概率变化。 图 1 两个分布的事件空间不同：预填的“{”已不是候选，而是条件上下文的一部分。 不能把 .25→.60 说成同一 token 概率提升；无前缀分布预测答案首 token，预填后分布预测花括号之后的 token。正确评测是比较完整输出的结构通过率、内容质量与失败类型。 方案； 首次 JSON 语法； Schema； 事实正确。 仅提示； 94%； 86%； 80%。 预填 {； 98%； 89%； 80%。 约束解码； 100%； 99%*； 80%。 。 *取决于支持范围。示例强调前两层改善不会自动抬高事实正确率。 这个案例输入空前缀或“{”两种条件以及各自的首步候选，输出两个不同位置的概率分布和完整结构指标。“{”的 .25 与“action”的 .60 不是同一事件，不能说概率从 .25 提升到 .60；要解释的是完整输出的结构、事实与失败类型。

### 4.11.5 适合固定开场，不适合替模型做结论

哪些前缀是低风险格式骨架，哪些已经偷偷注入答案？。 较适合：JSON 的开括号、固定标题、已验证的代码前文、语言/语气开场、枚举标签的共同前缀。高风险：成功/失败结论、用户身份、金额、引文、工具已执行状态和任何未经外部验证的事实。 前缀； 风险； 替代。 {； 低，但不能保完整 JSON； schema 约束。 “根据政策证据：”； 若证据实际缺失会误导； 条件模板/拒答。 “退款已批准”； 锚定未经授权结论； 工具确认后由服务器填。 已有代码文件； 旧代码可能含漏洞/注入； 版本与测试校验。 。 前缀选择输入拟固定文本、证据状态和任务风险，输出中性骨架或“不使用预填”的决定。只固定 JSON 开括号、标题或已验证代码；结论、身份、金额、引文和工具状态必须由权威系统确认。前缀越长，越可能锚定未知事实。

### 4.11.6 API 模板、拼接与停止规则会制造隐藏错误

为什么有些服务不允许最后一条 assistant 消息非空？。 聊天模板和安全策略由服务实现；有的 API 原生支持 assistant prefix，有的会拒绝、自动闭合或把它当历史回答。必须查接口并用真实模型测试：返回 delta 是否含前缀，计费是否包含，流式首事件从哪里开始。 客户端只拼接一次前缀，按 UTF-8 增量解码；停止串可能跨 token/事件，不能简单裁字符串；若前缀以半个转义或不完整 Unicode 结尾，会产生不可恢复路径。日志记录前缀版本但避免敏感原文。 模板重复： 服务若把前缀回显，客户端再手动前置会得到 {{ 或重复标题；契约测试必须覆盖。 API 接入输入服务能力、assistant 前缀、流式事件和停止规则，输出正确拼接的一份完整结果。服务决定前缀是续写条件、历史答案还是非法消息，客户端再按契约拼接、解码和停止；回显或重复开头说明契约理解有误。半个转义、不完整 Unicode 和未经实测的接口都不适合直接上线。

### 4.11.7 错误前缀会造成锚定和“合理化”

为什么强迫答案以“是”开头，会让模型更自信地编理由？。 自回归模型要生成与既有前缀连贯的后续。即使内部证据倾向“否”，已给定的“是，因为”也会让反驳变得语言上突兀，于是模型更可能搜寻支持性理由。这是条件生成的自然结果，不是模型主动撒谎。 用正反对照测试：同一问题分别预填“是”“否”和空前缀，观察结论敏感度；若事实随前缀翻转，说明系统在用格式控制替代证据。高风险任务只预填中性骨架。 安全绕过风险： 预填可能把模型置于安全模板不常见的状态；供应商允许的前缀范围与安全行为要单独红队。 锚定测试输入同一问题的空前缀、“是”和“否”三个版本，输出结论变化和证据变化。模型按连贯性续写已有开头，所以理由随前缀翻转表示格式正在替代证据，而不是答案更可靠。高风险任务只能使用中性骨架，并需单独红队。

### 4.11.8 预填不能替代完整约束和业务验证

输出已经以 { 开头，仍要经过哪些门？。 等待完整输出和明确结束，断流不是完成。 解析 JSON 并做 schema 校验。 验证金额、日期、引用与跨字段不变量。 对实体查权威数据库，未知则询问。 工具执行按当前主体重新鉴权和幂等提交。 结构失败有限重试；同类重复则用约束解码或表单。 若硬结构是核心要求，直接使用受支持的约束解码，比不断加长前缀和修复提示更可靠。预填适合作为兼容性或体验优化，不应被包装成保证。 业务验证输入完整模型输出、schema、权威数据与当前权限，输出可接受、拒绝或重新询问。系统依次检查完整性、结构、字段事实、实体权限和幂等提交；通过 JSON 解析只说明形式正确，不说明事实或动作获准。硬结构应优先使用约束解码，预填只作兼容或体验优化。

### 4.11.9 评测要和无预填基线配对

结构通过率上升后，怎样发现事实质量、拒答和安全被前缀伤害？。 同一批输入配对运行空前缀与候选前缀，测首次语法/schema、字段准确、任务成功、事实、拒答、越权、长度、TTFT 和 token 成本；按缺信息、高风险、语言和长输入切片。 记录“前缀反转率”：给相反结论前缀时答案是否无证据翻转；故障测试断流、回显、重复拼接、Unicode、停止串和接口升级。只有格式改善且内容/风险不退化才可采用。 成功标准： 前缀减少低价值开场或格式偏离，但不替模型决定未知事实，也不让下游降低校验。 配对评测输入相同样本的空前缀与候选前缀结果，输出格式、事实、拒答、安全、延迟和成本差异。按相同切片逐项比较并注入断流、回显和接口升级故障；只有格式改善且内容与风险不退化才可采用。模型、API 或模板版本变化后必须重新评测。

### 4.11.10 常见误区与概念依赖

响应预填充是条件控制，强而简单，但也正因简单而容易被误用。 误区； 更准确的理解。 预填会修改模型权重； 只改变当前上下文条件。 预填 { 保证 JSON； 只固定开头，后续仍可偏离或截断。 与 prompt cache 相同； 一个引导输出，一个复用输入 KV 计算。 前缀越长控制越好； 越可能锚定错误事实和降低可恢复性。 服务都支持同一语义； 聊天模板、回显和安全行为因 API 而异。 。 层级； 概念依赖与延伸学习。 先修； 自回归生成、条件概率、聊天模板。 本页核心 ； assistant prefix、锚定、拼接、停止与配对评测。 硬格式； 结构化输出、约束解码、采样参数。 性能区别； 提示缓存、输入 prefill、流式输出与推理优化。 。

### 4.11.11 把因果链连起来

这个概念怎样从问题一路连接到可验证的实践？。 选择可独立保证正确的最小前缀。 按真实 API 契约发送 assistant prefix。 模型条件于前缀续写。 正确拼接/停止并等待完整结果。 做 schema/事实/权限验证。 与空前缀配对评测并监控锚定。

你能否不用背术语，解释它的机制、边界与验证方法？。 响应预填充改模型权重吗？。 为什么图中 .25 和 .60 不能直接比较成概率提升？。 响应预填充与提示缓存差什么？。 哪些内容不应预填？。 怎样检测锚定？。 假设“响应预填充：让模型从一个给定的答案前缀继续”在离线示例上表现正常、上线后核心结果却下降，你会怎样按输入、内部变换、输出反馈和适用边界定位问题？。 。 参考答案 不改，只把前缀加入当前条件上下文。 它们对应不同预测位置和事件空间。 前者引导输出内容，后者复用相同输入前缀的 KV 计算。 未经验证的结论、身份、金额、引用和工具状态。 对同一输入用空、正反结论前缀做配对，看是否无证据翻转。 先保存同一失败样本及环境，确认输入、权限和前置条件没有漂移；再记录关键中间状态，检查机制是否按本页描述完成变换；随后把原始输出与独立指标、人工终验对照；最后用边界样例和对照实验复测。只有定位到首次偏离预期的环节，才能判断应修改数据、机制、评测还是使用边界。

## 4.12 提示缓存：复用共同前缀的 KV 计算（prompt-caching）

### 4.12.1 重复计算发生在输入预填充

每轮 Agent 都携带相同系统规则和工具 schema，GPU 为什么还要从头处理？。 自回归服务先并行处理输入 token，产生每层 K/V，再逐 token 解码。相邻请求常共享系统提示、工具定义和早期会话；跨请求前缀缓存保存这些中间张量，让新请求从共同前缀末尾继续预填充。 缓存内容不是自然语言答案，也不是语义检索结果。它只对特定模型、tokenizer、权重/适配器和位置配置下的确切 token 前缀有效。 主要收益： 减少输入计算、降低 TTFT、释放预填充吞吐；长输出的逐 token 解码仍原样发生。 提示缓存输入模型配置和多个请求共享的精确 token 前缀，输出可供后续请求复用的中间 KV 状态。服务先查找最长可用前缀，再只计算新后缀；命中表示省去了部分输入计算，不表示答案被缓存或输出一定正确。它只适用于模型、tokenizer、位置配置和安全域一致的请求。

### 4.12.2 三种缓存不要混淆

请求内 KV cache、跨请求提示缓存和回答缓存分别复用了什么？。 机制； 复用范围； 键/条件； 改变的阶段。 请求内 KV cache； 同一次生成历史 token； 当前序列； 逐 token 解码。 跨请求前缀缓存； 不同请求共同开头； 模型+精确 token 前缀； 输入预填充。 响应/语义缓存； 相同或近似问题答案； 请求/语义+版本； 跳过部分或全部生成。 应用数据缓存； 检索/工具结果； 查询+权限+新鲜度； 外部组件。 。 后两者可能返回陈旧或越权内容，正确性风险远高于纯计算状态复用。不能用“缓存命中率”一个数字混报。 缓存分类输入“被保存的对象、复用范围和跳过的阶段”，输出请求内 KV、跨请求前缀、回答或应用数据缓存之一。看它复用当前生成历史、共同输入状态、最终答案还是工具结果，就能解释收益与正确性风险；这些机制不能共享一个命中率口径。

### 4.12.3 只有连续共同 token 前缀可直接复用

两份提示含相同 8000 token 文档，顺序不同为什么仍可能命中为零？。 因果注意力中位置 i 的表示依赖此前全部 token。中间插入时间戳会改变后续位置与上下文，因此从分叉点后的 KV 不能直接复用。 公式：两条序列的最长共同前缀。 语义相同不代表 token 相同：JSON 字段顺序、空格、Unicode 规范化、模板版本和工具排序都可改变 token 序列。某些 radix-tree 系统能在许多前缀间寻找最长命中，但仍遵守精确 token 前缀条件。 不要把动态值放最前。 请求 ID、当前时间或用户问题在开头，会让其后所有稳定内容失去复用。 最长共同前缀计算输入两条 token 序列 A、B，输出从首 token 起连续相同的长度 ℓ。系统逐 token 比较，第一次分叉就停止复用；LCP 较长只说明计算状态可复用，不代表两份提示语义更相近。任何影响 token、位置或模型状态的变化都会终止命中。

### 4.12.4 运行示例：12k 输入里究竟省了多少

系统规则 2k、工具 3k、共享政策 5k、会话 1k、当前问题 1k，怎样布局并估算？。 图示：十二千 token 提示按稳定性排序形成十千 token 缓存命中与两千 token 新后缀。 图 1 按稳定性排序把大段共享内容放在前，动态历史与问题放后，最长共同前缀才有机会达到 10k。 公式：期望避免处理的输入 token 数。 若无缓存 TTFT 中预填充 600ms，命中后 10k/12k 计算可省但有 60ms 查找/搬运，粗略命中请求约 600×(10/12)−60=440ms ；全流量期望约 308ms。真实注意力成本非线性，必须实测。 案例输入 12k token 的稳定与动态片段、70% 命中率和预填充延迟，输出 10k 命中长度、平均节省 7k token 及粗略延迟收益。h 是命中率，L 是命中的 token 长度；先按稳定性排布，再用 h×L 求平均避免量并扣除查找搬运。440ms 和 308ms 是给定假设下的估算，真实注意力成本必须实测。

### 4.12.5 提示布局与规范化决定命中

怎样组织上下文既提高复用，又不破坏语义和权限？。 最前放模型/应用版本稳定的系统规则。 随后放排序固定的工具 schema 和共享少样本。 再放版本化公共文档或政策。 后部放会话历史、检索证据和当前输入。 时间戳、随机 nonce、trace id 留在不参与模型的元数据或末尾。 确定性序列化对象，固定字段与工具顺序、空白和 Unicode 规范。不能为了命中把用户特定权限或秘密提升为共享前缀；性能优化服从数据边界。 语义顺序也重要。 把安全规则移到前面有利缓存，但若模板语义改变必须重新评测，不能只按命中率重排。 提示布局输入各片段的稳定性、权限域和语义顺序，输出稳定公共内容在前、动态私有内容在后的序列。确定性序列化提高精确前缀复用，但结果必须同时保持安全规则含义和租户隔离。不能为提高命中率移动或共享本应私有的内容。

### 4.12.6 KV 容量随层、token 和并发增长

为什么 10k token 前缀不能无限常驻 GPU？。 粗略 KV 字节数与 2×层数×KV头数×头维×token数×每元素字节 成正比；2 表示 K 与 V。以 32 层、8 KV 头、128 维、FP16、10k token：。 公式：KV 缓存字节数估算。 不同架构、张量并行和量化会改变数字，但规模说明缓存会与模型权重和活跃请求争显存。使用分块/PagedAttention、前缀树、TTL、LRU 或按“节省计算/占用字节”价值淘汰；搬到 CPU/远端会增加延迟与带宽。 策略； 优点； 代价。 GPU 常驻； 命中最快； 昂贵、挤压并发。 CPU/远端层级； 容量大； 搬运可能超过重算。 TTL/LRU； 简单； 不理解前缀价值。 价值感知； 保留长且热门前缀； 估值和实现复杂。 。 容量规划输入层数 Nlayer、KV 头数 NKVhead、头维 d、token 数 Ntoken、每元素字节 b 和并发，输出 KV 字节数 MKV 与存储层级选择。K 与 V 各保存一份，所以乘二；估算占用用于比较 GPU 驻留、搬运与重算，但架构、并行和量化不同会改变实际值。

### 4.12.7 缓存键和失效必须包含模型语义版本

文本前缀没变，换了 LoRA 或 RoPE 配置还能复用吗？。 不能假定。权重/适配器、tokenizer、位置编码、注意力实现、精度、模型模板和可能影响隐藏状态的推理配置变化都需进入 namespace 或使缓存失效。提示、工具和政策版本变更也改变 token。 缓存键通常包含模型快照、适配器、token 序列哈希、租户/安全域与位置起点；命中后可抽样重算对比，捕获实现错误。滚动发布时新旧缓存隔离，不能让 v42 读取 v41 状态。 缓存污染会静默传播。 错误状态被高频复用，比单次推理错误影响更大；需校验哈希、版本和快速全量失效开关。 失效设计输入模型快照、适配器、tokenizer、位置配置、模板和租户域，输出缓存命名空间、键和失效动作。只要其中一项改变，同一文本也可能产生不同 KV；命中后抽样重算可发现污染。版本字段不完整时必须拒绝复用，而不是冒险读旧状态。

### 4.12.8 隐私、租户隔离与侧信道

KV 不是可读文本，为什么仍属于敏感数据状态？。 KV 是输入的派生表示，可能包含敏感信息；跨租户共享还可能通过命中延迟推测某前缀是否存在，或因键缺少权限字段复用不应共享内容。默认按租户/组织/数据分类隔离，公共系统前缀与用户私有历史分开。 设置保留期、加密、访问审计和删除传播；日志只记录前缀哈希/长度而非原文。共享公共政策也要确认所有租户有相同版本和访问权。服务供应商缓存政策属于数据处理协议的一部分。 不要用用户可控前缀直接寻址共享缓存。 需要域隔离、完整哈希和长度/配额限制，防碰撞、探测与资源耗尽。 安全治理输入前缀的数据分类、租户、保留期和访问权，输出隔离域、加密、审计与删除策略。KV 虽不是可读原文，仍是输入的派生数据，且命中时间可能泄露前缀是否存在。跨租户共享只限真正公共且权限一致的版本化内容。

### 4.12.9 评测要证明净收益而非命中率

命中率从 40% 升到 80%，为什么 TTFT 可能没有改善？。 可能只命中很短前缀，查找/跨机搬运超过重算，或路由到缓存节点增加排队。测请求级命中长度分布、节省 prefill token/时间、查找/搬运、GPU KV 占用、驱逐、TTFT p50/p95/p99、吞吐、费用和质量。 A/B 必须保持提示语义和路由负载可比；按租户、长度和并发切片。故障测试版本错配、节点丢失、缓存雪崩、冷启动、删除和跨租户访问。 价值指标： 每 GB·小时缓存带来的 TTFT/计算节省，以及在 SLO 下增加的可服务吞吐，比裸命中率更接近决策。 缓存评测输入请求级命中长度、计算与搬运时间、显存、延迟、吞吐和质量，输出按租户、长度、并发切片的净收益。A/B 固定提示语义与路由负载，并测试错版本、冷启动和雪崩；命中率升高但 TTFT 不降，通常说明命中太短或查找、搬运、排队抵消了收益。

### 4.12.10 常见误区与概念依赖

提示缓存是带版本和安全域的计算状态复用，不是“记住答案”。 误区； 更准确的理解。 缓存保存模型答案； 提示缓存保存共同前缀的层级 KV 状态。 包含相同文本就能命中； 必须从首 token 连续相同且配置一致。 命中会减少输出计算； 主要省输入 prefill，新后缀与 decode 仍需算。 命中率越高越好； 还要看长度、搬运、驻留和排队净收益。 KV 不可读所以不敏感； 它是输入派生数据，需隔离、保留和删除治理。 。 层级； 概念依赖与延伸学习。 先修； self-attention、KV cache、tokenization、prefill/decode。 本页核心 ； LCP、前缀布局、KV 容量、路由亲和、失效隔离。 性能； 推理优化、部署、流式输出。 上下文； 上下文工程、响应预填充、隐私与可观测性。 。

## 4.13 上下文压缩：在 token 预算内保留决策所需信息（context-compaction）

### 4.13.1 为什么不能只保最近消息

早期的一句关键约束为何可能比最近十轮更重要？。 时间近不等于任务价值。直接滑窗会丢目标和决定；全量保留又增加成本、冲突和中间迷失。压缩需按职责而非仅按时间选择。 上下文压缩输入完整历史、当前任务和 token 预算，输出仍足以支持下一步决策的精简上下文。它按任务价值而非消息时间选择信息；结果变短只代表装入更少 token，不代表关键事实都保住。目标、权限和验收条件无法确认时不得直接丢弃原文。

### 4.13.2 四种压缩方式

不同手段丢失的信息有何不同？。 截断：便宜但不可控。 摘要：流畅但可能幻觉和抹平分歧。 抽取：保指定字段但漏未知重要信息。 外存检索：保原文但可能取不回来。 方法选择输入信息类型、预算和可接受损失，输出截断、摘要、字段抽取或外存检索方案。截断按位置删除，摘要重新表述，抽取保指定字段，检索保原文但按需取回；应根据最不能承受的失败选择或组合，而不是把四者当成等价压缩。

### 4.13.3 结构化状态与叙事分离

哪些内容不应交给自由摘要决定？。 将目标、验收条件、权限、已完成、未决和失败原因放入结构化状态；对话叙事可摘要。每项保留来源消息或工具结果 id，避免摘要变成唯一事实。 结构化状态输入目标、约束、权限、进度、未决项和来源，输出可版本化字段；叙事摘要输入其余对话，输出可重建概述。字段更新受权限和事件规则控制，摘要不能覆盖状态。来源引用仍可回查时，压缩内容才不是唯一且不可验证的事实源。

### 4.13.4 压缩率不是唯一指标

token 减少 90% 是否就是好压缩？。 公式：上下文压缩综合效用。 还需测问答可恢复性、约束保持、引用一致和后续任务成功；极高压缩通常提高遗漏风险。 压缩效用输入后续任务收益、token 成本、关键信息损失及权重 λ、μ，输出一个用于比较方案的综合效用。λ 表示每单位 token 成本的惩罚，μ 表示关键信息丢失的惩罚；效用更高只在同一任务和权重口径下更好，不能跨风险场景直接比较。

### 4.13.5 递归摘要会漂移

每十轮摘要上一次摘要会发生什么？。 小误差和遗漏逐代累积，原始分歧被改写成确定结论。定期从原始日志重建，保留里程碑快照和不可压缩字段，并允许用户纠正。 递归摘要输入上一代摘要和新事件，输出更短的新摘要；每次重写都可能累积遗漏和措辞偏差。与原始日志重建结果出现分歧说明摘要漂移，而不是原始事实改变。高风险字段必须无损保存，并允许从原始事件定期重建和人工纠正。

### 4.13.6 安全与隐私

摘要是否天然比原文更安全？。 摘要仍可能包含敏感数据，也可能把不可信指令固化为长期规则。压缩前后都做作用域、保留期和来源标记；删除请求应覆盖摘要、索引和缓存。 “更短”不是“更相关”。 压缩器必须围绕当前任务评测。 安全治理输入原文与摘要的数据分类、来源、作用域和删除请求，输出保留、隔离、审计与删除动作。摘要可能继续保存敏感数据，也可能把外部恶意指令固化成长期规则；更短不等于更安全。没有可信来源的文本只能作为候选证据，不能升级为系统权限。

### 4.13.7 完整示例：把 18k token 项目历史压进 4k 预算

怎样分配预算，既不丢验收条件，也保留足够原始证据？。 假设系统提示与工具说明占1,200 token，当前问题和回答预留1,300，真正可供历史使用的只剩1,500。原始历史18,000 token不能按比例盲缩；先把5条目标/约束、3个未决事项和最近工具状态抽成500 token结构化状态，再给里程碑摘要500 token，最后用剩余500 token检索最相关原文片段。 公式：历史预算与压缩率。 预算块； token； 不可接受的失败。 受保护状态； 500； 目标、权限、验收条件被改写。 里程碑摘要； 500； 把未决争议写成已决定。 检索原文； 500； 找不到支撑当前决策的证据。 。 若后续问题改为追查某次失败，预算也应重分配：保留同一份受保护状态，但摘要和原文检索围绕失败时间线重建。由此可见，压缩结果是“任务条件下的视图”，不是可永久替代原始日志的真相。 预算案例输入 18k 历史、4k 总窗口、系统与回答预留，输出 1500 token 历史预算及状态、摘要、原文各 500 token 的分配。Bhistory 是历史预算，压缩率是装入历史与原历史之比；8.3% 只描述长度，不证明任务信息保真。任务改变时摘要和检索必须围绕新问题重建。

### 4.13.8 原创图：压缩器应输出状态、摘要和可回查证据三条通道

为什么一段流畅摘要不足以支撑长期 Agent？。 图示：原始事件流经过分类后进入受保护状态任务摘要和可检索原文并在组装上下文时合流。 图 1 摘要只是一路；关键状态与原始证据必须保持独立生命周期。 三通道设计输入原始消息、工具和决策事件，输出受保护状态、任务摘要和带权限的原文索引，随后按当前任务合流。状态保硬约束，摘要保叙事，索引负责证据回查；一段流畅摘要无法替代三者。预算不足时必须明确哪些证据未装入。

### 4.13.9 受保护状态要像数据库记录，而不是散文

### 4.13.10 差异化压缩：代码、对话和工具输出不能用同一摘要器

一条命令的退出码与一段讨论的中心思想，哪一个更该逐字保留？。 代码修改应保留文件、行号、补丁和测试结果；工具调用保留参数、退出状态与关键输出；讨论可抽取立场、决定和未决点；长文档适合先分块检索再局部摘要。压缩器必须认识信息类型，否则会把“测试失败，exit 1”润色成“测试已运行”，或把尚未采用的建议写成最终决定。 对高风险字段采用无损抽取与模式校验，对叙事采用有损摘要，对可回查材料只存索引。若预算不足，系统应暴露“哪些证据未装入”，而不是静默假装上下文完整。 差异化压缩输入代码、讨论、工具输出或长文档，输出与类型匹配的补丁记录、决定摘要、执行证据或检索索引。先判断哪些字段必须逐字无损，再对叙事有损摘要；退出码、权限和测试结果不能只保“中心思想”。无法容纳的证据要显式报告缺失。

### 4.13.11 如何做压缩回归：让原文与压缩版完成同一组后续任务

ROUGE 很高的摘要，为什么仍可能让 Agent 做错事？。 字面重合不等于决策信息保真。建立带原始日志的任务集，为每段历史设计后续问题：复述目标、列出不可违反约束、继续未完成步骤、解释某次决定、定位证据、响应删除请求。分别用全量历史与压缩上下文运行，比较任务成功差、约束违例、无源断言和引用命中。 公式：压缩造成的任务成功率差。 还要做多代压力测试：连续压缩10轮后从原始事件重建，对比受保护字段和未决事项。上线监控压缩触发频率、重建次数、用户纠正率和因遗漏导致的回退；模型、摘要提示或token预算变化都要重跑回归。 压缩回归输入同一原始历史的全量版与压缩版以及一组后续任务，输出任务成功差 Δtask、约束违例、无源断言和引用命中。success(full context) 是全量上下文成功率，success(compacted context) 是压缩上下文成功率；差值越大表示压缩损失越严重。模型、提示或预算变化后必须重跑。

### 4.13.13 压缩触发与并发隔离

## 4.14 推理优化：先定位 prefill、decode、KV 还是排队瓶颈（inference-optimization）

### 4.14.1 先把端到端时间拆开

长输入短回答与短输入长回答，为何需要不同优化？。 请求先排队，再 prefill 全部输入并建立 KV，随后每步 decode 一个 token，期间还可能检索、工具和传输。长输入主要增加 prefill 与 KV；长输出主要占用 decode 槽和权重/KV 读取。 公式：首 token 与完成时间分解。 先按输入长度、输出长度、并发和缓存命中切片，否则“平均慢”无法指导是改内核、调度、缓存还是模型。 用户体验不是 tokens/s。 交互场景重 TTFT/抖动，批处理离线任务更重吞吐和总成本。 阶段拆分输入排队、输入长度、输出长度、工具与传输日志，输出 TTFT、TPOT 和端到端完成时间。TTFT 是请求到首 token 的时间，Q 是排队时间，Ccontext 是上下文准备时间，Tprefill 是输入预填充时间，Tfirst 是首步解码时间；TPOT 是首 token 后平均每个新 token 的时间，N 是输出 token 总数，Texternal 是工具与传输时间。指标指向不同瓶颈，不能用单一 tokens/s 代表用户体验。

### 4.14.2 prefill 与 decode 的硬件性格不同

为什么同一 Transformer 在两个阶段一个吃算力、一个吃带宽？。 prefill 可并行处理许多输入 token，大矩阵乘法有较高算术强度，更容易利用 GPU compute；decode 每步 batch/token 维度小，要反复读取大权重和增长的 KV，常受 HBM 带宽限制。 公式：算术强度与 roofline 性能上限。 这是 roofline 直觉，不是每个内核的精确模型。批量增大可提升 decode 的权重复用，却会增加排队和 KV 压力；量化减少字节，FlashAttention 减少中间内存往返，分别瞄准不同瓶颈。 阶段； 主要工作； 常见瓶颈； 典型优化。 排队； 等待调度； 容量/批策略； 扩容、优先级、背压。 prefill； 输入并行矩阵/注意力； 算力、长序列 IO； FlashAttention、前缀缓存。 decode； 逐 token 权重/KV 读取； 带宽、串行步数； 批处理、量化、推测解码。 工具； 外部请求； 网络/服务； 并行、超时、缓存。 。 硬件瓶颈分析输入每阶段 FLOPs、内存读写字节 BytesIO、峰值算力 ComputePeak 和内存带宽 Bandwidth，输出算术强度 AI 与 roofline 性能上限 Perfmax。AI 是每搬运一字节完成的浮点运算数；上限取算力峰值与 AI×带宽中的较小者。它是定位直觉，不是每个内核的精确耗时预测。

### 4.14.3 连续批处理用动态调度填掉空洞

静态批里短回答结束后，为什么 GPU 仍像在为它保留座位？。 静态批等所有序列完成才换批，长度差异造成空槽。连续批处理在每个调度步移除已完成请求、插入新请求，提高利用率。代价是调度复杂、延迟波动和长短请求公平。 设置最大 batch token、prefill chunk、优先级和抢占；避免一个超长 prefill 阻塞所有 decode。交互与离线队列可分池，关键租户保留容量。组批等待越长吞吐可能越高，但 TTFT 也越差。 过载时优化器会变成放大器。 无限队列让 GPU 始终满载却使 p99 失控；需要 admission control 和背压。 连续批处理输入等待请求、每步可用 token 容量和优先级，输出每个调度步的移除、插入、分块或抢占决定。完成序列立刻让位给新请求以减少空槽；吞吐提高不代表尾延迟更好。过载时必须有准入控制、背压和租户公平边界。

### 4.14.4 KV cache 是并发容量的隐藏预算

模型权重放得下，为什么并发一上来仍 OOM？。 每个活跃 token 在每层保存 K/V，内存随并发和序列长度近似线性增长。粗略：。 公式：KV 缓存内存估算。 32 层、8 KV 头、128 维、FP16、每请求 8k token 时约 1.05GB/请求；16 个并发约 16.8GB，还未计权重与工作区。PagedAttention 用固定块减少外部碎片，支持前缀共享和更灵活驱逐，但不会消除 KV 本身。 KV 量化可减容量/带宽，却可能影响长上下文与质量；滑窗/压缩缓存会改变可见历史，应视作算法变化而非纯工程优化。 KV 容量估算输入层数 Nlayer、KV 头数 NKVhead、头维 d、token 数 Ntoken、并发 B 和元素字节 b，输出缓存内存 MKV。K 与 V 各保存一次所以乘二；估算解释 OOM 和并发上限，但 PagedAttention 只减少碎片，不会消除 KV 本体。量化或滑窗还需质量回归。

### 4.14.6 FlashAttention 减少 IO，不近似注意力结果

不保存完整 N×N 注意力矩阵，softmax 还能算得精确吗？。 FlashAttention 将 Q/K/V 分块装入片上 SRAM，在线维护 softmax 的行最大值和归一化和，避免把巨大中间分数矩阵反复写回 HBM。算法在数值精度范围内计算同一注意力，而非稀疏近似。 收益随序列、硬件、dtype 和实现变化；短序列或其他算子主导时不显著。FlashAttention 不改变 KV 长期容量，也不会解决队列和工具延迟。升级内核要做数值、质量和稳定性回归。 优化匹配： 看到长 prefill 的注意力 IO 占主导才优先；若 p99 来自排队，换内核可能治标不治本。 FlashAttention 输入同一 Q、K、V 注意力计算，输出数值精度范围内相同的注意力结果和更少 HBM 往返。它通过分块和在线 softmax 改变计算顺序而非近似目标；收益表示注意力 IO 降低，不代表 KV 容量、排队或工具延迟得到解决。短序列和非注意力瓶颈可能无收益。

### 4.14.7 量化减少字节，但属于质量相关改动

把 FP16 权重改 INT4，为何既可能更快也可能更慢？。 更低位宽减少显存与权重带宽，可提高 decode 吞吐和容纳更大 batch；但反量化内核、硬件支持和小 batch 会决定净收益。权重量化、激活量化与 KV 量化影响不同。 对象； 主要收益； 主要风险。 权重； 模型显存/带宽； 少数通道误差、内核开销。 激活； 算子速度/通信； 动态范围和校准。 KV； 长上下文并发/带宽； 远距离检索与累积误差。 。 按任务、语言、长上下文、概率校准和工具参数切片回归，不能只看困惑度平均。后续“量化”页会深入方法，本页关注服务选择边界。 量化选择输入权重、激活或 KV、目标位宽、硬件内核和任务切片，输出低精度模型及显存、速度和质量差异。低位宽减少存储和带宽，反量化与校准又增加开销；更快只在支持良好且瓶颈匹配时成立。必须按语言、长上下文、工具参数和高风险任务回归。

### 4.14.8 推测解码用并行验证减少串行步数

小模型先猜 k 个 token，大模型怎样既加速又保持目标分布？。 草稿模型快速提出一段，大模型一次前向并行评估多个位置，按接受/拒绝规则校正；正确算法保持目标模型分布。收益取决于草稿速度、k、接受率与验证批效率。 公式：推测解码每轮近似产出。 a=.8、k=4 时约 1+.8+.64+.512+.4096=3.36 token/轮；但草稿和验证有成本，实际加速小于 3.36。领域错配、温度高或模型差异大时 a 低，反而变慢。 推测解码优化 TPOT/吞吐，不一定改善长输入 prefill；与流式结合时还要避免因验证批次造成可见输出突发抖动。 推测解码输入草稿模型、目标模型、草稿长度 k 和逐 token 接受率 a，输出经目标模型验证后的 token。草稿先并行提出，目标模型批量验证并按规则接受或校正；近似轮产出是 1+a+…+a^k。它不改变正确目标分布的前提是使用正确校正规则，低接受率或高验证成本会变慢。

### 4.14.9 真实负载基准和质量门禁缺一不可

离线单请求 tokens/s 提升 2 倍，怎样证明生产真的更好？。 回放真实输入/输出长度联合分布、并发、到达突发、缓存命中和优先级；报告 TTFT/TPOT/E2E p50/p95/p99、吞吐、超时、KV/显存、功耗、每成功任务成本。做稳态、突发、过载和单节点故障。 任何量化、压缩 KV、上下文裁剪或近似解码都跑完整应用评测；所谓“质量不变”必须带切片与区间。内核和调度也可能产生数值错误、饥饿或公平问题。 基准作弊： 固定短输出、预热缓存、忽略排队、只报最佳 batch 和不计失败请求，会让结果无法迁移到生产。 生产基准输入真实长度分布、并发、突发、缓存命中、优先级和故障，输出延迟分位数、吞吐、资源、失败率、质量和每成功任务成本。固定负载做方案对照并覆盖稳态、过载和节点故障；只有平均 tokens/s 提升不能证明生产更好。任何算法或低精度变化都必须经过质量门禁。

### 4.14.10 常见误区与概念依赖

推理优化不是技巧清单，而是瓶颈诊断、约束选择和真实负载验证。 误区； 更准确的理解。 prefill 和 decode 同样受限； 前者常偏计算，后者常偏权重/KV 带宽。 吞吐高就延迟低； 组批可提高吞吐却增加排队和 p99。 PagedAttention 减少 KV 数量； 主要减少碎片并改善管理/共享。 FlashAttention 是近似注意力； 通过 IO 感知分块精确计算同一注意力。 推测解码总能加速； 接受率低或草稿/验证开销高会变慢。 。 层级； 概念依赖与延伸学习。 先修； Transformer、self-attention、KV cache、GPU 内存层级。 本页核心 ； TTFT/TPOT、roofline、连续批、KV 容量、推测解码。 专项； 量化、提示缓存、分布式推理、流式输出。 生产； 部署、模型路由、应用评测与可观测性。 。

### 4.14.11 把因果链连起来

## 4.15 模型选型与成本：寻找满足约束的最小可行方案（model-selection）

### 4.15.1 “哪个模型最好”缺少目标函数

抽取发票、写文案和批准退款，为什么不能共享同一排行榜结论？。 三类任务的正确性定义、错误代价、上下文、输出结构和权限完全不同。先定义输入分布、成功事件、高风险切片、延迟 SLO、数据边界、吞吐与预算；只有这些条件固定，模型分数才成为可比较证据。 退款助手的硬门槛可包括：越权率≤0.5%、质量问题资格准确率≥90%、p95≤1.8s、数据不得跨指定区域。普通解释清晰度和成本则是可优化目标。硬约束失败的模型不能靠更低价格“补回来”。 选型问题： 在约束集合 C 内，哪个模型—提示—工具配置的长期总成本最小？模型名字只是方案的一部分。 模型选型输入任务分布、成功定义、风险切片、SLO、数据边界和预算，输出满足全部硬约束的候选配置集合。先定义“成功”和不可补偿门槛，再比较候选；榜单分数只有在这些条件相同才可解释。任何硬约束失败都不能被价格或普通样本高分抵消。

### 4.15.2 先用强模型建立系统上界

原型表现差时，怎样判断是模型不够强还是检索、提示和流程有问题？。 先用能力强、上下文充分、工具稳定的候选跑代表性样本，得到当前架构上界。若 oracle 证据下强模型仍失败，应修任务定义、数据、工具或验收；若强模型通过，再逐项换小模型、减少上下文和推理预算，测每个节省造成的损失。 冻结评测集和评分器，不边比较边改题。 强模型 + 完整证据建立可达上界。 固定其余变量，只替换一个模型或推理配置。 保留逐样本差异，检查新旧错误迁移。 再评端到端回退链，而非只测单次输出。 强模型基线不是默认生产方案。 它是诊断参照；隐私、延迟或许可也可能让它从一开始就不可行。 强模型基线输入冻结评测集、充分证据和稳定工具，输出当前系统架构可达到的质量上界及逐样本错误。若强模型在 oracle 证据下仍失败，优先修任务、数据或工具；若它通过，再一次只替换一个变量做消融。上界是诊断参照，不是自动生产推荐。

### 4.15.3 选型是受约束的多目标优化

质量、风险、延迟和成本怎样放进同一决策，而不武断加成一个总分？。 公式：模型选型的受约束优化。 先用门槛筛可行域，再看成本、吞吐和维护负担。若多个目标没有公认换算率，用帕累托前沿：不存在另一个候选在所有维度不差且至少一项更好。处于前沿不等于自动胜出，只说明值得结合业务权重讨论。 维度； 建议表达； 不能被什么抵消。 关键质量； 切片通过率与区间； 普通样本平均提升。 安全/权限； 事件率与严重度； 更自然的文风。 延迟； TTFT、p95/p99、超时； 平均延迟。 成本； 每成功任务与峰值容量； token 单价。 治理； 地域、保留、审计、退出能力； 模型能力分。 。 约束优化输入候选 m、各质量 Qualityk、风险 Riskj、延迟 P95、隐私类别 Privacy 与门槛，输出可行域中总成本 TotalCost 最低的方案。Qk 是第 k 项质量下限，Rj 是第 j 项风险上限，L 是延迟上限，C 是允许的隐私类别集合。先执行硬门槛，再看帕累托和成本；进入帕累托前沿只表示未被全面支配，不代表自动胜出。

### 4.15.4 完整成本从请求流转而不是价目表计算

小模型单次只要大模型的四分之一，为什么可能更贵？。 一次任务可能包含初答、检索、重试、升级强模型、工具、人工复核和失败补救。固定成本还包括部署冗余、监控、评测、供应商集成和迁移。把这些都归到成熟业务结果上。 公式：每成功任务完整成本。 失败损失不一定能精确定价，高风险通常用硬门槛更诚实；但至少要显示人工和重试，否则会奖励把成本转嫁给运营团队的方案。 分母陷阱： 若只统计系统宣称完成的任务，会漏掉用户放弃和错误自动批准；成功必须由独立业务状态定义。 成本核算输入调用 Ccall、检索工具 Ctool、重试升级 Cretry、人工 Chuman、基础设施 Cinfra、失败损失 Closs 和独立确认的成功任务数 Nsuccess，输出每成功任务完整成本 CostPerSuccess。分子汇总任务全链路资源与损失，分母只计真实业务成功；低单次价格若带来更多人工和失败，最终可能更贵。无法定价的高风险应保留硬门槛。

### 4.15.5 运行示例：便宜模型怎样输给较贵模型

处理 1000 笔退款，单次 ¥0.02 的 S 与 ¥0.08 的 M，谁的每成功任务成本低？。 图示：三个模型候选经过硬门槛筛选和每成功任务成本比较。 图 1 先筛硬约束，再比较完整经济性；便宜但越权的候选不会进入成本赛道。 候选； 单次调用； 成功率； 人工率×¥1； 失败补救； 每成功任务。 S 小模型； ¥20； 78%=780； 180×1=¥180； 40×¥3=¥120； (20+180+120)/780=¥0.410。 M 中模型； ¥80； 90%=900； 65×1=¥65； 2×¥3=¥6； ¥151/900=¥0.168。 L 强模型； ¥180； 93%=930； 35×1=¥35； 1×¥3=¥3； ¥218/930=¥0.234。 。 S 虽调用最便宜，总成本最高且若越权率超过硬门槛应直接淘汰。M 在给定假设下胜出；人工单价或流量结构改变，结论也会改变，所以要做敏感性分析。 案例输入 1000 笔退款及 S、M、L 三个候选的门槛、调用、成功、人工和补救数据，输出可行候选及每成功任务成本。先淘汰越权或延迟不合格者，再计算 M 的 151÷900≈0.168 元；它在当前假设胜出，但人工单价和流量变化后必须重做敏感性分析。

### 4.15.6 供应商与运行方式也是候选的一部分

两个端点输出质量相近时，为什么合同、版本与退出能力会决定结果？。 比较数据是否用于训练、保留期、区域、加密、审计、模型版本锁定、速率限制、SLA、批量价格、内容政策和停服条款。自托管还要计 GPU 利用、补丁、值班和灾备。开源权重允许控制却不自动给出许可、数据来源或安全保证。 做退出演练：导出提示与评测、切换备用端点、验证输出契约和工具兼容，测实际恢复时间。供应商“等价模型”可能在格式、拒答和 tokenization 上不同；抽象接口只能降低迁移成本，不能消除行为差异。 问题； 需要的证据。 能否锁版本； 快照标识、变更通知和回归窗口。 数据去向； 合同、地域、保留和子处理方。 容量保证； 配额、突发策略、SLA 与故障记录。 退出成本； 替代端点实测、迁移脚本和兼容差异。 。 供应商评估输入模型行为、合同、地域、保留期、版本、容量、许可和退出演练，输出可治理的运行方案与替代路径。接口相同不保证格式、拒答和 tokenization 相同；实际切换恢复时间才是退出能力证据。自托管也必须计入运维、补丁和值班成本。

### 4.15.7 一个应用可静态组合多个模型

“选一个模型”为什么常常不是最终系统设计？。 意图分类、查询改写、核心推理、代码执行和安全复核的难度与风险不同，可按组件静态分工。例如确定性规则先检查权限，小模型抽取订单字段，中模型解释政策，高风险异常转人工。这样比让一个大模型承担所有步骤更可测。 动态路由则在请求级预测难度再选模型，可能进一步省成本，但引入错误下放、级联延迟和路由器漂移。应先建立静态基线，确认每个组件门槛，再把路由作为独立系统评测；不能把路由收益归功于底层模型。 工具不是模型能力的免费加成。 不同候选对 schema、错误恢复和上下文的利用不同，必须在同一端到端工具链实测。 静态模型组合输入各组件的难度、风险、结构与工具需求，输出规则、小模型、中模型、强模型或人工的职责分工。按组件固定责任能让权限检查、抽取和高风险判断分别验收；动态路由是后续独立系统，不能把路由收益误记为底层模型能力。

### 4.15.8 回退、降级和退出必须进入评测

首选模型超时、限流、低置信或输出非法时，用户实际经历什么？。 预先定义：重试同端点、升级强模型、改用确定性代码、请求补充信息、返回缓存、转人工或明确失败。每种分支有总 token、总延迟和副作用预算；首答内容不可无审查地塞给后续模型，以免错误或注入污染级联。 把故障注入评测：供应商 429、流中断、工具超时、schema 变化和区域不可用。测最终任务成功率、p95、重复动作和人工负载。主模型 99.9% 可用不代表完整级联相同可靠，依赖串联会降低端到端可用性。 公式：串行独立依赖的近似可用率。 回退设计输入超时、限流、低置信、非法输出与第 i 个依赖的可用率 Ai，输出重试、升级、确定性代码、询问、人工或失败分支以及系统可用率 Asystem。串行独立依赖的可用率近似各 Ai 的乘积；它解释组件各自很可靠时端到端仍会下降。真实相关故障、重复副作用和总延迟必须通过故障注入验证。

### 4.15.9 选择会过期，需要触发复评

今天的最优模型为什么下个月可能不再可行？。 价格、版本、上下文长度、供应商政策、流量语言、任务规则和人工成本都会变化。设置触发器：模型快照更新、价格变动、关键切片漂移、错误预算耗尽、新风险要求或备用切换失败。定期运行冻结集和真实抽样，而不是只在采购期比较一次。 记录决策卡：候选、排除原因、数据版本、门槛、区间、成本假设、审批人、复评日期和退出方案。避免团队忘记某候选为何因隐私或越权被淘汰，又仅凭新版榜单重新引入。 基准污染： 公开榜单只能提供候选，不能代替私有代表性集；反复针对同一私有集调参也会过拟合。 生命周期复评输入价格、模型版本、任务分布、政策、人工成本和错误预算变化，输出继续使用、重新比较、灰度切换或退出决定。触发器出现时重跑冻结集与真实抽样，并更新决策卡；历史最优只对当时数据和假设成立，不能永久继承。

这个概念怎样从问题一路连接到可验证的实践？。 定义任务分布与硬约束。 强模型建立架构上界。 固定条件比较逐样本差异。 筛除不满足门槛的候选。 计算完整每成功任务成本。 灰度发布并按触发器复评/退出。

### 4.15.12 误区与自测

你能否不用背术语，解释它的机制、边界与验证方法？。 为什么先用强模型建立上界？。 每成功任务成本应包含什么？。 帕累托前沿代表自动最优吗？。 模型路由与静态选型差在哪？。 哪些变化触发复评？。 假设“模型选型与成本：寻找满足约束的最小可行方案”在离线示例上表现正常、上线后核心结果却下降，你会怎样按输入、内部变换、输出反馈和适用边界定位问题？。 如何为“模型选型与成本：寻找满足约束的最小可行方案”设计一个最小对照实验，证明观察到的改善来自核心机制，而不是数据、提示、权限或评测口径同时变化？。 。 参考答案 帮助区分模型能力不足与数据、提示、工具或任务定义问题。 调用、检索工具、重试升级、人工、基础设施和失败补救。 不代表，只说明没有候选在所有维度支配它，仍需业务权重。 选型按项目/组件固定方案，路由按每个请求动态选择。 模型/价格/供应商政策、流量分布、任务规则、风险或故障表现变化。 先保存同一失败样本及环境，确认输入、权限和前置条件没有漂移；再记录关键中间状态，检查机制是否按本页描述完成变换；随后把原始输出与独立指标、人工终验对照；最后用边界样例和对照实验复测。只有定位到首次偏离预期的环节，才能判断应修改数据、机制、评测还是使用边界。 固定数据、模型版本、提示、权限、预算和评测，只改变一个与核心机制直接相关的因素，并在多个样本与随机种子上重复；同时保存中间状态和失败样本。若差异只在目标因素变化时稳定出现，才支持机制解释，否则应继续排查混杂变量。

## 4.16 模型路由与级联：把不同难度请求分给足够的能力（model-routing）

### 4.16.1 路由把一次选型变成逐请求决策

同一退款系统里，FAQ 与跨政策异常为何不该付相同计算成本？。 简单状态查询可由小模型完成，证据冲突、金额异常或高权限请求升级强模型或人工。静态选型为整个组件固定模型；动态路由根据当前输入与运行证据选择；MoE 则是一个模型内部为 token 选择专家，用户通常不直接控制完整模型切换。 路由不会创造底层模型没有的能力，只在已有候选之间分配。若所有模型在某切片都失败，路由器最多选出不同的失败；应先通过选型与评测建立逐样本基线。 真正目标： 最大化安全可下放覆盖率，而不是最大化“小模型调用率”。后者会诱导把困难请求错误地下放。 模型路由输入当前请求、风险规则、候选模型能力和运行证据，输出小模型、强模型、人工或拒绝路径。它逐请求选择已有能力，不会创造候选都没有的能力；下放表示证据显示小模型足够，不表示请求天然简单。高风险硬规则优先于概率分数。

### 4.16.2 直接路由、级联和并行选择

是在调用前选模型，还是先让小模型回答再决定升级？。 形态； 过程； 优势； 代价。 规则路由； 按领域/风险/长度选择； 可解释、无额外模型； 边界粗、维护规则。 直接路由； 轻量分类器先选 S/M/L； 困难请求不先浪费小模型； 仅凭输入可能判断不足。 级联； 先跑 S，低置信再跑 L； 利用首答、验证与检索信号； 升级请求更慢且首答可能污染。 并行选择； 多个模型同时跑再选择； 低墙钟延迟、候选多； 成本高、选择器也会错。 。 高风险请求可用确定规则强制 L/人工，不交给概率路由器；低风险长尾可级联。架构应按错误成本和延迟 SLO组合，而不是全站只用一个阈值。 架构选择输入决策时点、可用信号、错误成本和延迟 SLO，输出规则路由、直接路由、级联或并行选择。调用前信号适合直接选择，首答和验证信号适合级联，并行用成本换墙钟时间；没有一种形态适合所有请求。首阶段可能产生副作用时不得无审查级联。

### 4.16.3 数学目标必须带切片硬约束

只最小化平均费用，路由器会学到什么危险捷径？。 公式：带逐切片约束的模型路由目标。 平均约束允许多数简单请求的高分抵消少数越权错误。应为语言、领域、风险和用户群设置最低质量/最大错误下放率；样本少时报告区间并采用保守上界。 训练目标最好预测“强模型相对小模型的质量增益”而非绝对难度：若两者都对，升级浪费；若两者都错，升级也无收益；只有强对小错的样本最值得升级。质量标签来自独立评分器与人工，不能用强模型自评当无偏真值。 选择偏差： 线上只给被升级样本运行强模型，就看不到下放样本的反事实强模型表现；需随机探索或离线双跑建立无偏数据。 路由优化输入请求 x、所选模型 m(x)、成本 c、质量 q、质量下限 Q0、关键切片风险 Riskk 和上限 Rk，输出满足逐切片硬约束的最低期望成本策略。平均质量不能抵消少数切片错放；训练应预测强模型相对收益，并用随机双跑补足下放样本的反事实。

### 4.16.4 级联期望成本和延迟怎样计算

小模型 ¥0.02、强模型 ¥0.10，升级 25% 时平均成本真是 ¥0.045 吗？。 若所有请求先跑小模型，升级后再跑强模型，忽略其他组件时：。 公式：级联期望成本与延迟。 代入 Cₛ=.02、Cₗ=.10、r=.25，平均调用成本=.045。若直接路由只在前置分类器后选一个模型，则是 Crouter +(1−r)Cₛ+rCₗ 。两者费用接近时，级联仍让升级请求承受 S+L 的串行尾延迟。 真实成本还包括评分器、重试、检索、人工和失败。若小模型首答写入对话或触发工具，即使后来升级也可能留下污染或副作用，因此级联首阶段应默认无副作用、输出只作为候选证据。 级联核算输入小模型成本 Cs、强模型成本 Cl、升级率 r、小模型延迟 Ts、判定延迟 Tjudge 和强模型延迟 Tl，输出期望成本 ECost 与期望延迟 ETime。所有请求先付 Cs，升级请求再付 Cl 和串行延迟；0.045 元成立于给定调用假设，不含评分器、失败和人工。

### 4.16.5 运行示例：阈值怎样改变覆盖、错误与成本

1000 笔退款按“需要强模型概率”排序，τ=.5 与 τ=.3 如何取舍？。 图示：退款请求按升级分数路由到小模型和强模型并由抽样审计回流。 图 1 路由分数要预测升级收益；下放样本必须抽样双跑或人工审计，否则系统看不见自己错放的请求。 阈值； 升级数； 错放困难请求； 质量通过； 平均模型成本； 升级请求延迟。 τ=.7； 150； 28； 91.0%； .02+.15×.10=¥.035； S+判定+L。 τ=.5； 250； 12； 93.1%； ¥.045； S+判定+L。 τ=.3； 420； 4； 94.0%； ¥.062； S+判定+L。 。 若门槛是质量≥93%、错放≤15，则 τ=.5 是最低成本可行点。若高风险切片在这 12 个错放中占 5 个并超过独立门槛，仍需对该切片强制升级，而不是全局阈值继续平均。 阈值案例输入 1000 笔请求、升级分数 g(x)、阈值 τ 和三组质量成本结果，输出满足质量与错放门槛的最低成本阈值。τ 降低会增加升级、成本并减少错放；τ=.5 只在全局与所有关键切片同时通过时可选。高风险切片失败需强制升级，不能靠全局平均掩盖。

### 4.16.6 路由信号必须在决策时可得且可校准

哪些特征真正能预测强模型比小模型更有价值？。 输入领域、长度、语言、风险规则、检索命中与证据冲突可在调用前获得；小模型 logprob、自一致分歧、格式校验和外部验证需先运行首答。训练时不能使用最终人工标签、未来工具状态或只有强模型运行后才知道的特征，否则离线路由器会数据泄漏。 信号； 阶段； 盲区。 规则/元数据； 调用前； 新型困难与代理歧视。 小模型 logprob； 首答后； 流畅错误、长度偏差、失准。 多样本分歧； 首答后； 成本高、可能一致地错。 检索/验证器； 工具后； 验证覆盖与自身错误。 历史群体特征； 调用前； 公平、隐私和分布漂移。 。 将分数在独立集上校准为“升级能修复的概率”，按切片画可靠性图。模型说“我有 90% 把握”不能直接成为路由阈值。 路由特征输入决策时已经可得的领域、长度、语言、风险、检索、首答或验证信号，输出经独立集校准的“升级可修复概率”。训练时使用未来标签或强模型后验信息会数据泄漏；分数可靠性必须按切片检查。模型自报置信度不能未经校准直接当阈值。

### 4.16.7 错误下放会集中在谁身上

平均质量合格，为什么长尾语言和专业用户仍可能系统性得到弱模型？。 路由器通常在多数语言和常见任务上训练，可能把短输入误判为简单，把少数语言的低置信当噪声，或用地区、账户等级等代理让服务质量不公平。报告每个切片的下放率、强对小错率、错放率、升级收益和置信区间。 高影响领域可不依赖学习路由：医疗、金融决策、权限写操作与明确合规关键词强制更强验证或人工。公平并非要求所有群体升级比例相同，而是错误与服务质量不因路由策略造成不可接受差距。 反馈环： 小模型服务的用户更可能流失，从未来日志消失；若只用留下来的交互训练路由器，会错误地认为下放成功。 公平评测输入语言、领域、用户群和风险切片，输出各切片下放率、强对小错率、错放率、升级收益与置信区间。平均合格可能隐藏长尾用户持续收到弱模型；公平目标是限制不可接受的质量与错误差距，不是强求相同升级比例。高影响任务可直接绕过学习路由。

### 4.16.8 路由器上线也需要探索、监控与回退

底层模型、价格或流量一变，旧阈值为什么会立即失真？。 路由标签是候选模型之间的相对差异；任一模型版本、提示、价格、检索质量或流量变化都会改变最优边界。记录路由分数、选择原因、候选版本、升级率、逐切片质量、成本和级联延迟。新版本先离线双跑、影子，再金丝雀。 对少量下放请求随机运行强模型或人工审计，估错放反事实。 按时间和切片监控分数分布、校准与升级收益。 若质量标签延迟，先看证据缺失、用户纠正和人工改判代理。 越权或错放超预算时切到保守规则：全量强模型/人工或禁用动作。 重新收集双跑数据再校准，而不是只移动阈值掩盖根因。 探索会增加成本和潜在风险，必须限于安全可双跑的请求；不可逆工具只让一个经批准路径执行。 在线治理输入模型版本、价格、流量、路由分数、选择原因和延迟质量反馈，输出探索审计、重校准、金丝雀或保守回退动作。随机双跑让系统看见下放反事实，漂移则触发重新收集数据；错放超预算时先禁用危险动作或全量升级，不能只移动阈值掩盖根因。

### 4.16.9 常见误区与概念依赖

路由系统的核心产品是“安全下放证据”，不是一张节省百分比图。 误区； 更准确的理解。 小模型比例越高越好； 应最大化满足切片门槛的安全覆盖。 输入越短越简单； 短提示也可能含专业或高风险歧义。 低 logprob 就升级； 原始概率需校准且会漏掉自信错误。 级联一定省钱； 升级请求支付 S+判定+L 并增加尾延迟。 只看已升级样本可训练路由； 缺少下放样本的反事实强模型结果。 。 层级； 概念依赖与延伸学习。 先修； 模型选型、应用评测、不确定性校准。 本页核心 ； 直接路由、级联、质量差预测、阈值、反事实审计。 系统； 部署、推理优化、提示缓存、人在回路。 治理； 数据漂移、公平性、可观测性与安全回退。 。

### 4.16.10 把因果链连起来

这个概念怎样从问题一路连接到可验证的实践？。 建立候选逐样本质量与成本基线。 定义高风险强制规则。 训练/校准强模型增益分数。 选择满足切片门槛的阈值。 灰度路由并随机审计下放样本。 版本或分布变化后重校准/回退。
