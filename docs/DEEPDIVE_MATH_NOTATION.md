# 「理解原理」符号与公式生成规范

版本：1.0
生效日期：2026-07-25

## 1. 目标

公式必须呈现为读者在教材、课堂板书或纸笔推导中看到的数学，而不是源代码、计算器输入或变量名转储。

“教材式/纸笔式”指标准数学排版，不指模仿手写字体。展示层优先使用分式、上下标、根号、求和上下限、希腊字母、范数和标准运算符；可执行表达式另放代码块，两者不能混为一层。

## 2. 两层表示

### 2.1 展示公式

用于解释概念和推导，必须面向人阅读：

| 不合格的电脑符号表达 | 合格的教材式表达 |
|---|---|
| `theta` | \(\theta\) |
| `y_hat` | \(\hat{y}\) |
| `sum_i p_i * log(q_i)` | \(\sum_i p_i \log q_i\) |
| `(a+b)/n` | \(\frac{a+b}{n}\) |
| `sqrt(d)` | \(\sqrt{d}\) |
| `x[i]` | \(x_i\) |
| `x ** 2` | \(x^2\) |
| `a <= b` | \(a \le b\) |
| `x -> y` | \(x \rightarrow y\) |
| `abs(x)` | \(\lvert x\rvert\) |
| `norm(x)` | \(\lVert x\rVert\) |

普通网页正文不得直接输出表格左栏的写法充当正式公式。

### 2.2 可执行表达式

用于复算、单元测试或实现，放在 `.dd-code`、`code` 或证据 artifact 中：

```js
loss = -Math.log(p);
```

同一案例同时提供两层时，先显示数学含义，再给可执行对应关系：

```text
展示：L = −ln p
实现：loss = -Math.log(p)
```

实现变量可以使用 `learning_rate`，展示公式应使用 \(\eta\)，正文必须明确二者对应。

## 3. 页面标记

### 3.1 简单公式

只含少量上下标或标准运算的公式，可以使用语义 HTML：

```html
<div class="dd-formula" data-formula-id="binary-cross-entropy">
  L = −ln p
</div>
```

### 3.2 非平凡公式

包含分式、根号、求和上下限、多层上下标、矩阵或分段函数时，使用原生 MathML。不得用连续斜杠、下划线或空格模拟二维结构。

根号必须显式标记完整的被开方范围。核心展示公式使用 MathML 的 `<msqrt>`；正文、表格中的历史短根式可使用 `.dd-radical > .dd-radicand` 语义包装。禁止直接输入普通字符 `√` 后跟一串文本，因为该字符只是固定宽度字形，根号上横线不会随被开方内容延伸。

```html
<div class="dd-formula" data-formula-id="empirical-risk">
  <math display="block" aria-label="J theta 等于一除以 n，乘以从 i 等于一到 n 的损失求和">
    <mrow>
      <mi>J</mi><mo>(</mo><mi>θ</mi><mo>)</mo><mo>=</mo>
      <mfrac><mn>1</mn><mi>n</mi></mfrac>
      <munderover>
        <mo>∑</mo>
        <mrow><mi>i</mi><mo>=</mo><mn>1</mn></mrow>
        <mi>n</mi>
      </munderover>
      <mi>L</mi><mo>(</mo><msub><mi>y</mi><mi>i</mi></msub><mo>,</mo>
      <mi>f</mi><mo>(</mo><msub><mi>x</mi><mi>i</mi></msub><mo>;</mo><mi>θ</mi><mo>)</mo><mo>)</mo>
    </mrow>
  </math>
</div>
```

原生 MathML无需网络、远程字体或运行时脚本，必须保持 `file://` 与 Chromium阅读路径可用。

### 3.3 可访问名称

复杂 MathML必须具有简短、可理解的 `aria-label`。公式后的正文仍要用自然语言解释含义，不能把屏幕阅读器标签当成教学说明。

## 4. 符号生成规则

1. **首次出现先定义。** 符号第一次参与公式前或紧随公式后，必须说明角色、取值范围及必要单位。
2. **一符一义。** 同一页内一个符号不能无提示地切换含义；相邻官方页面应优先沿用同一约定。
3. **一义一主符号。** 同一对象不要在连续内容中交替使用 `p`、“垃圾概率”、“正确类别置信度”等未声明别名。
4. **下标表达角色。** 样本、时间、类别等索引用 \(i,t,c\) 等下标表达，不用 `x[i]` 冒充展示公式。
5. **装饰符有固定含义。** 帽号通常表示估计或预测，星号通常表示最优解，横线通常表示均值；页面若采用其他含义必须说明。
6. **向量与标量可区分。** 需要区分时采用粗体、箭头或文字说明，并在全页保持一种方式。
7. **函数使用标准名称。** 使用 \(\ln,\log_2,\exp,\operatorname{softmax}\) 等标准形式，不输出 `Math.log`、`np.exp` 或 `softmax_fn`。
8. **运算符使用数学字符。** 使用 \(×,·,÷,\le,\ge,\ne,\rightarrow\)，不用编程语言的 `*`, `//`, `<=`, `!=`, `->`。

## 5. 公式教学链

核心公式不能孤立出现。根据学习目标，至少建立以下证据链：

1. **问题或直觉：** 为什么需要这个量？
2. **符号表：** 每个新符号代表什么？
3. **定义或来路：** 公式是定义、化简、近似还是推导结果？
4. **数值代入：** 选择有语义的数值并逐步代入。
5. **结果解释：** 数值变大、变小或改变符号意味着什么？
6. **边界：** 在什么条件下不成立、会发散或不能直接比较？
7. **实现对应：** 只有确有复现价值时再给代码表达式。

并非每个辅助公式都需要完整七步；但页面学习目标若包含“解释、计算、推导或比较”，相应核心公式必须有对应证据。

## 6. 对数、概率和单位

1. 使用 `ln` 时说明结果单位为 nat；使用 `log₂` 时说明结果单位为 bit。
2. 困惑度还原必须与底数一致：nat 使用 \(e^H\)，bit 使用 \(2^H\)。
3. 概率符号必须说明它是目标类别概率、某个类别概率、联合概率还是条件概率。
4. 总体期望与有限样本平均不能使用同一公式后不加区分。
5. 改变对数底数只会按常数缩放数值的场景，也必须声明比较口径。

## 7. 公式元数据

新页面和大改页面的核心公式应登记：

```js
quality: {
  formulas: [{
    id: "empirical-risk",
    section: "section-3",
    display: "mathml",
    role: "definition",
    symbols: {
      "θ": "模型参数",
      "n": "当前数据集的样本数",
      "i": "样本索引",
      "L": "单样本损失"
    },
    logBase: null,
    unitConvention: "J 与单样本损失使用相同单位",
    workedExample: "example-1"
  }]
}
```

门禁根据元数据检查声明完整性，L4负责确认解释是否准确、充分。采用 `quality.contractVersion: 1` 时，每条符号声明还必须提供 `evidence`，绑定同一章节正文中的真实解释片段；审计器会拒绝不存在于正文的证据、公式中没有出现的登记符号，以及没有登记的核心公式。

## 8. 门禁分工

### 自动 blocker

- `.dd-formula`使用 `<code>` 包裹正式展示公式；
- 展示公式出现 `theta`、`sum_`、`sqrt(`、`**`、`<=`、`!=`、`->` 等明确编程记法；
- 页面出现未由 MathML `<msqrt>` 或 `.dd-radical > .dd-radicand` 表达被开方范围的裸文本根号 `√`；
- 声明为 `mathml` 的公式没有 `<math>` 或可访问名称；
- 元数据声明的核心符号未在符号表登记；
- 合同版本 1 的公式缺唯一 `data-formula-id`，或符号的 `meaning`、正文 `evidence`、章节映射不完整；
- 对数底数、信息单位和指数还原的结构化声明冲突；
- 可执行案例的期望值与复算结果不一致。

### `review-required`

- 新符号可能晚于首次使用才解释；
- 公式只有结果，没有直觉、代入或解释；
- 公式密度过高；
- 同一含义疑似使用多个未声明别名。

### L4人工判断

- 推导是否正确且省略步骤合理；
- 符号选择是否适合目标读者；
- 数值案例是否真正解释概念；
- 公式深度是否与页面目标匹配；
- 类比、图示和公式是否共同降低而非增加认知负担。

## 9. 禁止事项

- 禁止通过把公式放进等宽字体框来制造“技术感”。
- 禁止把源代码变量名直接替换进数学句子。
- 禁止用空格排版矩阵、分式或分段函数。
- 禁止只生成公式而不生成符号解释。
- 禁止为了满足门禁数量而增加与学习目标无关的公式。
- 禁止把渲染正确当成数学正确或教学有效。
