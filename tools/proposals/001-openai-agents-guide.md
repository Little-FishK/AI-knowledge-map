## 二、🆕 新增节点（3 个）

### 1. `multi-agent` 多 Agent 编排

- **大区**：coding 编程与 Agent
- **建议层级**：`base` ｜ 理由：Manager / Handoff 这两种模式已被广泛采用并稳定，不是新冒出来的东西
- **heat**: 0.7
- **aliases**: Multi-agent, Manager 模式, Handoff, 交接

**summary**：把工作拆给多个 Agent 协作完成，两种主流模式：中心调度与对等交接。

**body**：

> **是什么**
>
> 当单个 [[agent]] 的工具太多、指令太复杂时，把工作拆给多个各司其职的 Agent。两种主流模式：
>
> | 模式 | 怎么运作 | 谁在控场 |
> |---|---|---|
> | **Manager（Agent 即工具）** | 一个中心 Agent 通过 [[tool-calling]] 调用各专业 Agent，自己汇总结果 | 中心 Agent 全程控场，用户只和它对话 |
> | **Decentralized（交接）** | 各 Agent 平等，一个把控制权**单向移交**给另一个，连同对话状态一起 | 移交后原 Agent 不再参与 |
>
> 关键区别是**控制权**：Manager 模式里子 Agent 只是被调用的工具，结果要回到中心；交接模式里控制权真的转移了，接手的 Agent 直接面对用户。
>
> **为什么不该急着上多 Agent**
>
> 多个 Agent 看起来更清晰（职责分离），但引入了真实的额外成本：跨 Agent 的上下文传递、更多的失败点、更难的调试和评测。
>
> **默认应该先把单个 Agent 的能力做满**——加工具比加 Agent 便宜得多。出现下面两种信号才考虑拆：
>
> - **逻辑过于复杂**：提示里塞满 if-then-else 分支，模板难以维护
> - **工具过载**：注意问题不在工具**数量**，而在**相似度**。十几个界限清晰的工具可能没问题，而几个功能重叠的工具就会让模型频繁选错。先试着把工具描述写清楚，无效再拆
>
> **它的代价**
>
> 每一次移交或调用都要传递上下文，而 [[context-window]] 是有限的——多 Agent 系统很容易在传递中丢失信息。失败也更难定位：出问题时要判断是哪个 Agent 的哪一步判断错了。

**cases**：

1. **Manager 模式的典型场景** — 「把『你好』翻译成西班牙语、法语和意大利语」：中心 Agent 分别调用三个翻译 Agent（作为工具），拿回三份结果后合成一个回答。用户全程只感知到一个助手。
2. **交接模式的典型场景** — 客服系统里，分诊 Agent 判断用户问的是订单问题，就把控制权连同对话历史一起交给订单 Agent，自己退出。适合「专业 Agent 需要完全接手」的场景。
3. **工具过载不是数量问题** — 有的系统能管好 15 个界限清晰的工具，有的却在 10 个功能重叠的工具上翻车。拆分之前先问：是不是把工具描述写清楚就能解决？

### 2. `guardrails` 护栏

- **大区**：safety 安全与对齐
- **建议层级**：`base` ｜ 理由：分层防御是安全工程的成熟做法，不是新概念
- **heat**: 0.8
- **aliases**: Guardrails, 防护栏, 输入输出过滤

**summary**：在模型前后加多道独立检查，用分层防御把风险挡在外面。

**body**：

> **是什么**
>
> 在模型的输入侧和输出侧加装的一系列独立检查，用来拦截风险内容和危险操作。
>
> **核心思路：分层，而不是找一个万能拦截器**
>
> 这是护栏最该理解的一点。**任何单一手段都会被绕过**——[[jailbreak]] 那一节讲过原因：防守方要覆盖所有表达方式，攻击方只需找到一种漏网的。
>
> 所以正确做法不是把一道检查做到完美，而是**叠加多道机制不同的检查**，让攻击者必须同时绕过所有层。
>
> **常见的几层**
>
> | 类型 | 拦什么 | 机制 |
> |---|---|---|
> | 规则检查 | 已知的固定威胁 | 黑名单、长度上限、正则。确定性，最便宜 |
> | 相关性判断 | 跑题的请求 | 判断输入是否在业务范围内 |
> | 安全分类 | [[jailbreak]] 与 [[prompt-injection]] | 专门训练的分类器 |
> | 内容审核 | 仇恨、骚扰、暴力等有害内容 | 通常用现成的审核模型 |
> | PII 过滤 | 个人身份信息泄露 | 检查**输出**，不只是输入 |
> | 输出校验 | 不合品牌调性或事实存疑的回答 | 生成之后再验一遍 |
> | **工具风险分级** | 高危操作 | 见下 |
>
> **工具风险分级值得单独说**
>
> 给每个工具按风险打分——**只读还是写入、能不能撤销、需要什么权限、有没有资金影响**——然后用分级触发不同处理：低风险直接执行，中风险加检查，高风险必须人工确认。
>
> 这条比内容检测更可靠，因为它**不依赖识别出攻击**：哪怕 [[agent]] 被彻底劫持，它能碰的高危操作仍然卡在人工确认那一关。
>
> **怎么建**
>
> 别试图一次设计完备。可行的顺序是：先覆盖数据隐私和内容安全这两条底线 → 遇到真实的漏网案例再补一层 → 随 Agent 演进持续调整。
>
> **它不能替代什么**
>
> 护栏是**应用层**的防御，替代不了认证授权、访问控制、常规软件安全这些基础设施层面的东西。两者是叠加关系。

**cases**：

1. **为什么 PII 要查输出而不只是输入** — 用户没提任何隐私信息，但 Agent 从数据库检索到了别人的手机号并写进了回答。只查输入的护栏对此完全无感。
2. **风险分级怎么落地** — 「查询订单状态」是只读、可撤销、无资金影响 → 低风险，直接执行。「发起退款」是写入、不可撤销、有资金影响 → 高风险，必须人工确认。**这个判断和模型能力无关，是纯粹的工程设计。**

### 3. `model-selection` 模型选型与成本

- **大区**：building 应用搭建
- **建议层级**：`base` ｜ 理由：是每个 LLM 应用都要做的工程决策，方法论稳定
- **heat**: 0.65
- **aliases**: Model Selection, 选型, 成本优化

**summary**：不是所有任务都需要最强的模型——先用最强的建立基线，再往下换。

**body**：

> **是什么**
>
> 在能力、延迟、成本三者之间为每个任务挑合适的模型。**同一个应用里的不同环节，通常该用不同的模型。**
>
> **为什么不能一律用最强的**
>
> 因为能力、延迟、成本大致是同向的：更强通常也更慢更贵。而一个应用里的任务难度差异很大——意图分类、格式转换、简单检索，用小模型完全够；而「要不要批准这笔退款」这种需要权衡的判断才值得上最强的。
>
> 一律用最强模型，等于为简单任务付了不必要的钱和延迟。
>
> **推荐的顺序（反直觉但有效）**
>
> 1. **先用最强的模型把原型跑通**，建立一条性能基线
> 2. 再逐个环节换成更小的模型，看结果还能不能接受
> 3. 保留那些换小之后仍然合格的
>
> 为什么是这个顺序：**如果一开始就用小模型，你无法区分「这个任务本来就做不了」和「这个模型不够强」**。先用最强的划出上界，后面的每一次降级才有参照。
>
> **前提：得先有评测**
>
> 没有一套能自动跑的评测，「换小之后结果还能不能接受」就只能靠感觉。所以选型的第一步其实是建立评测基线——这一步做不了，后面的优化都是盲调。
>
> **其他成本杠杆**
>
> 换模型不是唯一手段：[[prompt-caching]] 能大幅削减长提示的重复开销，批量接口通常有折扣，把 [[context-window]] 里塞的东西精简掉既省钱又常常提升效果。

**cases**：

1. **一个应用里的分工** — 用小模型做意图分类和格式化（每次调用便宜、快），用最强的模型做需要权衡的核心判断。**混合使用的成本可能只有一律用最强模型的几分之一，而质量几乎不降。**
2. **为什么不能反过来** — 先用小模型做原型，效果不好时你会陷入「是提示词不对、还是 RAG 没检索到、还是模型不行」的三重猜测。先用最强的排除掉最后一项，问题空间立刻小一半。

## 三、➕ 给现有节点追加内容（不改写正文）

### 1. `tool-calling` — 追加一个案例

> **工具的三种类型** — 数据类（查数据库、读文档、搜网页，用来**获取上下文**）、行动类（发邮件、改记录、转人工，用来**改变外部状态**）、编排类（把另一个 Agent 当作工具调用）。**区分它们的实际意义在于风险**：数据类基本只读，行动类可能不可逆——这正是工具风险分级的依据，见 [[guardrails]]。

### 2. `prompt-engineering` — 追加一个案例

> **用模板代替一堆散提示** — 与其为每个场景各维护一条提示词，不如用一条带变量的基础模板（`你正在服务 {{用户名}}，该用户最常反馈 {{问题类型}}`）。新场景来了改变量而不是重写，维护和评测成本都低得多。**这是在单 Agent 内部控制复杂度的主要手段**，也是拆成多 Agent 之前该先试的一步。

### 3. `agent-frameworks` — 追加一个案例

> **声明式 vs 代码优先** — 有的框架要求你预先把整个工作流画成图（节点是 Agent、边是跳转），可视化清晰，但工作流一动态就变得笨重，还得学一套专用的表达方式。另一类直接用普通代码表达流程，不必预先定义整张图，更灵活。**这是选框架时的主要分歧点**，比对比功能列表更值得先想清楚。

## 五、审核要点

我认为最值得你判断的三处：

1. **`guardrails` 和现有 `prompt-injection` 的防御部分重叠**。现有 `prompt-injection` 正文里已有「纵深防御」一节列了最小权限、沙箱、人工确认。我的处理是：`prompt-injection` 讲**为什么防不住**，`guardrails` 讲**怎么系统地防**，两者用 `mitigates` 边连起来。你觉得这个分工清楚吗？还是应该合并？

2. **三个新节点我都建议 `base` 而不是默认的 `emerging`**。理由是它们都不是新冒出来的东西（分层防御、按风险分级、先强后弱地选型，都是成熟工程做法）。如果你更想严守「新捕获默认进活跃层」，告诉我改。

3. **`model-selection` 是否该并进 `prompt-engineering` 的「实践顺序」那一节**？我判断不该——选型是独立的工程决策，有自己的方法论和成本杠杆。但它确实和「先提示、再 RAG、后微调」那条链有关联。
